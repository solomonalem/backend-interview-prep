Section 01 · 22 questions

Node.js runtime

The event loop is the most-asked backend Node topic. Understand it properly and half the performance, concurrency, and debugging questions answer themselves.

The event loop & concurrency model

N01Node is single-threaded — so how does it serve thousands of concurrent requests?

Your JavaScript executes on one thread, but I/O does not. Node delegates work to libuv, which uses the operating system's asynchronous facilities (epoll on Linux, kqueue on macOS, IOCP on Windows) for network I/O, and a small thread pool — four threads by default, tunable via UV_THREADPOOL_SIZE — for work the OS can't do asynchronously: file system operations, dns.lookup, and some crypto and zlib.

So while one request waits on a database, the single JS thread is free to start the next. Concurrency comes from never sitting idle, not from parallelism.

Most common use case — the difference in practice
// GOOD — the thread is released while the DB works.
// 1,000 concurrent callers all make progress.
app.get('/orders/:id', async (req, res) => {
  const order = await db.orders.findById(req.params.id);  // yields
  res.json(order);
});

// BAD — this is CPU work on the main thread. For the whole time
// this runs, EVERY other request is frozen, not just this one.
app.get('/report', (req, res) => {
  let total = 0;
  for (let i = 0; i < 5e8; i++) total += heavyMath(i);  // ~10s block
  res.json({ total });
});
Senior signalSay "non-blocking for I/O," not just "non-blocking." Then volunteer that CPU-bound work needs worker_threads and multi-core usage needs cluster — different problems, different answers.
N02Walk through the phases of the event loop.

The phase that matters most is poll: it retrieves new I/O events and runs their callbacks, and if nothing else is pending it will block there waiting for I/O rather than spinning.

Most common use case — knowing when a callback actually runs
// Inside an I/O callback the ordering IS deterministic:
fs.readFile('config.json', () => {
  setTimeout(() => console.log('timeout'), 0);
  setImmediate(() => console.log('immediate'));
  // → immediate, then timeout.
  // We are in POLL, so CHECK (setImmediate) comes before
  // looping around to TIMERS again.
});
Common mistakesetTimeout(fn, 0) does not run "immediately." It runs in the next timers phase, and the real minimum delay is about 1ms.
N03Order these: process.nextTick, Promise.then, setTimeout(fn,0), setImmediate. 
setTimeout(() => console.log('1 timeout'), 0);
setImmediate(() => console.log('2 immediate'));
Promise.resolve().then(() => console.log('3 promise'));
process.nextTick(() => console.log('4 nextTick'));

// Output: 4 nextTick → 3 promise → then 1 and 2 in EITHER order.
// nextTick drains first, then microtasks, both before the loop
// advances. timeout-vs-immediate at top level is genuinely
// non-deterministic: it depends on whether process startup took
// longer than the 1ms timer threshold.
Most common use case — deferring work without starving the loop
// Chunk a large synchronous job so I/O still gets serviced.
// setImmediate yields to the loop; a recursive nextTick would NOT —
// it would drain forever and starve every pending request.
function processInChunks(items, i = 0) {
  const end = Math.min(i + 1000, items.length);
  for (; i < end; i++) transform(items[i]);
  if (i < items.length) setImmediate(() => processInChunks(items, i));
}
N04What is the microtask queue and how does it differ from macrotasks?

Microtasks are promise continuations (.then, await resumptions, queueMicrotask). The entire microtask queue drains to empty before the loop proceeds — and a microtask that schedules another microtask is handled in the same drain. Macrotasks (timers, I/O callbacks, setImmediate) are processed one phase at a time.

Most common use case — the "async but still blocking" trap
// Looks async. Isn't cooperative. 100,000 awaits generate 100,000
// microtasks that ALL drain before any I/O is serviced.
for (const row of hundredThousandRows) {
  await validate(row);      // no real I/O inside → pure microtask churn
}

// Fix: yield to the macrotask queue periodically.
let n = 0;
for (const row of hundredThousandRows) {
  await validate(row);
  if (++n % 500 === 0) await new Promise(r => setImmediate(r));
}
N05How would you detect that something is blocking the event loop in production?

Measure event loop lag — the delay between when a timer should fire and when it actually does. Node exposes this properly through perf_hooks.

Most common use case — a production lag metric
const { monitorEventLoopDelay } = require('perf_hooks');

const h = monitorEventLoopDelay({ resolution: 20 });  // sample every 20ms
h.enable();

setInterval(() => {
  logger.info({
    loopLagP99Ms:  h.percentile(99) / 1e6,   // histogram is in nanoseconds
    loopLagMeanMs: h.mean / 1e6
  });
  h.reset();                                  // each window independent
}, 10000).unref();                            // unref → won't hold process open

// Alarm when p99 > ~100ms. That means some callback is hogging the
// thread long enough that users feel it.

Once you know it's happening, find what with a CPU profile — node --cpu-prof, Chrome DevTools via --inspect, or clinic.js flame graphs. The framing that impresses: measure, then profile, then optimize — never guess.

N06Cluster vs worker_threads vs child_process — when do you reach for each?
Most common use case — moving CPU work off the request path
// server.js — hand heavy work to a worker so the loop stays free
const { Worker } = require('node:worker_threads');

function runHeavy(payload) {
  return new Promise((resolve, reject) => {
    const w = new Worker('./heavy-worker.js', { workerData: payload });
    w.once('message', resolve);
    w.once('error', reject);
    w.once('exit', code => code !== 0 && reject(new Error('worker ' + code)));
  });
}

app.post('/analyze', async (req, res) => {
  const result = await runHeavy(req.body);   // main thread never blocks
  res.json(result);
});

// heavy-worker.js
const { workerData, parentPort } = require('node:worker_threads');
parentPort.postMessage(expensiveComputation(workerData));

// In production, POOL the workers (piscina) — spawning one per
// request costs ~30ms of startup and unbounded memory.

N08What's the difference between a Buffer and a string, and when does it bite you?

A Buffer is a fixed-length sequence of raw bytes allocated outside the V8 heap. Strings are UTF-16 sequences inside the heap. Converting between them requires an encoding, and getting it wrong corrupts data.

Most common use case — verifying a webhook signature
// Signatures MUST be computed over the RAW bytes. If a body parser
// has already parsed and re-serialized the JSON, key order and
// whitespace change and the signature will never match.
app.post('/webhooks/payer',
  express.raw({ type: 'application/json' }),   // keep it as a Buffer
  (req, res) => {
    const expected = crypto.createHmac('sha256', SECRET)
                            .update(req.body)          // Buffer, not string
                            .digest();
    const given = Buffer.from(req.get('x-signature'), 'hex');

    // timingSafeEqual prevents a timing side-channel; it throws on
    // length mismatch, so check length first.
    if (given.length !== expected.length ||
        !crypto.timingSafeEqual(given, expected)) {
      return res.status(401).end();
    }
    handle(JSON.parse(req.body.toString('utf8')));
    res.status(204).end();
  });

The other classic bite: chunking a stream on byte boundaries can split a multi-byte UTF-8 character across two chunks, producing mojibake. string_decoder exists to buffer those partial characters.

N10How does require caching work, and how can it cause bugs?

Node caches modules by resolved filename. The module body executes exactly once; every later require returns the same exports object. That's why the module pattern works as a singleton.

Most common use case — and the data-leak bug it enables
// db.js — GOOD use of module caching: one pool for the process
const { MongoClient } = require('mongodb');
const client = new MongoClient(process.env.MONGO_URL);
module.exports = client;      // every requirer gets this same client

// context.js — DANGEROUS: module-level mutable state is GLOBAL.
// One module instance serves every concurrent request, so request A
// can read request B's user. This is a real security bug.
let currentUser = null;
module.exports = { set: u => { currentUser = u; }, get: () => currentUser };

// The correct tool for per-request state is AsyncLocalStorage (E10).
N11How do you find a memory leak in a Node service?
  1. Confirm it. Watch heap used across GC cycles — a leak trends upward, normal churn sawtooths.
  2. Snapshot at two points under load.
  3. Compare in the DevTools Memory tab and trace retainers to find what holds the reference.
Most common use case — the two leaks you'll actually find
// LEAK 1 — a listener added per request, never removed. The emitter
// is long-lived, so every closure it holds survives forever.
app.get('/subscribe', (req, res) => {
  eventBus.on('update', () => res.write('data: ping\n\n'));  // leaks
});
// FIX: remove on disconnect
app.get('/subscribe', (req, res) => {
  const onUpdate = () => res.write('data: ping\n\n');
  eventBus.on('update', onUpdate);
  req.on('close', () => eventBus.off('update', onUpdate));
});

// LEAK 2 — an unbounded module-level cache.

// FIX: bound it by size AND time
const LRU = require('lru-cache');
const cache = new LRU({ max: 5000, ttl: 60000 });

// Grab a snapshot from a live prod process:

Watch for MaxListenersExceededWarning — that is Node telling you about leak 1 before it becomes an outage.

N12Operational errors vs programmer errors — why does the distinction matter?

Operational errors are expected runtime conditions: invalid input, a database timeout, an upstream 503. You handle these. Programmer errors are bugs: reading a property of undefined, a typo. You do not handle these — the process is in an unknown state, so log and exit.

Most common use case — a typed error your handler can branch on
class AppError extends Error {
  constructor(message, statusCode, code, details) {
    super(message);
    this.statusCode    = statusCode;   // 400, 404, 409…
    this.code          = code;         // 'ORDER_NOT_FOUND' — stable string
    this.details       = details;
    this.isOperational = true;         // ← the flag that decides everything
    Error.captureStackTrace(this, this.constructor);
  }
}

// Service layer — expected condition, so throw an AppError
if (!order) throw new AppError('Order not found', 404, 'ORDER_NOT_FOUND');

// Error handler — branch on the flag
if (err.isOperational) {
  res.status(err.statusCode).json({ code: err.code, message: err.message });
} else {
  logger.fatal({ err }, 'programmer error — restarting');
  res.status(500).json({ code: 'INTERNAL' });
  gracefulShutdown();                // do not keep serving
}
Trap"Catch everything and keep the server running" is the wrong answer. Continuing after an uncaught exception risks serving corrupted data — worse than a two-second restart.

N14How do you implement graceful shutdown?
Most common use case — zero-downtime deploys
let ready = true;
app.get('/health/ready', (_r, res) => res.status(ready ? 200 : 503).end());

async function shutdown(signal) {
  logger.info({ signal }, 'shutting down');
  ready = false;                          // 1. LB stops routing to us
  await sleep(5000);                        //    give it time to notice

  await new Promise(r => server.close(r));   // 2+3. drain in-flight
  await consumer.disconnect();              // stop taking new messages
  await mongo.close();                      // 4. release resources
  process.exit(0);
}

['SIGTERM', 'SIGINT'].forEach(s => process.on(s, () => shutdown(s)));

// Keep the total under the orchestrator's grace period
// (Kubernetes terminationGracePeriodSeconds, default 30s) or you
// get SIGKILLed mid-drain anyway.

N16You need to call an API for 10,000 records. How do you avoid destroying it?

Promise.all over 10,000 items fires 10,000 concurrent requests — you exhaust sockets, blow the target's rate limit, and probably get blocked. You need bounded concurrency.

Most common use case — a bulk sync or migration job
const pLimit = require('p-limit');
const limit = pLimit(10);            // at most 10 in flight, ever

const results = await Promise.allSettled(
  records.map(r => limit(() => syncOne(r)))
);

async function syncOne(record, attempt = 1) {
  try {
    return await http.post('/upstream', record, { timeout: 5000 });
  } catch (err) {
    const retryable = err.code === 'ETIMEDOUT' ||
                      [429, 502, 503, 504].includes(err.status);
    if (!retryable || attempt >= 3) throw err;   // never retry a 400

    // exponential backoff + JITTER: without jitter every client
    // retries at the same instant and re-kills the recovering service
    const base  = 200 * 2 ** (attempt - 1);
    const delay = err.retryAfter ?? base + Math.random() * base;
    await sleep(delay);
    return syncOne(record, attempt + 1);
  }
}
N17What's the most common async/await performance mistake?

Accidental serialization — awaiting independent operations one at a time.

Most common use case — building a composite response
// SLOW — 3 sequential round trips: 600ms
const user    = await userSvc.get(id);          // 200ms
const orders  = await orderSvc.list(id);        // 200ms
const credits = await billingSvc.credits(id);   // 200ms

// FAST — independent, so start all three at once: 200ms
const [user, orders, credits] = await Promise.all([
  userSvc.get(id), orderSvc.list(id), billingSvc.credits(id)
]);

// When there IS a dependency, only that part serializes:
const user = await userSvc.get(id);
const [orders, plan] = await Promise.all([   // both need user fields
  orderSvc.list(user.accountId),
  planSvc.get(user.planId)
]);
N18What is the EventEmitter and when would you use it?

Node's observer pattern, and the base class for streams, HTTP servers, and process. Use it to decouple producers from consumers within one process.

Most common use case — side effects off the critical path
const { EventEmitter } = require('node:events');
const bus = new EventEmitter();

// ALWAYS attach an error listener — an unhandled 'error' event
// throws and crashes the process.
bus.on('error', err => logger.error({ err }, 'event bus error'));

bus.on('order.placed', o => auditLog.write(o));
bus.on('order.placed', o => searchIndex.upsert(o));

await db.orders.insertOne(order);
bus.emit('order.placed', order);   // listeners run SYNCHRONOUSLY, in
                                   // registration order, blocking emit()
Connect the dotsAn EventEmitter is in-process only. The moment you run two replicas, half your listeners miss half the events — which is exactly where you need a real broker (SNS, SQS, Kafka). The API looks similar; the delivery guarantees are completely different.

N20npm install vs npm ci, and what is the lockfile for?

N21What are the biggest Node performance wins in a typical API?
  1. Fix the database first. Missing indexes and N+1 queries dwarf everything else.
  2. Don't block the loop. One synchronous call in a hot path costs more than every micro-optimization combined.
  3. Reduce payload size. Project only needed fields, compress, paginate.
  4. Reuse connections. Keep-alive agents outbound, correctly sized DB pools.
  5. Cache the expensive and stable.
  6. Scale out — after the above, not before.
Most common use case — the keep-alive agent people forget
const { Agent } = require('undici');

// Without keep-alive, every outbound call pays a fresh TCP + TLS
// handshake — often 100ms+ of pure overhead per request.

  keepAliveTimeout: 60000,
  connections: 50           // doubles as a BULKHEAD: bounds how many
});                         // sockets one slow dependency can consume

const res = await fetch('https://payer.example.com/claims', {
  dispatcher: agent,
  signal: AbortSignal.timeout(3000)   // never an unbounded call
});
Senior signalLead with "measure first." Candidates who start listing micro-optimizations without mentioning profiling are signalling they've never done this on a real system.

Express.js

Express is deliberately minimal, so interviewers go deep on the few concepts it does have. Middleware ordering and async error handling are where most candidates stumble.

The middleware model

E01What is middleware in Express, and how does the chain work?

A middleware is a function with the signature (req, res, next) in an ordered pipeline. Each can read and mutate req/res, end the response, or call next() to pass control on. Express walks the stack in registration order, matching path and method.

Most common use case — a production middleware stack, in order
app.disable('x-powered-by');              // stop advertising the framework

app.use(helmet());                        // 1. security headers
app.use(cors({ origin: ALLOWED }));       // 2. explicit allowlist
app.use(express.json({ limit: '1mb' })); // 3. bounded body parsing
app.use(correlationId);                   // 4. tracing — before logging
app.use(requestLogger);                   // 5. logs now carry the id
app.use('/api', rateLimiter);            // 6. BEFORE auth, so unauthenticated
                                          //    attackers can't burn CPU on JWT verify
app.use('/api', authenticate);            // 7. who are you
app.use('/api/v1/orders', orderRouter);   // 8. routes (authorize inside)
app.use(notFoundHandler);                 // 9. 404 for anything unmatched
app.use(errorHandler);                    // 10. MUST be last, 4 args

Three things a middleware can do: continue (next()), terminate (res.send()), or fail (next(err)). Doing none of the three hangs the request until the client times out.

E02Why does middleware order matter? Give concrete failures.
  • Error handler registered before your routes → it never sees their errors.
  • authenticate after the route → the route runs unauthenticated. A real security hole, and one of the first things to check when investigating an authorization bypass.
  • Rate limiter after authentication → unauthenticated attackers get free JWT verification, which is CPU-expensive with RS256.
  • Body parsing after a route → req.body is undefined inside it.
  • Logger before correlation ID → your logs have no ID to correlate on.
Trapapp.use('/api', x) treats the path as a prefix, so it matches /api/anything/deep. app.get('/api', x) requires an exact match. Mixing these up silently leaves routes unprotected.
E03How do you write a centralized error handler?

Express identifies an error handler by arity — four parameters — and it must be registered last.

Most common use case — one handler, RFC 7807 output, no leaks
// The 4th arg is required for Express to recognise this as an
// error handler, even though it's unused.
// eslint-disable-next-line no-unused-vars
app.use((err, req, res, next) => {
  const status = err.statusCode || 500;

  // Log everything internally, including the stack…

E12What is the request lifecycle in Express, end to end?
  1. Node's HTTP server parses headers and emits request.
  2. Express extends req/res with its own prototypes.
  3. The router walks the middleware stack, matching method and path.
  4. Body-parsing middleware consumes the request stream into req.body.
  5. The route handler writes headers and body via res.
  6. On res.end() the response flushes and finish fires — that's where you log status and duration.
  7. Any next(err) jumps straight to the first four-argument handler.
Most common use case — logging on finish, not at the top
app.use((req, res, next) => {

  // 'finish' fires once the response is fully flushed, so this is
  // the only place you know the real status and duration.
  res.on('finish', () => {
    logger.info({
      method: req.method, path: req.route?.path ?? req.originalUrl,
      status: res.statusCode,
      ms: Number(process.hrtime.bigint() - start) / 1e6
    });
  });
  next();
});

E15What are health check endpoints and why are there two kinds?

Liveness answers "is this process wedged?" — cheap, checks nothing external. Failing it restarts the container. Readiness answers "can this instance serve traffic now?" — checks dependencies. Failing it removes you from the load balancer without a restart.

Most common use case — and the outage the wrong version causes
// LIVENESS — deliberately dumb. If the process responds, it lives.
app.get('/health/live', (_req, res) => res.status(200).send('ok'));

// READINESS — checks dependencies, with a short timeout.
app.get('/health/ready', async (_req, res) => {
  try {
    await Promise.all([
      mongo.db().admin().ping(),
      redis.ping()
    ].map(p => withTimeout(p, 1000)));
    res.status(ready ? 200 : 503).json({ status: 'ready' });
  } catch (err) {
    res.status(503).json({ status: 'degraded', error: err.code });
  }
});

REST & API design

Expect design questions where they hand you a domain and ask you to model the endpoints. What they're grading is whether you reach for nouns, correct status codes, and idempotency without being prompted.

Fundamentals

R01What actually makes an API RESTful?

Six constraints from Fielding's dissertation: client-server separation, statelessness, cacheability, a uniform interface, a layered system, and optionally code-on-demand. The ones that carry weight in practice:

  • Statelessness — every request carries what's needed to process it. No server-side session affinity. This is what makes horizontal scaling possible, which is why it matters for microservices.
  • Uniform interface — resources identified by URI, manipulated through representations, standard methods with standard semantics.
  • Cacheability — responses declare whether and how long they can be cached.

Honest framing: almost nothing in industry is fully RESTful. Most APIs sit at level 2 of the Richardson Maturity Model and skip hypermedia entirely. Saying that shows you know both the theory and the practice.

R04How do you make a POST safe to retry?
Most common use case — payments, order placement, any create
// db.idempotency has: unique index on { key: 1, userId: 1 }
//                     TTL index on { createdAt: 1 } expireAfter 24h
async function withIdempotency(key, userId, fn) {
  const existing = await idem.findOne({ key, userId });
  if (existing?.status === 'completed') return existing.response;
  if (existing?.status === 'in_progress')
    throw new AppError('Request already in progress', 409, 'IN_FLIGHT');

  const session = client.startSession();
  try {
    let result;
    await session.withTransaction(async () => {
      // The unique index makes the concurrent case safe: two
      // simultaneous requests race, exactly one insert wins.
      await idem.insertOne({ key, userId, status: 'in_progress',
                            createdAt: new Date() }, { session });
      result = await fn(session);          // business write, same txn
      await idem.updateOne({ key, userId },
        { $set: { status: 'completed', response: result } }, { session });
    });
    return result;
  } finally { await session.endSession(); }
}

// Route usage
app.post('/api/v1/orders', async (req, res) => {
  const key = req.get('Idempotency-Key');
  if (!key) throw new AppError('Idempotency-Key required', 400, 'NO_KEY');
  res.status(201).json(await withIdempotency(key, req.user.id,
                        session => orderSvc.place(req.body, session)));
});

R10How do you prevent lost updates when two users edit the same record?

Optimistic concurrency control: the server returns a version fingerprint, the client sends it back, and the server rejects if it no longer matches.

Most common use case — ETag + If-Match
app.get('/api/v1/orders/:id', async (req, res) => {
  const o = await orders.findOne({ _id: toId(req.params.id) });
  res.set('ETag', `"${o.version}"`).json(o);
});

app.patch('/api/v1/orders/:id', async (req, res) => {
  const ifMatch = req.get('If-Match');
  if (!ifMatch) throw new AppError('If-Match required', 428, 'NO_ETAG');

  // The version check is part of the QUERY, not a read-then-write.
  // That makes it atomic — no race between checking and updating.
  const r = await orders.updateOne(
    { _id: toId(req.params.id), version: Number(ifMatch.replace(/"/g,'')) },
    { $set: req.body, $inc: { version: 1 } }
  );

  if (r.matchedCount === 0) {
    // Either it's gone, or someone else wrote first.
    throw new AppError('Modified by another user', 409, 'STALE_VERSION');
  }
  res.status(204).end();
});

The alternative — pessimistic locking on read — is simpler to reason about but hurts throughput and needs lock expiry to survive a crashed client. Optimistic is right for the overwhelming majority of web APIs because conflicts are rare.

R11Explain HTTP caching: Cache-Control, ETag, conditional requests.
Most common use case — three different caching postures
// 1. Reference data that rarely changes — cache hard at the edge

//    stale-while-revalidate: serve the old copy INSTANTLY while
//    refreshing in the background. Huge perceived-speed win.

// 2. Per-user data — private, revalidate every time
res.set('Cache-Control', 'private, no-cache');
res.set('ETag', `"${hash}"`);
if (req.get('If-None-Match') === `"${hash}"`) return res.status(304).end();
//    304 = no body sent. Saves bandwidth, not the round trip.

// 3. Sensitive data (PHI, financial) — never store, anywhere
res.set('Cache-Control', 'private, no-store');
//    'private' alone still allows the BROWSER to write it to disk.

Caching is the cheapest performance work available, and most teams never set a single header.

R15What's the difference between PUT and PATCH, really?

PUT replaces the entire resource — omitted fields should be cleared, not preserved. PATCH applies a partial modification. Most teams get PUT wrong by treating it as partial, which makes it non-idempotent in practice and confuses clients.

Most common use case — the two standardised PATCH formats
// JSON Merge Patch (RFC 7386) — Content-Type: application/merge-patch+json
// Send only what changes; null DELETES a field.
PATCH /orders/o1
{ "status": "shipped", "notes": null }
// Simple — but you can't express "append to an array".

// JSON Patch (RFC 6902) — Content-Type: application/json-patch+json
// An array of explicit operations. Handles arrays and preconditions.
PATCH /orders/o1
[
  { "op":"test",    "path":"/version",  "value": 7 },  // concurrency guard
  { "op":"replace", "path":"/status",   "value":"shipped" },
  { "op":"add",     "path":"/items/-",  "value":{"sku":"X-9"} }
]

Data modelling

M01Embed or reference? How do you decide?

The heuristic: data read together should be stored together, unless that makes the document unbounded.

Embed whenReference when
One-to-one, or one-to-few with a hard boundOne-to-many where "many" is unbounded
The child has no meaning without the parentThe child is queried independently
Always fetched togetherMany-to-many
Updated together (atomicity within one document)The child changes far more often than the parent
Most common use case — the update pattern each choice enables
// EMBEDDED: a single atomic update, no transaction needed.
// Single-document writes have ALWAYS been atomic in MongoDB.
await customers.updateOne(
  { _id: 'c1', 'addresses.type': 'billing' },
  { $set: { 'addresses.$.city': 'Dallas' } }   // $ = matched element
);

// REFERENCED: two writes → needs a transaction to stay consistent.
// If you find yourself needing transactions often, that is a signal
// the schema is modelled relationally rather than for access patterns.
await session.withTransaction(async () => {
  await orders.insertOne(order, { session });
  await customers.updateOne({ _id: 'c1' },
                            { $inc: { orderCount: 1 } }, { session });
});

M02Name the MongoDB schema design patterns you know.
size

Subset

Embed only the hottest slice — the 5 most recent orders — and keep full history in a separate collection. Keeps the working set in RAM.

size

Bucket

Group time-series readings into one document per hour or day instead of one per reading. Far fewer documents and index entries.

reads

Computed

Store the aggregate (order count, lifetime value) on write instead of computing it on every read. Trades write cost for read speed.

reads

Duplicate the two or three fields you always need from a referenced document (customer name next to the ID) to avoid a lookup.

shape

Polymorphic

Store related-but-different shapes in one collection with a discriminator field. Fits Mongo's flexible schema naturally.

shape

Attribute

Turn sparse, variable fields into an array of key/value pairs so one index covers them all instead of dozens of sparse indexes.

shape

Outlier

Handle the rare document that breaks your model (the account with 40,000 records) with a flag and overflow documents, rather than designing for the worst case.

lifecycle

Schema versioning

A schemaVersion field on every document so the app can migrate lazily on read rather than in a big-bang migration.

lifecycle

Move cold data out, or let a TTL index expire it. Keeps indexes and the working set small.

writes

Approximation

For high-volume counters where exactness doesn't matter, increment by 10 one time in ten. Cuts write load by an order of magnitude.

Most common use case — the extended reference in practice
// Without it: every order list needs a second query or $lookup

// With it: the list renders from ONE query. You duplicate only the

M03What are the MongoDB anti-patterns?
  • Unbounded arrays — embedding a list that grows forever. Hits the 16MB cap, and destroys write performance long before that.
  • Massive documents — the whole document is read into memory even if you project one field.
  • Bloated documents you never read — pushes the working set out of RAM.
  • Case-insensitive queries without a collation index — forces a collection scan.
  • A relational schema ported straight over — normalized tables becoming collections, then $lookup everywhere. The most common mistake teams make coming from SQL.
  • $where and mapReduce — execute JavaScript server-side; slow and a security risk.
Most common use case — fixing an unbounded array
// ANTI-PATTERN: comments grow without limit inside the post.
{ _id: 'p1', title: '…', comments: [ /* 40,000 and counting */ ] }
// Every read pulls all 40,000. Every push rewrites the document.

// FIX — subset pattern: keep the newest N inline for display,
// full set in its own collection.
{ _id: 'p1', title: '…',
  commentCount: 40213,
  recentComments: [ /* exactly 5 */ ] }

await posts.updateOne({ _id: 'p1' }, {
  $push: {

      $each:  [newComment],
      $sort:  { createdAt: -1 },
      $slice: 5                // ← hard cap, enforced by the database
    }
  },
  $inc: { commentCount: 1 }

M04What is BSON and how does it differ from JSON?

BSON is Mongo's binary serialization format — a superset of JSON with ObjectId, Date, Decimal128, Binary, Int32/Int64, and regex types. It's length-prefixed so fields can be skipped without parsing.

Most common use case — why Decimal128 exists
// JavaScript numbers are IEEE 754 doubles. They cannot represent
// 0.1 exactly, and the error compounds across many operations.
0.1 + 0.2                       // → 0.30000000000000004
(19.99 * 3).toFixed(2)          // → "59.97"  … looks fine
let t = 0; for (let i=0;i<10;i++) t += 0.1;
t === 1                         // → false. This is how money goes missing.

// Decimal128 stores exact decimal values — use it for currency,
// dosages, or any quantity where a cent matters.
const { Decimal128 } = require('mongodb');
await orders.insertOne({
  total: Decimal128.fromString('19.99'),   // exact
  taxRate: Decimal128.fromString('0.0825')
});

// Aggregations respect it too:
{ $group: { _id: null, revenue: { $sum: '$total' } } }  // exact sum

// The other half of the fix: never use parseInt() on a decimal
// string — parseInt('19.99') === 19. Silent data loss.
M05What is an ObjectId and what's inside it?
Most common use case — free creation timestamps, and one trap
// 12 bytes: 4-byte timestamp | 5-byte random per process | 3-byte counter
const id = new ObjectId();
id.getTimestamp();                // → Date — creation time, for free

// Because the leading bytes are a timestamp, sorting by _id
// approximates sorting by creation time:
db.orders.find().sort({ _id: -1 }).limit(10);   // 10 newest, no extra index

// Generated CLIENT-side by the driver, so you know the id before
// the insert round-trips — useful for building references first:
const orderId = new ObjectId();
await Promise.all([
  orders.insertOne({ _id: orderId, … }),
  audit.insertOne({ subjectId: orderId, action: 'CREATE' })
]);

// TRAP: it's monotonically increasing, so as a SHARD KEY it sends
// every new write to one shard. Classic hot-shard mistake.

Indexing

M06Explain the ESR rule for compound indexes.
Most common use case — plus the prefix rule
db.orders.createIndex({ status: 1, createdAt: -1, qty: 1 });

// PREFIX RULE: one compound index also serves any LEFT prefix.
// This index covers all three of these queries:
db.orders.find({ status: 'active' })                              // ✔
db.orders.find({ status: 'active' }).sort({ createdAt: -1 })     // ✔
db.orders.find({ status: 'active', qty: { $gt: 30 } })
         .sort({ createdAt: -1 })                                 // ✔

// But NOT these — they skip the leading field:
db.orders.find({ qty: { $gt: 30 } })                              // ✘ COLLSCAN
db.orders.find().sort({ createdAt: -1 })                          // ✘

// That's why you can often replace three single-field indexes
// with one well-ordered compound index — fewer index writes,
// less RAM.

M08How do you read explain() output?
Most common use case — diagnosing a slow query
db.orders.find({ customerId: x, status: 'active' })
         .sort({ createdAt: -1 })
         .explain('executionStats');

{
  winningPlan: { stage: 'COLLSCAN' },   // ← 1. THE headline. No index used.
                                       //    You want IXSCAN.
  executionStats: {
    nReturned: 20,
    totalKeysExamined: 20,             // ← 3. keys == returned and
    totalDocsExamined: 500000,         // ← 2. selectivity: examined 500k
                                       //    to return 20 = index too weak
    executionTimeMillis: 1840
  }
}

//   COLLSCAN                      → no usable index
//   docsExamined >> nReturned     → index not selective enough
//   docsExamined === 0 &&
//     keysExamined === nReturned  → COVERED query (ideal)
//   a SORT stage present          → in-memory sort; index doesn't

//   rejectedPlans                 → what the optimizer discarded

db.orders.aggregate(pipeline).explain('executionStats');
M09What is a covered query?

A query answered entirely from the index — every field in the filter, sort, and projection is in the index, so Mongo never fetches the document. Enormously faster because it avoids random document reads.

Most common use case — a fast lookup/autocomplete endpoint
db.products.createIndex({ category: 1, name: 1, sku: 1 });

// COVERED — every field used is in the index.
db.products.find(
  { category: 'pharma' },
  { _id: 0, name: 1, sku: 1 }        // ← _id: 0 is REQUIRED
);
// _id is returned by default and is NOT in this index, so leaving
// it in silently breaks coverage. This is the #1 gotcha.

// NOT covered — 'price' isn't in the index, so Mongo must fetch
// every matching document from disk.
db.products.find({ category: 'pharma' }, { _id: 0, name: 1, price: 1 });
M10What's the cost of an index?

Indexes speed reads and slow writes: every insert, delete, and update to an indexed field must update every relevant index. They also consume RAM — and MongoDB's performance model depends on indexes fitting in memory. An index that doesn't fit means disk reads on every lookup, which can be slower than no index.

Most common use case — finding indexes nobody uses
// $indexStats shows access counts since the last server restart.
// An index with ops: 0 after weeks of uptime is pure write tax.
db.orders.aggregate([
  { $indexStats: {} },
  { $project: { name: 1, ops: '$accesses.ops', since: '$accesses.since' } },
  { $sort: { ops: 1 } }
]);

// Check total index size against available RAM:
db.orders.stats().totalIndexSize;      // bytes

// Rule: prefer one well-ordered compound index over three
// single-field ones (prefix rule, M06), and drop what $indexStats
// says nobody reads.

Aggregation

M11Walk through the aggregation pipeline stages you use most.
Most common use case — a revenue report
db.orders.aggregate([
  // 1. Filter FIRST so this stage uses an index and everything
  //    downstream works on a fraction of the data.
  { $match: { placedAt: { $gte: start }, status: 'fulfilled' } },

  // 2. Left outer join to another collection.
  { $lookup: { from: 'customers', localField: 'customerId',
               foreignField: '_id', as: 'customer' } },

  // 3. $lookup produces an ARRAY; unwind turns it into a field.
  { $unwind: '$customer' },

  // 4. Aggregate. _id is the grouping key; the rest are accumulators.
  { $group: { _id:        '$customer.region',
              revenue:    { $sum: '$total' },
              orderCount: { $sum: 1 },
              avgOrder:   { $avg: '$total' },
              topSkus:    { $addToSet: '$items.sku' } } },

  // 5. $sort immediately followed by $limit lets Mongo do a top-K
  //    sort instead of sorting everything.
  { $sort: { revenue: -1 } },
  { $limit: 20 },

  // 6. Rename _id to something meaningful for the API response.
  { $project: { _id: 0, region: '$_id', revenue: 1, orderCount: 1 } }
]);
M12How do you optimize an aggregation pipeline?
Most common use case — the same report, done badly then correctly
// SLOW — unwinds 10M documents into 60M, then throws most away.
db.orders.aggregate([
  { $unwind: '$items' },
  { $lookup: { from: 'products', … } },
  { $match: { placedAt: { $gte: start } } },      // filter LAST — too late
  { $group: { … } }
]);

// FAST — same result, orders of magnitude less work.
db.orders.aggregate([
  { $match:   { placedAt: { $gte: start } } },    // 1. index-backed filter
  { $project: { items: 1, total: 1, customerId: 1 } }, // 2. drop fat fields
  { $unwind:  '$items' },                       // 3. now on a small set
  { $lookup:  { from: 'products', … } },
  { $group:   { … } }
], { allowDiskUse: false });   // needing true is a design smell
  1. $match first, always.
  2. $project away unneeded fields early to cut memory per document.
  3. Never $unwind before $match.
  4. $limit right after $sort.
  5. Mind the 100MB per-stage memory limit.
  6. explain() the aggregation — the optimizer reorders some stages, and you should verify it did what you expected.
M13Is $lookup a real join? When should you avoid it?

It's a left outer join, but not equivalent to a relational one: it executes per input document, can only use an index on the foreign collection's join field, and doesn't work across shards in all configurations. On large collections it's often slower than two queries joined in application code.

Most common use case — designing the join away
// OPTION A — $lookup. Correct, but the cost scales with input size.
{ $lookup: { from: 'customers', localField: 'customerId',
             foreignField: '_id', as: 'customer' } }

// OPTION B — two queries, joined in Node. Often faster, and always
// easier to reason about. This is what Mongoose populate() does.
const orders = await db.orders.find(filter).toArray();
const ids    = [...new Set(orders.map(o => o.customerId))];
const custs  = await db.customers.find({ _id: { $in: ids } }).toArray();
const byId   = new Map(custs.map(c => [String(c._id), c]));
orders.forEach(o => { o.customer = byId.get(String(o.customerId)); });

// OPTION C — the Mongo-native answer: don't need the join at all.
// Extended reference (M02) keeps the 2 fields you display inline.
{ _id:'o9', customer:{ id:'c1', name:'Acme' }, total:42 }  // zero joins

Preferring option C demonstrates you think in Mongo rather than in SQL with different syntax.

M14What are change streams and what would you use them for?

A subscription to inserts, updates, deletes, and replacements on a collection, database, or deployment. Built on the replica set oplog — so it requires a replica set — and resumable via a token after a disconnect.

Most common use case — the outbox relay (connects to Section 05)
const stream = db.collection('outbox').watch(
  [{ $match: { operationType: 'insert' } }],
  { fullDocument: 'updateLookup',
    resumeAfter: await loadResumeToken() }   // survive restarts
);

  const evt = change.fullDocument;
  await broker.publish(evt.type, evt.payload);

Replication, sharding & consistency

M15Explain replica sets and elections.

A replica set is a group of mongod processes holding the same data: one primary that takes all writes, and secondaries replaying the primary's oplog (a capped collection of idempotent operations). Failover uses a raft-like election requiring a majority, which is why you run an odd number of voting members.

M16What are read and write concerns?
Most common use case — matching the guarantee to the operation
// FINANCIAL WRITE — must survive a failover. Slower, correct.
await payments.insertOne(doc, {
  writeConcern: { w: 'majority', j: true }
});
//   w:'majority' → a majority of members acknowledged; the write
//                  will NOT be rolled back by an election.
//   j:true       → also flushed to the on-disk journal.

// TELEMETRY WRITE — high volume, loss is acceptable. Fast.
await metrics.insertOne(doc, { writeConcern: { w: 1 } });

// READ THAT DRIVES A DECISION — must not see rollback-able data.
await accounts.findOne({ _id }, {
  readConcern:    { level: 'majority' },
  readPreference: 'primary'
});

// ANALYTICS READ — offload from the primary, tolerate staleness.
await orders.find(q, { readPreference: 'secondaryPreferred' });
// ⚠ This is where read-your-own-writes bugs come from: a user
//   saves, then reads from a lagging secondary and sees old data.
M17Explain sharding and how to choose a shard key.

Three properties for a shard key: high cardinality (enough distinct values to split indefinitely), even distribution (no hot shard), and query isolation (most queries include it so mongos can target one shard instead of scatter-gathering).

Senior signal"Most systems don't need sharding — vertical scaling and replica sets go a very long way, and sharding adds real operational complexity." Knowing when not to shard is the senior answer.
M18Does MongoDB support transactions?

Yes. Single-document operations have always been atomic. Multi-document ACID transactions arrived in 4.0 for replica sets and 4.2 for sharded clusters.

Most common use case — two collections that must move together
const session = client.startSession();
try {
  await session.withTransaction(async () => {
    // Conditional decrement: the filter itself prevents overselling,
    // so there's no read-then-write race.
    const r = await inventory.updateOne(
      { sku, available: { $gte: qty } },
      { $inc: { available: -qty } },
      { session }
    );
    if (r.modifiedCount === 0) throw new AppError('Out of stock', 409);

    await orders.insertOne({ sku, qty, status: 'reserved' }, { session });
  }, {
    readConcern:  { level: 'snapshot' },
    writeConcern: { w: 'majority' }
  });
} finally {
  await session.endSession();      // ALWAYS — leaked sessions pile up
}

// Caveats: 60-second default runtime limit; real performance cost;
// and if you need them frequently, the schema is probably wrong —
// the Mongo-idiomatic answer is to model so related data lives in
// one document, making single-document atomicity sufficient.
M19What happens to transactions across microservices?

They don't exist. A database transaction cannot span two services with separate databases. This is the single most important consequence of database-per-service, and the answer is the saga pattern (S11).

Connect the dotsBeing able to say "Mongo has transactions, but they stop at the service boundary — so across services I'd use a saga with compensating actions, and publish the events via a transactional outbox so the local write and the event are atomic" is a complete, senior-level answer that spans three sections of this guide.

Mongoose & the driver

M20What does Mongoose give you over the native driver, and what does it cost?

Gives: schema definition and validation, type casting, middleware hooks, virtuals, populate, plugins. Costs: hydration overhead on every result, an abstraction that hides the real query, occasional lag behind server features, and the illusion of a rigid schema — validation is application-side only, so anything writing directly to the database bypasses it.

Most common use case — belt and braces: app schema + DB schema
// Mongoose validates in the application…
const OrderSchema = new Schema({
  customerId: { type: Schema.Types.ObjectId, required: true, index: true },
  status: { type: String, enum: ['open','shipped'], default: 'open' },
  total:  { type: Schema.Types.Decimal128, required: true }
}, { timestamps: true });

// …but a migration script, an ETL job, or the mongo shell can
// write whatever it likes. So enforce invariants in the DATABASE too:
db.createCollection('orders', {
  validator: { $jsonSchema: {
    bsonType: 'object',
    required: ['customerId', 'status', 'total'],
    properties: {
      status: { enum: ['open', 'shipped'] },
      total:  { bsonType: 'decimal' }
    }
  }},
  validationLevel: 'strict', validationAction: 'error'
});
M21What does .lean() do and when should you use it?
Most common use case — every read-only endpoint
// WITHOUT lean(): each result is hydrated into a full Mongoose
// Document — getters, setters, virtuals, change tracking, save().
// On a 1,000-row list that's 1,000 objects you never use.
const orders = await Order.find({ status: 'open' });

// WITH lean(): plain JS objects. Substantially faster, far less
// memory. You lose document methods — which a GET handler that
// serialises straight to JSON does not need.
const orders = await Order.find({ status: 'open' })
                          .select('_id status total')   // project too
                          .lean();

// Rule: .lean() on every read-only query. Highest value,
// lowest effort Mongoose optimization there is.
M22What is populate and what's wrong with it?

It resolves references by issuing additional queries — a client-side join, not a database join. Mongoose batches with $in, so it's usually one extra query per populated path rather than one per document, but nested populates multiply.

Most common use case — and its hidden cost
// 1 query for orders + 1 for customers + 1 for products = 3.
// Acceptable. But nest one level deeper and it compounds.
const orders = await Order.find(q)
  .populate('customerId', 'name tier')      // ALWAYS project — otherwise
  .populate('items.productId', 'name sku')   // you pull whole documents
  .lean();

// The deeper problem: populate encourages relational modelling in
// a document database. If you populate the same field on every
// query, that field belongs INSIDE the document (extended
// reference, M02).
M23How do Mongoose middleware hooks work, and what's the trap?
Most common use case — hashing a password, and the hook that doesn't fire
// DOCUMENT middleware — fires on doc.save() and Model.create()
UserSchema.pre('save', async function () {
  if (!this.isModified('password')) return;   // avoid re-hashing
  this.password = await argon2.hash(this.password);
});

// ⚠ THE TRAP — this does NOT fire the hook above. It's a QUERY
// operation, not a document operation. The password is stored
// in plaintext and nothing warns you.
await User.findOneAndUpdate({ _id }, { password: 'newpass' });
await User.updateMany({}, { password: 'x' });

// You need SEPARATE query middleware:
UserSchema.pre(['findOneAndUpdate', 'updateOne'], async function () {
  const update = this.getUpdate();
  if (update.password) {
    this.setUpdate({ ...update, password: await argon2.hash(update.password) });
  }
});
TrapBusiness logic hidden in hooks that silently doesn't run on bulk operations is a classic source of production bugs — and a great thing to name in an interview.
M24How do you manage MongoDB connections in Node?
Most common use case — connect once, plus the Lambda gotcha
// STANDARD SERVICE — connect once at process start, reuse forever.
// The driver maintains the pool internally. NEVER connect per request.
const client = new MongoClient(process.env.MONGO_URL, {
  maxPoolSize: 20,              // default 100 is often too high —
                                // each connection costs server memory
  minPoolSize: 5,               // keep warm connections ready
  serverSelectionTimeoutMS: 5000,
  maxIdleTimeMS: 60000
});
await client.connect();
module.exports = client;

// AWS LAMBDA — completely different rules.
const client = new MongoClient(URL, { maxPoolSize: 1 });  // ← 1, not 20
let connected;

exports.handler = async (event, context) => {
  // Without this, Lambda waits for the pool's idle sockets before
  // returning — every invocation times out or runs long.
  context.callbackWaitsForEmptyEventLoop = false;

  // Client declared OUTSIDE the handler survives warm invocations.
  connected ??= client.connect();
  await connected;
  return handle(event, client.db());
};
// At 1,000 concurrent invocations you still get 1,000 connections —
// which is why a proxy (or a container instead of Lambda) is often
// the real answer for database-heavy work.

Section 05 · 22 questions

Microservices architecture

Expect a whiteboard round. The recurring theme in every answer: distributed systems trade simplicity for independence, and every benefit has a matching cost you should name out loud.

Fundamentals & boundaries

S01What are microservices, and what problem do they actually solve?

An architectural style where an application is a suite of small, independently deployable services, each owning its own data, communicating over a network, organized around business capabilities.

The problem they solve is organizational. A monolith forces every team onto one release train, one stack, and one scaling unit. Microservices let teams deploy independently. Everything else — polyglot stacks, independent scaling, fault isolation — is secondary.

Senior signalSay this out loud: "Microservices trade code complexity for operational complexity. You're choosing to solve distributed-systems problems — partial failure, eventual consistency, distributed tracing — in exchange for team autonomy. If you don't have the team-autonomy problem, you're paying that cost for nothing." Interviewers are often listening specifically for whether you'll claim microservices are always better.
S02When should you not use microservices?
  • Small team. Under roughly 15 engineers you'll spend more time on infrastructure than features.
  • Unclear domain. If you don't know where the boundaries are, you'll draw them wrong. Boundaries in a monolith are cheap to move; boundaries between services are not.
  • No operational maturity. Without CI/CD, centralized logging, tracing, and monitoring, microservices are undebuggable.
  • Strongly transactional domain. If nearly everything needs ACID across entities, splitting is fighting the domain.

The recommended path is a modular monolith first — enforced module boundaries inside one deployable — then extract along seams that have proven themselves.

Most common use case — enforcing boundaries before you split
// A modular monolith gets you 80% of the benefit at 20% of the cost.
// Enforce module boundaries in the linter so they're real:

// .eslintrc — no-restricted-imports
{
  "rules": { "no-restricted-imports": ["error", { "patterns": [
    { "group": ["**/modules/*/internal/**"],
      "message": "Import a module's public index.js, not its internals." }
  ]}]}
}

// src/modules/orders/index.js — the ONLY public surface
module.exports = { placeOrder, getOrder };   // no repo, no schema

// When a module has been stable behind that interface for months,
// extracting it into a service is mechanical rather than surgical.
S03How do you decide where the service boundaries go?

By business capability or DDD bounded context — never by technical layer. A "database service" and a "business logic service" is a distributed monolith.

Tests for a good boundary
  • High cohesion: things that change together live together. If one business change edits four services, the boundary is wrong.
  • Loose coupling: deployable without coordinating with others.
  • Data ownership: exactly one service is the source of truth per entity.
  • Team alignment (Conway's Law): one team can own it end to end.
  • Independent scaling: its load profile differs from its neighbours.
Most common use case — the same word meaning different things
// This is what a "bounded context" actually means in practice.
// "Order" is a different concept in each service — and that is fine.

// Orders service — the customer's intent
{ id, customerId, items: [{ sku, qty, price }], status: 'placed' }

// Inventory service — a reservation against stock
{ orderRef, reservations: [{ sku, qty, warehouseId }], expiresAt }

// Billing service — an amount owed
{ orderRef, subtotal, tax, total, paymentStatus }

// Shipping service — a physical parcel
{ orderRef, address, weight, carrier, trackingNumber }

// The WRONG instinct is one shared canonical "Order" object with
// every field. That object couples all four teams to every change.
S04What is a distributed monolith and how do you recognize one?

The worst of both worlds: the operational complexity of microservices with the coupling of a monolith. Symptoms:

  • Services must be deployed together, in a specific order.
  • Multiple services share a database or schema.
  • A single user action requires a synchronous chain of five service calls.
  • Changing one service's API immediately breaks three others.
  • You can't test a service without spinning up the whole system.
Root causeAlmost always boundaries drawn by technical layer rather than business capability, or a shared database that was never split. Having a crisp answer here demonstrates you've seen microservices go wrong, not just seen the diagrams.
S05Why database-per-service, and what does it cost?

Why: a shared database is the tightest possible coupling. If two services read the same tables, neither can change its schema independently, and you've lost the entire benefit of separate deployment.

Costs — and these are the follow-up questions: no cross-service joins (use API composition or a CQRS read model), no distributed transactions (use sagas), duplicated data you must keep coherent, eventual consistency by design, and reporting that now needs a warehouse.

Most common use case — the query you can no longer write
// MONOLITH — one query, ACID, done.
SELECT o.id, c.name, i.warehouse
FROM orders o
JOIN customers  c ON c.id = o.customer_id
JOIN inventory  i ON i.sku = o.sku
WHERE o.status = 'open';

// MICROSERVICES — that join is now three network calls.
// Option 1: API composition (simple; latency is the SUM)
const orders = await orderSvc.list({ status: 'open' });
const ids    = [...new Set(orders.map(o => o.customerId))];
const [customers, stock] = await Promise.all([
  customerSvc.getMany(ids),                       // batch — never N calls
  inventorySvc.getMany(orders.map(o => o.sku))
]);
return merge(orders, customers, stock);

// Option 2: a read model this service owns, kept current by events.
// One local query again — at the price of eventual consistency.

S07What is an API Gateway and what does it do?

A single entry point in front of your services handling routing, authentication and token validation, rate limiting, TLS termination, request/response transformation, response aggregation, caching, and metrics. Without it, every client needs every service's address and every service reimplements auth.

Most common use case — validate once at the edge, trust inward
// AT THE GATEWAY — the expensive work happens once.
const claims = await verifyJwtAgainstJwks(token);   // RS256 verify + JWKS
const internal = signInternalToken({              // short-lived, HS256
  sub: claims.sub, scope: claims.scope,
  exp: Math.floor(Date.now()/1000) + 30            // 30 SECONDS
});
forward(req, { headers: { 'x-internal-token': internal,
                          'x-correlation-id': req.id } });

// IN EACH SERVICE — cheap symmetric verify, no network call to the IdP.
// Note this is still verification, not blind trust: zero-trust means
// the network being internal is NOT a reason to skip the check.
const claims = jwt.verify(req.get('x-internal-token'), INTERNAL_SECRET,
                          { algorithms: ['HS256'] });
Risk to nameIt's a single point of failure (run it HA), it can become a bottleneck, and it can turn into a "god gateway" full of business logic — at which point you've rebuilt the monolith at the edge. Keep it to cross-cutting concerns.
S08What is Backend for Frontend (BFF)?

A gateway per client type rather than one shared gateway. A mobile BFF returns compact payloads tuned for cellular; a web BFF returns richer data; a partner BFF exposes a stable public contract.

Most common use case — one backend, three shapes
// MOBILE BFF — minimal payload, pre-joined, one round trip.
// Cellular latency means chattiness costs far more than bytes.
{ id:'o9', status:'shipped', total:'42.00', eta:'2026-08-02' }

// WEB BFF — richer, since the desktop renders more per screen.
{ id:'o9', status:'shipped', total:'42.00',
  customer:{…}, items:[…], timeline:[…], invoiceUrl:'…' }

// PARTNER BFF — a deliberately stable, versioned contract that
// hides your internal service boundaries entirely.
{ orderId:'o9', orderStatus:'SHIPPED', amount:{ value:'42.00', currency:'USD' } }

// Each BFF is owned by the team that owns that client, so the
// duplication is a feature: nobody blocks anybody.
S09How do services find each other?
  • Client-side discovery — client queries a registry (Consul, Eureka) and load-balances itself. Fewer hops; logic duplicated everywhere.
  • Server-side discovery — client calls a stable address which resolves and routes. Simpler clients, extra hop.
  • DNS-based — Kubernetes internal DNS. Simple, and what most teams actually use.
  • Service mesh — a sidecar proxy handles discovery, load balancing, retries, mTLS, and telemetry outside your application code.
Most common use case — Kubernetes DNS, which is usually the answer
// A Kubernetes Service gives you a stable DNS name that resolves
// to healthy pods. No registry client, no library, no code.
const INVENTORY = 'http://inventory.production.svc.cluster.local:8080';

// Configuration, never hardcoded — same image, every environment.
const inventoryUrl = process.env.INVENTORY_URL;

// The subtlety worth mentioning: kube-proxy load-balances per
// CONNECTION, not per request. With HTTP keep-alive, one client
// pod can pin to one server pod and skew the load — which is one
// of the real reasons teams adopt a service mesh.
S10How do you evolve service APIs without breaking consumers?

Tolerant reader — consumers ignore fields they don't understand rather than failing on unknown properties. Additive-only changes. Expand and contract for anything breaking.

Most common use case — a tolerant consumer
// FRAGILE consumer — .strict() rejects unknown keys, so the
// provider adding ANY new field breaks you in production.
const Order = z.object({ id: z.string(), total: z.number() }).strict();

// TOLERANT consumer — validate only what you actually use, and
// let everything else pass through untouched.
const Order = z.object({
  id:    z.string(),
  total: z.number()
}).passthrough();          // ← unknown fields are fine

// Note the asymmetry: be STRICT on what you accept as INPUT
// (security), TOLERANT on what you read from upstream (resilience).

Back it with consumer-driven contract testing (T05) so the provider's CI fails if it breaks any consumer. That's how you get confidence to deploy independently — which is the entire point of microservices.

S11Explain the saga pattern.
ChoreographyOrchestration

Most common use case — an orchestrated saga with durable state
// The saga's state lives in a database, so a crash resumes rather
// than losing the flow. This is what makes orchestration debuggable.
const STEPS = [
  { name:'reserveStock', run: s => inventory.reserve(s.orderId, s.items),
                            undo: s => inventory.release(s.orderId) },
  { name:'chargeCard',   run: s => payments.charge(s.orderId, s.total),
                            undo: s => payments.refund(s.orderId) },
  { name:'confirmOrder', run: s => orders.confirm(s.orderId),
                            undo: s => orders.reject(s.orderId) }
];

async function runSaga(state) {
  const done = [];
  try {
    for (const step of STEPS) {
      await sagas.updateOne({ _id: state.id },
        { $set: { current: step.name, status: 'running' } });
      await step.run(state);         // each step MUST be idempotent —
      done.push(step);                // retries are guaranteed
    }
    await sagas.updateOne({ _id: state.id }, { $set:{ status:'completed' }});
  } catch (err) {
    // Compensate in REVERSE order, and keep going even if one
    // compensation fails — log it for manual reconciliation.
    for (const step of done.reverse()) {
      try { await step.undo(state); }
      catch (e) { logger.error({ e, step: step.name }, 'COMPENSATION FAILED'); }
    }
    await sagas.updateOne({ _id: state.id },
      { $set: { status: 'compensated', error: err.message } });
  }
}
// Also needed: a timeout sweeper. A saga stuck in 'running' for an
// hour must be force-compensated, or it hangs forever.
S12Why not just use two-phase commit?

2PC gives real ACID across services, but: it's a blocking protocol — if the coordinator dies after prepare, participants hold locks indefinitely; every participant must support XA; holding locks across network calls destroys throughput; and availability drops because every participant must be up for any write.

Sagas trade atomicity for availability — a direct application of CAP. Making that link explicitly is a good bridge to Section 07.

S14What is CQRS, and when is it worth it?

Separate the write model from the read model. Writes go through a normalized model optimized for consistency; reads come from denormalized projections optimized for query shape, kept current by events.

Worth it when read and write loads differ by orders of magnitude, reads need data from several services, or query shapes differ wildly from the write shape. Not worth it for basic CRUD.

Most common use case — a read model built from events
// WRITE side — normalized, validated, owns the truth.
await orders.insertOne({ _id, customerId, items, status: 'placed' });

// READ side — a denormalized projection purpose-built for one screen.
// No joins at query time; everything the UI needs is already here.
consumer.on('OrderPlaced', async (e) => {
  await orderSummaryView.updateOne(
    { _id: e.orderId },
    { $set: {
        orderId:      e.orderId,
        customerName: e.customerName,   // from the Customer service
        itemCount:    e.items.length,
        total:        e.total,
        status:       'placed',
        updatedAt:    new Date()
    }},
    { upsert: true }                     // upsert = idempotent replay
  );
});

// The dashboard query is now a single indexed find():
orderSummaryView.find({ customerId }).sort({ updatedAt: -1 }).limit(20);
Nuance worth statingCQRS does not require event sourcing, and event sourcing does not require CQRS. They're taught together but are independent choices. Saying that is an instant credibility marker.
S15What is event sourcing?

Instead of storing current state, store the immutable sequence of events that produced it. Current state is derived by replaying; snapshots avoid replaying from the beginning.

Most common use case — state as a fold over events
// The event log IS the system of record.
[ { seq:1, type:'OrderPlaced',   data:{ items:[…], total:42 } },
  { seq:2, type:'ItemAdded',     data:{ sku:'X-9', price:8 } },
  { seq:3, type:'PaymentTaken',  data:{ amount:50 } },
  { seq:4, type:'OrderShipped',  data:{ carrier:'UPS' } } ]

// Current state is a reduction. Add a snapshot every N events so
// you don't replay 100,000 to answer one query.
const state = events.reduce(apply, snapshot ?? initialState);

// What you get for free: "what did this order look like on the 3rd?"
const asOf = events.filter(e => e.at <= date).reduce(apply, initialState);

Benefits: a complete audit trail by construction, time-travel queries, and the ability to build new read models retroactively by replaying history. Costs: high complexity, genuinely hard event-schema evolution, and immutability colliding with GDPR/HIPAA right-to-erasure.

S16How do you query data that lives in three different services?
  1. API composition — a gateway or BFF calls each and merges. Simple; latency is the sum; fails if any is down. Fine for a handful of calls.
  2. CQRS read model — one service subscribes to events from all three and maintains a purpose-built view. Fast reads, eventual consistency, extra infrastructure.
  3. Data warehouse — stream everything into an analytical store. Right for BI; wrong for operational queries.
The wrong answer they may bait you intoQuerying another service's database directly. That reintroduces exactly the shared-database coupling you split to avoid.

S19What is the bulkhead pattern?

Named after ship compartments: isolate resources so a failure in one area can't sink the vessel.

Most common use case — per-dependency connection pools
// WITHOUT bulkheads: one shared pool. The slow payments API holds

// Same idea at the deployment level: separate instance pools for

// cannot degrade order placement.
S20How do you do retries correctly?
  • Only idempotent operations. Retrying a non-idempotent POST double-charges someone.
  • Exponential backoff so you don't amplify load on a struggling service.
  • Jitter — without it, all clients retry simultaneously and create a thundering herd that re-kills the recovering service.
  • A budget — 3 attempts, not infinite.
  • Don't retry 4xx. A 400 will be 400 forever.
Retry amplificationIf every layer retries 3 times, a three-layer stack turns one request into 27. Retry at one layer — usually the outermost one that knows whether the operation is idempotent — and pass a budget header downstream so nobody else retries.

S22How do you deploy microservices safely?
  • Blue-green — two identical environments, switch at the load balancer. Instant rollback, doubles infrastructure briefly.
  • Canary — 1%, then 5%, then 50%, watching error rate and latency. Limits blast radius; needs good metrics.
  • Rolling — replace instances gradually. Kubernetes default. Both versions run at once, so the API must be backward compatible.
  • Feature flags — decouple deploy from release. Ship dark, enable for a cohort, kill instantly with no redeploy.
The thing that underpins all fourBackward-compatible database migrations. Add a column, deploy code that writes both, backfill, deploy code that reads new, drop the old — the expand/contract pattern (D11). A migration that breaks the running version makes every deployment strategy above useless.

Microservices design patterns

Problem, solution, and the cost of each. Nobody expects you to recite thirty patterns — what lands is recognising which pattern a question is really about, then naming its price.

Decomposition — how to split

decomposition

By business capability

Split along what the business does — Orders, Claims, Inventory. Stable, because business capabilities change slowly.

Cost: requires real domain understanding up front.

decomposition

By subdomain (DDD)

Split along bounded contexts, where the same term means different things. Aligns code with the ubiquitous language.

Cost: needs DDD investment and domain-expert access.

decomposition

Strangler fig

Incrementally route capabilities away from a monolith behind a facade until nothing is left.

Cost: long transition running both; data sync is the painful part.

decomposition

Self-contained service

A service that answers requests without synchronously calling others — it keeps local replicas of what it needs.

Cost: data duplication and eventual consistency.

Data management

data

Database per service

Each service privately owns its store. The foundational pattern — everything else here exists because of it.

Cost: no joins, no distributed transactions, duplicated data.

data

Shared database

Multiple services on one database. Sometimes a pragmatic transitional step.

Cost: Anti-pattern in steady state — kills independent deployment.

data

Saga

A sequence of local transactions with compensating actions on failure. The replacement for distributed transactions.

Cost: no isolation; intermediate states visible; compensation is real work.

data

Transactional outbox

Write the event to an outbox table in the same transaction as the state change; a relay publishes it.

Cost: at-least-once delivery, so consumers must be idempotent.

data

Log tailing / CDC

Read the database's replication log (Debezium, Mongo change streams) to publish events with no application change.

Cost: couples you to storage internals; another moving part.

data

CQRS

Separate the write model from denormalized read models kept current by events.

Cost: eventual consistency; two models to maintain.

data

Event sourcing

Persist the event sequence rather than current state. Audit trail by construction.

Cost: high complexity; event-schema evolution; conflicts with right-to-erasure.

data

API composition

A composer queries several services and joins in memory. The simplest cross-service query.

Cost: latency is the sum; fails if any service is down.

data

Domain event

Publish a business-meaningful fact ("OrderConfirmed") rather than a CRUD notification. Consumers decide what it means to them.

Cost: the event schema becomes a public contract you must version.

Communication

communication

API gateway

Single entry point handling routing, auth, rate limiting, aggregation, TLS.

Cost: single point of failure; can accrete business logic.

communication

Backend for Frontend

A gateway per client type, each tuned to that client's needs.

Cost: duplication across BFFs — usually acceptable, since each is team-owned.

communication

Remote procedure invocation

Synchronous request/response — REST or gRPC. Simple, immediate.

Cost: temporal coupling; availability multiplies down the chain.

communication

Messaging

Asynchronous via a broker. Decouples in time; buffers load spikes.

Cost: eventual consistency; the broker is now critical infrastructure.

communication

Idempotent consumer

Track processed message IDs so redelivery is harmless. Mandatory with at-least-once delivery.

Cost: a dedupe store you must size and expire.

communication

Anti-corruption layer

A translation layer isolating your domain model from a legacy or third-party model. Essential when integrating with an old system whose concepts you don't want leaking in.

Cost: extra mapping code to maintain.

Reliability

reliability

Circuit breaker

Fail fast when a dependency is unhealthy; probe periodically to recover. Prevents cascading failure.

Cost: threshold tuning; can trip on transient blips.

reliability

Bulkhead

Isolate resource pools per dependency so one failure can't exhaust everything.

Cost: lower total utilization.

reliability

Retry with backoff + jitter

Absorb transient failures without creating a thundering herd.

Cost: amplifies load if unbounded; unsafe on non-idempotent calls.

reliability

Timeout

reliability

Rate limiter / throttling

Protect a service from being overwhelmed — by abuse, or by a well-meaning batch job.

reliability

SQL, NoSQL & data fundamentals

Postgres and Oracle appear on most enterprise backend postings alongside Mongo. Any relational background transfers almost completely — the concepts are identical, only the dialect differs.

D01Explain ACID.
  • Atomicity — all operations succeed or none do.
  • Consistency — the transaction moves the database from one valid state to another, respecting all constraints.
  • Isolation — concurrent transactions don't observe each other's intermediate state, to the degree the isolation level promises.
  • Durability — once committed, it survives a crash, guaranteed by the write-ahead log.

The interesting follow-up is that Isolation is a dial, not a boolean — which leads straight to the next question.

D02What are the transaction isolation levels and what does each prevent?
LevelDirty readNon-repeatable readPhantom
Read uncommittedPossiblePossiblePossible
Read committedPreventedPossiblePossible
Repeatable readPreventedPreventedPossible*
SerializablePreventedPreventedPrevented
Most common use case — the anomaly each level actually prevents
-- DIRTY READ: reading another transaction's uncommitted data.
-- T1: UPDATE accounts SET balance = 0 WHERE id = 1;   (not committed)
-- T2: SELECT balance FROM accounts WHERE id = 1;      → 0
-- T1: ROLLBACK;   ← T2 acted on a value that never existed.

-- NON-REPEATABLE READ: same row, two different values.
-- T1: SELECT balance ... → 100
-- T2: UPDATE ... SET balance = 50; COMMIT;
-- T1: SELECT balance ... → 50   ← changed mid-transaction

-- PHANTOM READ: same range query, different row COUNT.
-- T1: SELECT count(*) WHERE status='open' → 5
-- T2: INSERT a new open row; COMMIT;
-- T1: SELECT count(*) WHERE status='open' → 6  ← a row appeared

*PostgreSQL's repeatable read uses snapshot isolation and prevents phantoms too. Postgres and Oracle default to read committed. SQL Server also defaults to read committed but with locking rather than MVCC unless you enable RCSI — a real difference to know if you're moving between them.

D03Explain the CAP theorem, and why PACELC is more useful.

The common misreading is "pick two of three." Partition tolerance isn't a choice — networks fail. The real decision is CP or AP during a partition.

D04Normalization vs denormalization — how do you decide?

Normalization eliminates redundancy so each fact lives in one place: updates are cheap and anomalies impossible, but reads need joins. Denormalization duplicates data so reads are single-fetch, at the price of updating every copy.

Decide by read/write ratio and consistency requirement. A ledger normalizes; a product catalog page denormalizes. In microservices you denormalize across service boundaries almost by necessity — the extended reference pattern is denormalization with a name.

D05What is the N+1 query problem and how do you fix it?
Most common use case — the same bug in three dialects
// N+1: 1 query for the list, then 1 per item. Fast in dev with 3
// rows, catastrophic in prod with 3,000.
const orders = await Order.find({ customerId });        // 1
for (const o of orders) {
  o.product = await Product.findById(o.sku);            // N
}

// FIX — batch into one query, then join in memory.
const skus     = [...new Set(orders.map(o => o.sku))];
const products = await Product.find({ _id: { $in: skus } }).lean();
const bySku    = new Map(products.map(p => [String(p._id), p]));
orders.forEach(o => { o.product = bySku.get(String(o.sku)); });

// Same problem, other names:
//   SQL/ORM  → eager loading (JOIN or a second IN query)
//   GraphQL  → DataLoader (batches per tick, caches per request)
//   REST     → a batch endpoint: GET /products?ids=a,b,c

Being able to name it across three contexts shows you understand the concept rather than one framework's trick.

D06How does a B-tree index work, and when does the database ignore yours?

A balanced tree of sorted keys pointing at rows: O(log n) lookup, and efficient range scans because leaves are linked in order.

Most common use case — six reasons your index isn't being used
-- 1. LOW SELECTIVITY — matches 40% of rows. A sequential scan is
--    genuinely cheaper than 40% random I/O. Not a bug.
SELECT * FROM orders WHERE status = 'active';

-- 2. FUNCTION ON THE COLUMN — the index stores name, not UPPER(name)
SELECT * FROM users WHERE UPPER(name) = 'ACME';           -- ✘
CREATE INDEX idx_users_name_upper ON users (UPPER(name)); -- ✔ expression index

-- 3. IMPLICIT TYPE CONVERSION — casts every row
SELECT * FROM orders WHERE order_no = 12345;   -- order_no is VARCHAR ✘
SELECT * FROM orders WHERE order_no = '12345'; -- ✔

-- 4. LEADING WILDCARD — a B-tree can't seek to an unknown prefix
SELECT * FROM users WHERE email LIKE '%@acme.com';  -- ✘ needs trigram/FTS

-- 5. STALE STATISTICS — the planner's row estimates are wrong
ANALYZE orders;

-- 6. COMPOUND PREFIX VIOLATED — index (a,b,c), query only on b
--    Same rule as Mongo's ESR prefix rule (M06).
D07What Postgres-specific features would you mention?

  • jsonb with GIN indexes — document storage inside a relational database, which is why "Postgres or Mongo" is a live debate.
  • Index types — B-tree, GIN (arrays, jsonb, full text), GiST (geometry, ranges), BRIN (huge append-only tables), Hash.
  • EXPLAIN (ANALYZE, BUFFERS) — the actual plan with real timings and I/O.

D08SQL vs NoSQL — how do you actually choose?

Reject the framing first: "NoSQL" covers four unrelated families — document (Mongo), key-value (Redis, DynamoDB), column-family (Cassandra), and graph (Neo4j). They solve different problems.

Then answer on access patterns: relational for many entities with genuine many-to-many relationships and ad-hoc queries; document for hierarchical data read as a unit; key-value for cache and session state; column-family for enormous write volume with known query patterns; graph when the relationships are the data.

Then say polyglot persistence — most real systems use several, one per service, which is what database-per-service enables.

D09How does connection pooling work and how does it fail?
Most common use case — the leak, and the fix
// LEAK — if the query throws, release() never runs and that
// connection is gone for the life of the process.
const conn = await pool.acquire();
const rows = await conn.query(sql);      // throws → leak
conn.release();

// FIXED
const conn = await pool.acquire();
try { return await conn.query(sql); }
finally { conn.release(); }            // always runs

// ALSO A LEAK — holding a connection across a network call.
// The pool is now hostage to a third party's latency.
await conn.query('BEGIN');
const rate = await fetch('https://fx-api...');   // ✘ 2 seconds
await conn.query('UPDATE …');

// Fetch FIRST, then open the transaction.
const rate = await fetch('https://fx-api...');
await conn.query('BEGIN'); /* … */

// And fail fast rather than hanging forever:
const pool = new Pool({ max: 20, connectionTimeoutMillis: 3000 });
D10What is a deadlock and how do you avoid one?
Most common use case — inconsistent lock ordering
// DEADLOCK: T1 locks A then wants B; T2 locks B then wants A.
// Neither can proceed. The DB detects the cycle and kills one.
// T1: UPDATE accounts SET … WHERE id = 1;  then id = 2;
// T2: UPDATE accounts SET … WHERE id = 2;  then id = 1;

// FIX — always acquire locks in a CONSISTENT order.
// Sorting the ids makes the cycle impossible.
const ordered = [...accountIds].sort();
for (const id of ordered) await conn.query('UPDATE … WHERE id=$1', [id]);

// And retry — a deadlock victim is safe to retry by definition.
async function withDeadlockRetry(fn, attempts = 3) {
  for (let i = 1; ; i++) {
    try { return await fn(); }
    catch (e) {
      if (e.code !== '40P01' || i >= attempts) throw e;  // PG deadlock
      await sleep(50 * 2 ** i + Math.random() * 50);
    }
  }
}

Also: keep transactions short, use the lowest workable isolation level, and index appropriately so the engine locks rows rather than ranges.

D11How do you handle database migrations in a CI/CD pipeline?

Migrations live in source control, are versioned and forward-only, and run as an explicit pipeline step (Flyway, Liquibase, migrate-mongo, Prisma Migrate) — never by hand.

D12What is a materialized view and when would you use one?

A precomputed, physically stored query result, refreshed on a schedule or on demand. Use it when an expensive aggregation is read far more often than the underlying data changes.

Most common use case — a dashboard rollup
-- Postgres
CREATE MATERIALIZED VIEW daily_revenue AS
SELECT date_trunc('day', placed_at) AS day,
       region, sum(total) AS revenue, count(*) AS orders
FROM orders WHERE status = 'fulfilled'
GROUP BY 1, 2;

CREATE UNIQUE INDEX ON daily_revenue (day, region);  -- required for…
REFRESH MATERIALIZED VIEW CONCURRENTLY daily_revenue; -- …no read lock

-- MongoDB equivalent: $merge writes the aggregation to a collection
db.orders.aggregate([
  { $match: { status: 'fulfilled' } },
  { $group: { _id: { day: '$day', region: '$region' },
              revenue: { $sum: '$total' } } },
  { $merge: { into: 'daily_revenue', whenMatched: 'replace' } }
]);
Connect the dotsA CQRS read model is a materialized view maintained by events instead of by a scheduled refresh. Same idea, different trigger — and that framing makes CQRS much less exotic.

A05What is the alg: none attack?
Most common use case — the attack, and the one-line defence
// ATTACK 1 — alg:none. Attacker edits the payload, sets the header
// algorithm to "none", strips the signature. A naive library that
// reads alg from the UNTRUSTED header accepts it.
{ "alg": "none" } . { "sub":"victim", "role":"admin" } . <empty>

// Attacker signs with HS256 using the server's PUBLIC key as the
// HMAC secret. If the server infers the algorithm from the header,
// it verifies successfully — the public key is, after all, public.

jwt.verify(token, publicKey, { algorithms: ['RS256'] });   // ✔
jwt.verify(token, publicKey);                                // ✘ never

A08How do refresh token rotation and reuse detection work?
Most common use case — detecting a stolen refresh token
async function refresh(presented) {
  const row = await tokens.findOne({ token: hash(presented) });
  if (!row) throw new AppError('Invalid', 401, 'BAD_REFRESH');

  if (row.usedAt) {
    // This token was ALREADY used. Rotation means it should never
    // be presented twice — so either the attacker is replaying a
    // stolen token, or the legitimate user is replaying after the
    // attacker used it. Either way: burn the whole family.
    await tokens.updateMany({ familyId: row.familyId },
                            { $set: { revoked: true } });
    logger.warn({ familyId: row.familyId }, 'refresh token REUSE detected');
    throw new AppError('Session revoked', 401, 'REUSE_DETECTED');
  }

  // Normal path: mark used, issue a NEW refresh token in the same
  // family. Absolute expiry caps the family's total lifetime.
  await tokens.updateOne({ _id: row._id }, { $set:{ usedAt: new Date() }});
  const next = crypto.randomBytes(32).toString('base64url');
  await tokens.insertOne({
    token: hash(next), familyId: row.familyId, userId: row.userId,
    absoluteExpiry: row.absoluteExpiry
  });
  return { accessToken: signAccess(row.userId), refreshToken: next };
}

This turns a stolen refresh token from unlimited access into a detectable event with a short window.

  • Role — an identity with no permanent credentials that is assumed, producing temporary credentials via STS. This is how EC2, Lambda, and ECS tasks get permissions.
  • Policy — JSON with Effect / Action / Resource / Condition. Identity policies attach to principals; resource policies attach to resources and can grant cross-account access.
  • Permission boundary — a ceiling on what an identity policy can grant, so you can delegate IAM administration safely.

C01Image vs container vs layer.

An image is an immutable, layered filesystem template plus metadata. A container is a running instance with a thin writable layer on top. Each Dockerfile instruction produces a layer, and layers are cached and shared between images — which is why instruction order matters so much for build speed.

Containers are isolated by kernel features — namespaces for what a process can see, cgroups for what it can consume — not by virtualization. That's why they start in milliseconds and share the host kernel.

Understanding the three delivery models — queue, topic, log — covers most of what gets asked about SNS, SQS and Kafka.

Q02What does at-least-once delivery mean and why does it force idempotency?

Most brokers guarantee a message arrives at least once, not exactly once. A consumer can process successfully and crash before acknowledging — the broker cannot distinguish that from a consumer that died before processing, so it redelivers.

Most common use case — an idempotent consumer
// processed collection: unique index on { messageId: 1 }
//                       TTL index on { at: 1 } expireAfterSeconds: 604800
async function handle(msg) {
  const session = client.startSession();
  try {
    await session.withTransaction(async () => {
      // The unique index is what makes this safe. A duplicate
      // message hits a duplicate-key error and we skip the work.
      await processed.insertOne(
        { messageId: msg.id, at: new Date() }, { session });

      // Business effect in the SAME transaction as the dedupe record.
      await inventory.updateOne({ sku: msg.sku },
        { $inc: { reserved: msg.qty } }, { session });
    });
  } catch (e) {
    if (e.code === 11000) {                 // duplicate key
      logger.debug({ id: msg.id }, 'already processed — skipping');
      return;                               // ack it, do nothing
    }
    throw e;
  } finally { await session.endSession(); }
}

// Alternative when the operation is NATURALLY idempotent, which is
// always simpler: set a value rather than incrementing one.
await orders.updateOne({ _id }, { $set: { status: 'SHIPPED' } });
The exactly-once mythTrue end-to-end exactly-once delivery is impossible across a network. Kafka's "exactly-once semantics" is exactly-once processing within Kafka via idempotent producers and transactional writes — it does not extend to your external database.
Q03What is a dead-letter queue?

A separate queue where messages go after N failed attempts, so one malformed "poison message" can't block the queue forever while being retried infinitely.

The operational point most candidates missA DLQ is only useful if someone monitors it. Alarm on depth greater than zero, have a documented triage process, and build a replay mechanism so fixed messages can be reprocessed. An unwatched DLQ is a data-loss mechanism with extra steps.
Q04How do you guarantee message ordering?

Only within a partition or message group, never globally.

Most common use case — choosing the partition key
// Kafka: messages with the same KEY hash to the same partition and
// are strictly ordered within it. Choose the key to match your
// actual ordering requirement.
await producer.send({
  topic: 'order-events',
  messages: [{
    key: order.customerId,      // ✔ all events for ONE customer are
                                //   ordered relative to each other
    value: JSON.stringify(event)
  }]
});
// key: randomUUID()  ✘ — perfectly balanced, zero ordering
// key: 'constant'    ✘ — perfectly ordered, zero parallelism

// SQS FIFO equivalent:
await sqs.sendMessage({
  MessageGroupId: order.customerId,      // ordering scope
  MessageDeduplicationId: event.id       // 5-minute dedupe window
});

// Often the better answer is to make order NOT matter: include a
// version or timestamp and discard out-of-order updates.
await view.updateOne(
  { _id, version: { $lt: event.version } },   // only if newer
  { $set: { ...event.data, version: event.version } }
);

The design consequence: ordering requirements limit parallelism, because you can only process one message per key at a time.

Q05What is consumer lag and why do you alarm on it?

The gap between the newest offset in a partition and the offset a consumer group has processed. Growing lag means consumers can't keep up — the system still works, but data gets staler by the second, which is a business problem before it's a technical one.

Responses: scale consumers up to the partition count (you can't exceed it — that's the parallelism ceiling), increase partitions, batch processing, or fix the slow downstream call. The SQS equivalent is queue depth and age-of-oldest-message.

Q06Explain the dual-write problem.

You need to write to your database and publish an event. They're separate systems with no shared transaction, so no ordering is safe: write-then-publish loses the event if the publish fails; publish-then-write announces something that didn't happen.

The answer is the transactional outbox (S13), or change data capture — Debezium tailing the database log, or a MongoDB change stream (M14) — so the event is derived from the committed write rather than published alongside it.

Q07Event notification vs event-carried state transfer vs event sourcing.

//      call back at once

Q08How do you version event schemas?

The event schema is a public contract with consumers you may not control, so the same rules as API versioning apply — additive only, tolerant readers, and a version field in the envelope. A schema registry (Confluent with Avro or Protobuf) enforces compatibility at publish time, rejecting a producer change that would break existing consumers. That enforcement is the whole value.

Q09Is Kafka the same as Apache Kafka, and is it portable?

Yes — "Kafka" always means Apache Kafka, built at LinkedIn and donated to the Apache Software Foundation. It's open source and runs anywhere: self-hosted, AWS MSK, Confluent Cloud, Azure Event Hubs' Kafka endpoint, or protocol-compatible rewrites like Redpanda. Skills transfer because the wire protocol is the standard.

The broker is JVM-based, and since Kafka 4.0 it no longer requires a separate ZooKeeper cluster — KRaft mode replaced it. The stream-processing ecosystem (Kafka Streams, Connect) is JVM-centric, so from Node you get producers and consumers, which covers most application work.

Q10When would you choose messaging over a synchronous call?

When the caller doesn't need the result to continue: notifications, analytics, search indexing, audit logging, document generation, third-party sync. When the work is slow or unbounded. When multiple consumers care about the same fact. When you need to absorb a load spike rather than propagate it.

Stay synchronous when the user is waiting for the answer and it must be correct now — an inventory check before confirming an order.

  • Deterministic. No real clocks, no randomness, no network, no shared state.
  • Fast. A slow suite doesn't get run.
  • Readable as documentation. The name states the expected behaviour.
T03When do you mock, and when is mocking harmful?

Mock at architectural boundaries you don't own — third-party APIs, payment providers, email. Don't mock what you own, and especially don't mock the database: most bugs live in query behaviour, and a mocked repository tests only that your mock returns what you told it to.

Over-mockingTests that assert on interactions ("was save called with these arguments?") break on every refactor and pass while the system is broken. Prefer real implementations in containers where feasible.

T08How do you handle flaky tests?

Treat them as bugs, not noise. A flaky test is usually a real race condition, a shared-state leak between tests, or a timing assumption — and often the same race exists in production code. Quarantine it out of the blocking pipeline so it stops training people to ignore red builds, but track it and fix it. The worst outcome is a team that reflexively re-runs CI, because then a genuine failure gets re-run too.

T09What's your view on TDD?

A defensible, non-dogmatic answer: TDD is excellent where the specification is clear and the logic is intricate — pricing rules, dosage calculations, state machines — because writing the test first forces you to define the contract and produces a testable design. It's weaker for exploratory work where you don't yet know the shape of the solution.

Interviewers are usually checking whether you're an ideologue in either direction. "I use it where it pays and don't pretend it's universal" reads as experienced.

T10What do you look for in a code review?

In priority order: correctness against the requirement; security (authorization checks, input validation, injection, secrets, sensitive data in logs); error handling and edge cases; test coverage of the actual behaviour; performance at production data volumes (N+1, missing index, unbounded query); readability and naming; and only last, style — which should be automated anyway.

The senior-reviewer signalAsking "what happens if this is called twice?" and "what does this do when the downstream service is down?"

Section 13 · 11 questions

Production debugging & RCA

These questions are about structure. They want to see how you think, not whether you know a specific bug.

P01Walk me through how you handle a production incident.

See Fig 13.1. The order is the answer. Assess impact first — in a domain with safety implications, "is anyone harmed?" comes before everything. Stabilize before diagnosing. Communicate on a cadence so people stop asking. Diagnose metrics → traces → logs: metrics tell you where, traces tell you which hop, logs tell you why. Then verify the fix with the same metric that showed the problem, and hold a blameless postmortem.

P02What is root cause analysis and how do you do it properly?
Most common use case — Five Whys, worked
SYMPTOM: the API returned 500s for 12 minutes.

  Why? → The database connection pool was exhausted.
  Why? → Requests were holding connections for 30+ seconds.
  Why? → One query had no index and was scanning the whole collection.
  Why? → The index existed in staging but was never applied to prod.
  Why? → Index creation was a manual step, not part of the migration
         pipeline.

ROOT CAUSE: schema changes are not fully automated.
FIX:        indexes defined in versioned migrations, enforced in CI.
NOT A FIX:  "add the missing index" — that fixes this instance and
            guarantees the next one.
The disciplineIf your root cause is "a developer made a mistake," you haven't finished. People will always make mistakes; the question is why the system let the mistake reach production. Also worth naming: fishbone/Ishikawa for multi-factor incidents, and the principle that most real incidents have several contributing causes rather than one.
P03The API is slow but the database looks fine. What now?
Most common use case — the elimination checklist, in order
// 1. EVENT LOOP LAG — is something CPU-bound blocking?
//    metric: nodejs_eventloop_lag_p99  → if high, take a CPU profile

// 2. CONNECTION POOL WAIT — the classic answer to this question.
//    Queries are fast; requests are queuing to GET a connection.
//    Tell: latency rises with CONCURRENCY while the DB is idle.
setInterval(() => logger.info({
  poolTotal:   pool.totalCount,
  poolIdle:    pool.idleCount,
  poolWaiting: pool.waitingCount     // ← if > 0, this is your answer
}), 10000);

// 3. DOWNSTREAM CALLS — is a third party slow and your timeout
//    too generous? Check span durations per dependency.

// 4. SERIALIZATION — are you stringifying enormous payloads?

// 5. GC PRESSURE — heap near the limit means constant major GCs.
//    metric: nodejs_gc_duration_seconds

// 6. NO KEEP-ALIVE — a fresh TCP + TLS handshake per outbound call.

// 7. NOISY NEIGHBOUR — CPU credits exhausted, or a container
//    hitting its cgroup CPU quota (throttled, not busy).
P04Memory usage climbs until the container is OOM-killed. Diagnose it.

First distinguish a leak from legitimate growth: does RSS return to baseline after GC, or trend upward monotonically? Then take two heap snapshots under load, diff them, and look at which constructors grew and what retains them (N11 has the two leaks you'll actually find).

Most common use case — the container-specific gotcha
# Node does not automatically know about the cgroup memory limit.
# With a 512Mi container limit, V8 may happily grow the old space
# past it and get OOM-killed by the kernel with no JS error at all.
#
# Set the heap ceiling BELOW the container limit, leaving room for
# native allocations, buffers, and the runtime itself:
NODE_OPTIONS="--max-old-space-size=384"    # for a 512Mi limit

# The tell that it's this and not a leak: the process dies with
# exit code 137 (SIGKILL) and no stack trace.
P05How do you debug an issue you can't reproduce locally?

Narrow it with data. Which users, tenants, times, inputs, instances? Correlate with recent deploys and config changes — most "mysterious" bugs started at a specific deploy. Compare a failing correlation ID's full trace against a succeeding one. Add targeted logging scoped to affected users. Check whether production has data shapes staging doesn't — nulls, unicode, very large records, timezone edges.

The meta-point: an unreproducible bug usually means an environment or data difference you haven't identified yet, not magic.

P06What are the four golden signals and RED metrics?

Golden signals (Google SRE): latency, traffic, errors, saturation. RED (per service): Rate, Errors, Duration. USE (per resource): Utilization, Saturation, Errors.

The discipline that mattersUse percentiles, not averages. An average of 200ms can hide 5% of users at 8 seconds — and those are the users who churn. And alarm on symptoms users experience, not on causes like CPU.
P07How do you write a good postmortem?

Blameless, factual, actionable. Structure: summary, impact in user and business terms with duration, detailed timeline with timestamps, contributing factors, what went well, what went poorly, where we got lucky, and action items with named owners and due dates.

Blameless isn't kindness — it's that blame produces hiding, and hiding produces repeat incidents. Saying that explicitly is a mature-organization signal.

P08Tell me about a hard bug you found and how.

Structure any war story as: symptom → hypothesis → how you tested it → what you found → the fix → how you verified → what you changed so it can't recur. That last clause is what elevates it from "I fixed a bug" to "I improved the system."

What makes a story landNaming a hypothesis you eliminated. "I suspected pool contention, but the calls were sequential so I ruled it out and looked at X instead" is far more convincing than a straight line to the answer, because that's what real debugging looks like. See Section 18 for how to build your own story bank.
P09How do you handle a production data corruption issue?
  1. Stop the bleeding — disable the writing code path immediately, even if that means degraded service.
  2. Assess scope — write a query that identifies affected records exactly: how many, over what window, which fields.
  3. Preserve evidence — snapshot before you remediate, so you can re-derive if your first fix is wrong.
  4. Determine recoverability — can correct values come from audit logs, event history, backups, or an upstream source?
  5. Remediate in batches, verifying between batches, with the ability to stop.
  6. Notify — in regulated domains, corrupted records may be a reportable event with a legal clock, so compliance is involved early.
P10What's your approach when a bug report is vague?

Reproduce first, with the reporter if necessary — "it's broken" needs to become "clicking X as role Y at time Z produces W instead of V." Get the correlation ID, timestamp, and account. Then work backwards from the observable symptom rather than forward from a guess.

Worth namingConfirm the expected behaviour with whoever owns the requirement. A surprising number of "bugs" are two parts of a system implementing two different definitions of the same concept — and the fix is agreeing on the definition, not patching one side.
P11How do you support a team when you're the one they escalate to?

This maps directly to the "resolving issues faced by team" line that appears on senior postings. Good answer: teach the diagnostic path rather than just handing over the fix, so the same question doesn't come back; write the answer somewhere findable; and when a class of question recurs, fix the underlying cause — better error messages, a runbook, tooling, or a code change that makes the mistake impossible.

The strongest versionAn example where you noticed a recurring cost to the team and automated it away — a script, a lint rule, a generator, a CI check. That answers this question and the AI-automation question in Section 14 simultaneously.
Section 14 · 13 questions

AI-assisted development, Spec-Kit & agents

When a backend posting asks for spec-driven development, MCP, or agent tooling, most applicants have nothing to say. Prepare this hardest relative to how optional it looks.

G01What is Spec-Driven Development?

A workflow where the specification — what you're building and why — is a versioned artifact in the repository that an AI agent reads and derives implementation from, rather than a document written once and abandoned. The spec is the source; the code is the output. When requirements change, you change the spec and regenerate rather than re-prompting from scratch.

The distinction from a traditional PRD: a PRD is read by humans and then goes stale. A spec is re-read by the agent on every run, so drift is visible and correctable.

G02What is GitHub Spec Kit, specifically?

GitHub's open-source (MIT) toolkit implementing SDD. It's not a model and has no inference of its own — it's markdown prompt templates plus scripts that install into your repo and shape how your existing agent works.

Most common use case — what it puts in your repo
# Install into an existing repo (requires Python 3.11 + uv for the CLI)
specify init --here --integration copilot

# What lands:
.specify/
  memory/constitution.md        # engineering non-negotiables, once per repo
  templates/                    # the prompt templates themselves
.github/prompts/                # slash commands appear in Copilot Chat

# What each command produces:
/speckit.constitution  → .specify/memory/constitution.md
/speckit.specify       → specs/001-feature/spec.md      # what & why, NO stack
/speckit.clarify       → updates spec.md                # resolves ambiguity
/speckit.plan          → plan.md, data-model.md, contracts/
/speckit.tasks         → tasks.md                       # ordered, reviewable
/speckit.analyze       → consistency report             # every requirement covered?
/speckit.implement     → actual source code
/speckit.taskstoissues → pushes tasks into GitHub Issues
G03What problems does SDD actually solve?
  • Intent evaporates. You explain the edge cases in chat, the chat closes, and next month nobody can reconstruct why the code branches the way it does. With SDD the reasoning is in a reviewed file.
  • Every session starts from zero. Two developers prompting the same agent about the same service get two different architectures. The constitution and spec are re-read every run, so output is consistent across people and sessions.
  • Constraints arrive last. Auth, audit logging, accessibility bolted on after the code exists. The constitution puts non-negotiables up front and the plan is checked against them.
  • Review has no baseline. Reviewers can check a large AI diff compiles; they can't check it's what was asked for, because nobody wrote down what was asked for.
G04Is SDD a replacement for Agile, or for TDD?

Neither. It fits underneath your process. Generated tasks can be pushed into your existing issue tracker, so your board stays where it is. Tests still verify behaviour; the spec describes intent — several presets even enforce test-first ordering in the generated task list.

Rehearse the pushbackThe common objection is "this is waterfall." It isn't — nothing is frozen. You edit the spec and regenerate, which is a tight loop rather than a phase gate. Being able to defuse that cleanly is worth practising, because it's the first thing a skeptical interviewer raises.
G05How does Spec Kit work in an existing codebase rather than greenfield?

This is the question that separates people who've read about it from people who've tried it. Installing alongside existing code doesn't overwrite anything, but the templates know nothing about your architecture.

Most common use case — the brownfield recipe
# 1. GROUND THE AGENT FIRST. Before any spec, have it read the
#    codebase and write docs/codebase-research.md — architecture,
#    key modules, data flows, existing conventions.
#    Then REVIEW AND CORRECT IT YOURSELF. This is the step people skip.

# 2. Build the constitution from what is ALREADY TRUE, not from an
#    ideal. If the repo uses callbacks everywhere, say so.
#    Keep it tight — a bloated constitution burns context every run.

# 3. Spec only the CHANGE. Never reverse-engineer specs for code
#    nobody is touching.

# 4. Reference the research doc from every spec so the agent has
#    grounding rather than inventing an architecture.

# 5. Keep tooling upgrades separate from spec changes.
Name the honest weak spotMulti-repo features. A change spanning a web app, a service, and a shared package has no clean home when specs live per-repo. That's genuinely unsolved, and saying so builds credibility rather than costing it.
G06When is SDD not worth the ceremony?

Small, well-understood changes. Adding a field, renaming a prop, fixing a null check — seven commands to move a button is the most common and most justified criticism.

The split isn't ticket size, though; it's how much ambiguity there is about what correct looks like. A bug where nobody agrees what the correct behaviour is is spec-shaped even though it's small. And there's a lean path: for a medium change, specify → plan → implement, skipping clarify, tasks, and analyze.

G07What's the cost model of SDD?

The license is free; the tokens are not. Spec Kit is context-heavy — spec, plan, and tasks are re-read on each run — and the implement step is where requests concentrate.

The honest framing: it costs more turns per feature than one-shot prompting, but replaces the invisible "generate, discover it's wrong, regenerate" cycle that never appears in anyone's estimate. Whether it pays off depends on the size and ambiguity of the work — which is measurable, and saying you'd measure it on a pilot before rolling it out is the right answer.

G08How does Spec Kit compare to other SDD tools?
  • OpenSpec — lighter. Treats existing code as an immutable baseline and writes minimal delta specs. Cheaper and faster for routine brownfield work; weaker for greenfield architecture.
  • BMAD-METHOD — heavier. A simulated team of PM, architect, scrum master, and developer agents. More thorough, dramatically more expensive in tokens and wall-clock time.
  • IDE-native spec workflows — spec-driven flow built into a proprietary editor rather than into your repo. More integrated, less portable.

Because they all produce plain markdown, moving between them is mostly reformatting — you're not locking a codebase into a platform. That portability point is worth raising.

G09What is MCP and why does it matter?

The Model Context Protocol is an open standard for connecting AI models to external tools and data. Before it, every integration was bespoke. MCP defines a common protocol: an MCP server exposes tools, resources, and prompts; any MCP-compatible client can consume them.

Most common use case — a small read-only MCP server in Node
const { McpServer } = require('@modelcontextprotocol/sdk/server/mcp.js');
const { z } = require('zod');

const server = new McpServer({ name: 'orders-tools', version: '1.0.0' });

server.tool(
  'get_order_status',
  { orderId: z.string().uuid() },        // schema = the tool's contract
  async ({ orderId }) => {
    // Same engineering discipline as any API:
    //  · least-privilege credentials — this connection is READ-ONLY
    //  · validate inputs (zod above)
    //  · audit every call
    //  · never return sensitive fields to a model
    const o = await readOnlyDb.orders.findOne(
      { _id: orderId },
      { projection: { status: 1, updatedAt: 1, _id: 0 } }
    );
    await audit.write({ tool: 'get_order_status', orderId });
    return { content: [{ type: 'text', text: JSON.stringify(o) }] };
  }
);

// Rule of thumb: read-only by default. Any tool that WRITES should
// be gated behind explicit human confirmation.

The practical significance: instead of an engineer manually querying a database, checking a ticket, and reading a runbook, you expose those as tools and the agent orchestrates them.

G10Completion vs chat vs agent — what's the actual difference?
  • Completion — predicts the next tokens inline as you type.
  • Chat — answers a question with context you provide.
  • Agent — plans, acts, observes the result, and iterates toward a goal: editing multiple files, running commands, reading test output, and trying again.

The last one is qualitatively different because it takes actions with consequences, which is why review discipline and permission scoping matter in a way they don't for autocomplete. Tools in this space differ mainly in how much autonomy they take and how deeply they integrate with your repo and CI.

G11How do you use AI agents responsibly in a regulated environment?

This is the answer that separates a thoughtful adopter from an enthusiast, and in a regulated domain it will be asked:

  • No sensitive data in prompts unless the tool is covered by the appropriate agreement and configured for it. Use synthetic or de-identified data in examples and tests.
  • Mandatory human review. Generated code is a proposal, not a commit. The risk isn't code that fails to compile — it's confident, well-formatted code with a subtle logic error that a reviewer skims past because it looks considered.
  • Scoped permissions. An agent with production credentials is an incident waiting to happen. Read-only by default; writes behind explicit approval.
  • Auditability. Because specs and plans are committed files, you get a reviewable record of intent — genuinely useful for change control.
  • Licensing and provenance of generated code, and an SBOM.
G12Give an example of automating a recurring process with AI.

What makes this answer land is the engineering around the AI, not the AI itself. Structure it as: the recurring cost, the automation, the hard problems you had to solve, and how you measured whether it worked.

Most common use case — the shape of a good answer
// 1. THE RECURRING COST — quantify it.
//    "Every PR needed hand-written tests for changed modules;
//     roughly 40% of review comments were about missing coverage."

// 2. THE AUTOMATION — what you actually built.
//    "An editor extension / CI step that generates and updates
//     tests for changed files."

// 3. THE HARD PARTS — this is the credibility.
//    · a RETRY LOOP: generate → run the tests → feed failures back
//      → regenerate, capped at N attempts
//    · path translation between where files are written and where
//      the container actually runs them
//    · distribution so teammates could install it in one command

// 4. THE MEASUREMENT — what separates engineering from enthusiasm.
//    "I evaluated two models against the same 50 modules and
//     compared pass rate on first generation."

Point 4 is the detail that will impress most. Anyone can say they used an AI tool; very few say they measured it.

G13How would you introduce Spec Kit to a team that hasn't used it?

A concrete, measured pilot rather than a mandate:

  1. Pick one real, medium-sized upcoming feature in an existing repo — ambiguous enough to be interesting, small enough to ship.
  2. Ground it: install, generate the codebase research doc, correct it.
  3. Write the constitution from what the repo already does.
  4. Run the loop with real review at each gate.
  5. Measure three things: agent requests consumed, hours of cleanup after generation, and how many review comments were about intent rather than syntax. The third number is the one that tells you whether it's working.
  6. Report honestly, including where it wasn't worth it.

Presenting a rollout as an experiment with success criteria is a leadership signal, and it maps directly to the independence expectation on senior postings.

Section 15 · 11 questions

Agile, collaboration & behavioral

Behavioral answers use STAR: Situation, Task, Action, Result. The "works independently" line on a senior posting is not filler — it will be probed.

B01Explain Scrum: roles, ceremonies, artifacts.

Roles: Product Owner (owns backlog and priority), Scrum Master (facilitates, removes impediments), Development Team (self-organizing, cross-functional).

Ceremonies: Sprint Planning (what and how), Daily Standup (sync and surface blockers — not a status report to a manager), Sprint Review (demo, gather feedback), Retrospective (improve the process).

Artifacts: Product Backlog, Sprint Backlog, Increment — plus the Definition of Done, which is where quality standards actually live.

Worth adding the contrast: Kanban has no sprints, uses continuous flow with WIP limits, and often suits support or platform teams better.

B02How do you estimate work?

Story points as relative complexity — not hours — because humans are better at comparison than absolute prediction, and points absorb uncertainty. Planning poker to surface disagreement, since two people giving wildly different estimates usually means they understood the story differently, and that conversation is the real value. Velocity as a planning input for the team, never as a performance metric across teams.

And: if a story can't be estimated, it needs a timeboxed spike first.

B03How do you translate a business requirement into a technical design?

Most postings phrase this as "translate business requirements into well-designed, secure, scalable backend APIs." Structure:

  1. Understand the actual need, not the requested solution. "We need a report" often means "we need to answer a question."
  2. Clarify the non-functionals — volume, latency tolerance, consistency requirement, retention, who may see what. These drive architecture more than the features do.
  3. Model the domain — entities, relationships, lifecycle, invariants.
  4. Design the contract first and validate it against the consuming team.
  5. Choose storage from access patterns.
  6. Identify failure modes — what happens when each dependency is down.
  7. Write it down and get it reviewed before writing code. This is exactly what SDD formalizes (Section 14).
B04"Tell me about a time you worked independently to resolve something for the team."

What they're testing: do you own problems end to end, or escalate and wait?

Most common use case — the STAR skeleton to fill in
SITUATION  A specific symptom with a number attached.
           "A core page took ~40 seconds to load."
           "Two systems disagreed about the same value by 57 units."

TASK       What you owned, and what made it hard.
           "No obvious cause; the team had assumed it was the database."

ACTION     The investigation, INCLUDING what you ruled out.
           "I profiled rather than guessed. The query ran in 1.6s
            standalone but the API call took 31s, so I checked whether
            the calls were parallel — they were sequential, which ruled
            out pool contention. That pointed me at ___ instead."

RESULT     A number, plus what changed structurally.
           "Down to 15 seconds, and I added a plan-check to CI so the
            missing index can't recur."
The detail that makes it landNaming a hypothesis you eliminated. Interviewers hear "I fixed a bug" constantly; they rarely hear a clean root-cause narrative with a rejected hypothesis in it.
B05"Tell me about a time you disagreed with a technical decision."

Structure: what the decision was, why you disagreed, how you raised it (with data, not opinion), what happened, and — critically — how you behaved after. The best version ends with either "I was persuaded and here's what changed my mind" or "we went the other way, I committed fully, and here's what I learned when it turned out fine."

They're screening for whether you can disagree without being obstructive. Avoid stories where you were right and everyone else was foolish.

B06"Tell me about a time you made a mistake in production."

Have one ready, and make it real — a candidate who has never broken production has either never shipped or won't admit it. Structure: what happened, how you detected it, how quickly you mitigated, what the impact was, and what you changed so the class of mistake can't recur.

The last part carries all the weight. "I was more careful afterwards" is weak; "we added a check in CI so that specific mistake is now impossible" is strong.

B07How do you work with QA, DevOps, Product, and Architects?
  • QA — involve them at design time, not at handoff. Share the API contract early so tests are written in parallel; agree what "done" means before starting.
  • DevOps — treat deployability, observability, and alerting as part of the feature rather than someone else's problem afterwards.
  • Product — surface technical constraints as options with tradeoffs ("two weeks with this limitation, or five weeks without") rather than as blockers.
  • Architects — bring a proposal, not a question. Come with two options and a recommendation.
B08How do you handle technical debt?

Make it visible and quantified. Log it as tickets with the actual cost attached — "this adds two days to every change in this module," "this is why we can't upgrade the framework." Then negotiate a steady allocation rather than asking for a big-bang refactor sprint, which product will never approve. Attach cleanup to features that touch the same code.

The judgment pointNot all debt should be paid. Debt in code that rarely changes and works fine is often correctly left alone. Saying that shows you're prioritising rather than tidying.
B09How do you onboard onto an unfamiliar codebase?

Run it locally first — nothing teaches you the shape of a system like getting it to start. Trace one complete request from entry point to database and back. Read the tests, which document intent better than comments. Look at git history for the files that change most, because that's where the system's real activity is. Then take a small, real ticket end to end, asking questions with a specific proposal attached rather than open-ended ones.

Healthcare & pharmacy domain

Usually listed as "preferred," which means nobody expects you to have it — but a two-hour vocabulary pass buys a disproportionate amount of credibility. This is about holding the conversation, not claiming experience.

H01What is PHI and what makes it different from ordinary data?

Protected Health Information: any individually identifiable health information held or transmitted by a covered entity. That includes the obvious (diagnoses, medications, lab results) and the less obvious 18 identifiers — name, address, dates more specific than year, phone, email, SSN, medical record number, device identifiers, IP addresses, biometrics, photographs.

Most common use case — what changes in your code
// ✘ PHI in the URL — lands in access logs, browser history,
//   referrer headers, and CDN logs.
GET /api/patients?name=Jane+Doe&dob=1980-03-14

// ✔ Identifiers in the path, criteria in a POST body if needed
GET /api/patients/9f2e-…

// ✘ PHI in a JWT — base64 is encoding, not encryption
{ sub: 'u1', patientName: 'Jane Doe', mrn: '123456' }

// ✔ opaque identifiers only

// ✔ never cached anywhere shared

// ✔ MINIMUM NECESSARY is an engineering requirement, not a slogan:
//   return only the fields required for the purpose.

  { projection: { name: 1, allergies: 1, _id: 0 } });   // not the whole doc

H03What is NCPDP and why does it matter in pharmacy specifically?

The National Council for Prescription Drug Programs sets the standards pharmacy runs on. Two matter:

  • NCPDP Telecommunication Standard — the real-time claim format between a pharmacy and a payer/PBM. When a pharmacist scans a prescription and gets an approval or rejection in seconds, that's an NCPDP claim transaction.
  • NCPDP SCRIPT — the e-prescribing standard between prescribers and pharmacies, carried in the US primarily over the Surescripts network. New prescriptions, refill requests, cancellations, and change requests all have message types.
Highest-leverage fact in this sectionIf you name NCPDP unprompted in a pharmacy interview you will stand out immediately. It's the domain's defining acronym and most general backend candidates have never heard of it.

H05What is a PBM and what is a formulary?

A Pharmacy Benefit Manager is the intermediary administering prescription drug benefits for a health plan — it processes claims, negotiates with manufacturers, and manages the pharmacy network. When a pharmacy submits a claim, the PBM adjudicates it.

A formulary is the plan's list of covered drugs, usually tiered with different copays. Formulary status determines whether a claim pays, pays at a higher copay, or rejects with a message directing the pharmacist toward an alternative.

H06What is prior authorization, and why is it a hard engineering problem?

A requirement that the prescriber justify a medication before the plan will cover it. The claim rejects with a "PA required" code, then a separate workflow runs between prescriber, PBM, and pharmacy.

It's hard because it's long-running (hours to days), involves multiple parties with different systems, has many states, and must be resumable across restarts. That makes it a natural fit for an orchestrated saga with durable state, timeouts, and event-driven notification — and a terrible fit for synchronous request/response. Saying that demonstrates you can reason architecturally about a business process you've never implemented.

H08What is DUR and why does it constrain system design?

Drug Utilization Review — automated clinical safety checks before dispensing: drug-drug interactions, therapeutic duplication, dosage appropriateness for age and weight, allergy conflicts, refill-too-soon.

Design consequences: these are on the critical path, so they must be fast and available — you cannot fail open. They need data from multiple sources including medication history across pharmacies, making it a data-federation problem. And overrides must be captured with a reason and an identified pharmacist, because that's a clinical and legal record.

H09What is a controlled substance and what does it change technically?

Drugs scheduled by the DEA (Schedules II–V) with restrictions on refills, quantity, and transfer. Technically this brings EPCS (Electronic Prescribing for Controlled Substances) with two-factor authentication and digital signatures, reporting to state PDMPs, stricter audit trails, and business rules that differ by schedule and by state.

H10How would you design a prescription service for high availability?

Frame it with the domain stakes: downtime means someone doesn't get their medication, so availability targets are genuinely different from a typical web app.

  • Multi-AZ, stateless services, no single point of failure.
  • Explicitly defined degraded modes — if the PBM connection is down, can you queue claims and dispense on a documented override path? That's a business decision to ask about, not assume.
  • Circuit breakers on every external dependency, especially ones outside your control.
  • Idempotency everywhere — a retried claim submission must not double-bill.
  • Async for everything non-critical so it can never affect dispensing.
  • Comprehensive audit logging — both a compliance requirement and your forensic tool.
H11How do you handle PHI in non-production environments?

You don't copy production data down. Options: fully synthetic data generation, or de-identification per the Safe Harbor method (removing the 18 identifiers) or expert determination.

The caveat worth namingDe-identified data often loses the distribution characteristics that make performance testing meaningful. You frequently need synthetic data at production volume even though it's fictional — otherwise your load test passes and production doesn't. Also: separate cloud accounts per environment, and no production credentials on developer machines.

Honestly and structurally. Something like:

Angular for a React developer

If a backend posting lists Angular last under "preferred," this is vocabulary translation, not new learning. Note that postings often write "AngularJS" when they mean modern Angular — worth clarifying which.

V01What's the fundamental difference between Angular and React?

React is a library for rendering UI; you assemble routing, state management, forms, and HTTP from the ecosystem. Angular is a full framework with all of that built in and prescribed.

The practical consequence: Angular codebases look similar to each other and React codebases don't. That's a real advantage in a large enterprise with many teams, and a real cost in flexibility.

V03What is dependency injection in Angular?
Most common use case — a service, injected and trivially mockable
// providedIn:'root' → a singleton for the whole app.
// Provide it in a component instead and it's scoped to that
// component and its children.

  constructor(private http: HttpClient) {}
  list() { return this.http.get<Order[]>('/api/v1/orders'); }
}

});
Connect the dotsThis is the same dependency inversion as the Node service layer in N22 — declare what you need, let something else supply it, and testing becomes substitution rather than interception.
V04What is RxJS and why is it everywhere in Angular?

A library for composing asynchronous streams. Angular's HttpClient, router events, and form value changes all return Observables rather than Promises. An Observable can emit many values over time, is lazy (nothing happens until you subscribe), and is cancellable.

Most common use case — typeahead search, which needs all three properties
results$ = this.searchControl.valueChanges.pipe(
  debounceTime(300),            // wait for a pause in typing
  distinctUntilChanged(),       // ignore "abc" → "abc"
  switchMap(term =>             // ← THE important operator:
    this.api.search(term)),     //   CANCELS the previous in-flight
                                //   request. With mergeMap you'd get
                                //   a race where a slow early response
                                //   overwrites a fast later one.
  catchError(() => of([])),     // an error must not kill the stream
  takeUntilDestroyed()          // auto-unsubscribe on destroy
);

// In the template, the async pipe subscribes AND unsubscribes:
//   <li *ngFor="let r of results$ | async">{{ r.name }}</li>
// Manual .subscribe() without cleanup is the classic Angular leak.
V05How does change detection work in Angular?

By default Zone.js patches async APIs so Angular knows when something might have changed, then checks the entire component tree from the root. Simple, but wasteful on large trees.

ChangeDetectionStrategy.OnPush tells Angular to check a component only when an @Input reference changes, an event fires within it, or an observable it uses via the async pipe emits. That's the Angular equivalent of React.memo plus immutable props — and the same discipline applies: mutate an object in place and the view won't update.

Modern Angular is moving to Signals, which track dependencies precisely and enable zoneless change detection.

V06Template-driven vs reactive forms?

Template-driven puts logic in the template with ngModel — quick for simple forms, harder to test. Reactive defines a FormGroup in the component class — explicit, synchronous access to values and validity, easy to unit test, and far better for dynamic forms with cross-field validation. For anything enterprise, reactive is the answer.

V07What are modules, and what changed with standalone components?

Historically every component belonged to an NgModule that declared it and imported its dependencies — a source of significant boilerplate. Modern Angular supports standalone components that declare their own imports directly, removing NgModules from most applications.

Knowing the framework moved this direction is a useful currency signal — it says you looked at Angular recently rather than remembering it from years ago.

V08What are route guards and resolvers?

Guards run before navigation and can permit, block, or redirect — CanActivate for auth checks, CanDeactivate for unsaved-changes warnings. Resolvers fetch data before the route activates so the component renders with data present rather than flashing a loading state.

Say this out loudA frontend guard is a UX affordance, not a security control — it's trivially bypassed. The server must enforce every rule regardless. That connects directly to the authorization discussion in Section 08, and interviewers notice when a frontend-leaning candidate volunteers it.
V09What are HTTP interceptors?
Most common use case — attach the token, refresh on 401
export const authInterceptor: HttpInterceptorFn = (req, next) => {
  const auth = inject(AuthService);

  // Requests are immutable — clone to modify.
  const authed = req.clone({
    setHeaders: {
      Authorization: `Bearer ${auth.accessToken}`,
      'x-correlation-id': crypto.randomUUID()
    }
  });

  return next(authed).pipe(
    catchError(err => {
      if (err.status === 401) {
        // refresh once, then replay the original request
        return auth.refresh().pipe(switchMap(() => next(authed)));
      }
      return throwError(() => err);
    })
  );
};

Structurally identical to Express middleware, applied client-side — a nice symmetry to point out if asked to compare frontend and backend architecture.

V10How should you position Angular in the interview?

Directly: "My production depth is React and TypeScript. I've mapped the Angular equivalents — dependency injection instead of context, RxJS instead of promises and effects, OnPush instead of memo, reactive forms instead of controlled components with a schema. The architectural concerns are identical, and I'd expect to be productive in a couple of weeks with a real ramp on RxJS operators specifically."

Why that answer worksNaming RxJS as the genuine learning curve is what makes it credible rather than glib. It's the part that actually takes time, and admitting it signals you've looked properly instead of skimming a comparison table.

Two weeks of preparation

Week 1 — close the data-layer gap

Days 1–2. Stand up MongoDB in Docker Compose next to an Express or Fastify service. Model a small domain — customers, orders, fulfilments — and make the embed-versus-reference decision for each relationship explicitly, writing down why.

Days 3–4. Load a few hundred thousand documents. Run queries without indexes, read explain(), add indexes, watch COLLSCAN become IXSCAN. Deliberately violate the ESR rule and observe the in-memory sort. Build one covered query and confirm totalDocsExamined: 0.

Day 5. Write three aggregation pipelines of increasing complexity — a grouped summary, a $lookup join, and a $facet returning results plus a total count in one pass.

Weekend. Implement the transactional outbox with a change-stream relay. This single exercise touches transactions, change streams, at-least-once delivery, and idempotency — four separate interview answers from one afternoon.

Week 2 — architecture and rehearsal

Days 1–2. Add a broker to the same Compose stack — Kafka in KRaft mode, or LocalStack for SNS/SQS. One producer, two competing consumers. Kill a consumer mid-message and watch the redelivery. Then make the consumer idempotent and prove the redelivery is harmless.

Day 3. Split the service in two, with the second reacting to events from the first. Implement a saga with a compensating action, and wrap one call in a circuit breaker with opossum.

Day 4. Domain vocabulary pass. Two hours on the relevant standards for the industry you're interviewing in. Highest return per hour in this entire plan.

Day 5. Rehearse the five stories out loud, timed. Out loud, not in your head — the gap between the two is larger than people expect.

Ongoing. Re-read Sections 05 and 06 until you can name the pattern behind a scenario without looking.

The three things to get right on the day

1. Always name the tradeoff. Every architectural answer should end with what it costs. "Microservices give you independent deployment, and you pay for it in operational complexity and eventual consistency." That single habit is the strongest senior signal available, and it works even on topics you know less well.

2. Anchor in something you built. A concrete story beats a correct definition every time. If you can't anchor an answer in experience, anchor it in something you built deliberately to learn — that counts, and it shows initiative.

3. Be straight about the gaps. "I haven't run this in production, but here's what I built to understand it and here's the equivalent problem I have solved" is a strong answer. Bluffing is the only version that fails, and experienced interviewers detect it in one follow-up.
