Node.js runtime

The event loop is the single most-asked backend Node topic. If you understand it properly, half the performance, concurrency, and debugging questions answer themselves.

The event loop & concurrency model

N01Node is single-threaded — so how does it serve thousands of concurrent requests?

Your JavaScript executes on one thread, but I/O does not. Node delegates work to libuv, which uses the operating system's asynchronous facilities (epoll on Linux, kqueue on macOS, IOCP on Windows) for network I/O, and a small thread pool — four threads by default, tunable via UV_THREADPOOL_SIZE — for things the OS can't do asynchronously, notably file system operations, DNS lookups via dns.lookup, and some crypto and zlib work.

So while one request waits on a database, the single JS thread is free to start the next. Concurrency comes from never sitting idle, not from parallelism.

The consequence that matters

This model only works if nothing CPU-bound runs on the main thread. A synchronous JSON parse of a 50MB payload, a bcrypt round with a high cost factor, an unbounded array sort — any of these freeze every in-flight request, not just the one that caused it. That's the failure mode interviewers are really probing for.

Senior signalSay "non-blocking for I/O" rather than just "non-blocking." Then volunteer that the fix for CPU-bound work is worker_threads, and the fix for using more cores is cluster — they're different problems with different answers.
N02Walk through the phases of the event loop.

Each iteration ("tick") of the loop moves through phases in a fixed order:

  1. Timers — callbacks scheduled by setTimeout and setInterval whose threshold has elapsed.
  2. Pending callbacks — some system-level callbacks deferred from the previous iteration, e.g. certain TCP errors.
  3. Idle / prepare — internal to libuv.
  4. Poll — the important one. Retrieves new I/O events and runs their callbacks. If there's nothing pending, the loop may block here waiting for I/O.
  5. Check — setImmediate callbacks run here.
  6. Close callbacks — socket.on('close') and friends.

Between every phase — and between individual callbacks — Node drains two additional queues: the process.nextTick queue first, then the promise microtask queue. These are not event loop phases; they're checkpoints that run more often.

Common mistakeBelieving setTimeout(fn, 0) runs immediately. It runs in the next timers phase, after at least one full loop iteration, and the actual delay has a minimum of ~1ms.
N03Order these: process.nextTick, Promise.then, setTimeout(fn,0), setImmediate.

process.nextTick → Promise.then (microtasks) → then, depending on context, setTimeout or setImmediate.

// inside the main module
setTimeout(() => console.log('timeout'), 0);
setImmediate(() => console.log('immediate'));
Promise.resolve().then(() => console.log('promise'));
process.nextTick(() => console.log('nextTick'));

// nextTick, promise — then timeout/immediate order is NOT guaranteed

The setTimeout versus setImmediate ordering in the main module is genuinely non-deterministic, because it depends on how long process startup took relative to the 1ms timer threshold. Inside an I/O callback, however, setImmediate always wins — you're already past the poll phase, so check comes before the next timers phase.

Senior signalNote that nextTick can starve the event loop: a recursive nextTick never lets the loop advance. That's why the Node docs steer you toward setImmediate for deferring work.
N04What is the microtask queue, and how does it differ from the macrotask queue?

Microtasks are promise continuations (.then, await resumptions, queueMicrotask). The entire microtask queue drains to empty before the loop proceeds — and any microtask that schedules another microtask gets processed in the same drain. Macrotasks (timers, I/O callbacks, setImmediate) are processed one phase at a time.

Practical implication: an await inside a loop over 100,000 items generates 100,000 microtasks that all drain before any I/O gets serviced. That's a real way to stall a server with code that looks perfectly asynchronous.

N05How would you detect that something is blocking the event loop in production?

Measure event loop lag — the delay between when a timer should fire and when it actually fires. Node exposes this properly via perf_hooks.monitorEventLoopDelay(), which returns a histogram you can export to Prometheus or CloudWatch.

const { monitorEventLoopDelay } = require('perf_hooks');
const h = monitorEventLoopDelay({ resolution: 20 });
h.enable();
setInterval(() => {
  // nanoseconds → ms
  logger.info({ p99: h.percentile(99) / 1e6, mean: h.mean / 1e6 });
  h.reset();
}, 10000);

Alarm on p99 above ~100ms. Once you know it's happening, find what with a CPU profile — node --cpu-prof, Chrome DevTools via --inspect, or clinic.js for flame graphs. The framing that impresses: measure first, then profile, then optimize — never guess.

Naming a hypothesis you eliminated is the strongest possible answer to this question.

N07Explain streams and backpressure.

A stream processes data in chunks rather than loading it all into memory. Four types: Readable, Writable, Duplex, Transform.

Backpressure is what happens when a fast producer outpaces a slow consumer. writable.write() returns false when its internal buffer exceeds highWaterMark; a correct producer stops and waits for the 'drain' event. Ignore that signal and the buffer grows without bound until the process runs out of memory.

const { pipeline } = require('stream/promises');

// handles backpressure AND cleanup on error — always prefer this
await pipeline(
  fs.createReadStream('claims.csv'),
  csvParser(),
  transformToFhir(),
  s3UploadStream()
);
TrapHand-rolling src.on('data', d => dest.write(d)) ignores the return value of write and silently discards backpressure. Use pipeline — it also destroys every stream in the chain on error, which .pipe() does not.
N08What's the difference between a Buffer and a string, and when does it bite you?

A Buffer is a fixed-length sequence of raw bytes outside the V8 heap. Strings are UTF-16 sequences inside the heap. Conversion between them requires an encoding, and getting it wrong corrupts data.

Where it bites: chunking a stream on byte boundaries can split a multi-byte UTF-8 character across two chunks, producing mojibake. string_decoder exists precisely to handle that. Also relevant for signature verification — you must hash the raw bytes, not a re-encoded string.

N10How does require caching work, and how can it cause bugs?

Node caches modules by resolved filename in require.cache. The module body executes exactly once; every subsequent require returns the same exports object. This is why the module pattern works as a singleton — a database connection pool exported from a module is genuinely shared.

The bug: mutable module-level state becomes global state. A module that exports let currentUser and mutates it per request will leak one request's data into another, because there's one module instance serving all concurrent requests. This is the classic Node security bug and it's worth naming.

N11How do you find a memory leak in a Node service?
  1. Confirm it. Watch RSS and heap used over time. A leak trends upward across GC cycles; normal churn sawtooths.
  2. Snapshot. Take heap snapshots at two points under load (node --inspect then Chrome DevTools Memory tab, or v8.writeHeapSnapshot()).
  3. Compare. Use the comparison view to find object types growing between snapshots, then trace retainers to find what's holding the reference.
The usual culprits
  • Event listeners added per request and never removed — watch for the MaxListenersExceededWarning
  • Unbounded caches or arrays at module scope (use an LRU with a size cap)
  • Closures capturing large objects, held by a long-lived timer or promise
  • Global maps keyed by user or session with no eviction
N12Operational errors vs programmer errors — why does the distinction matter?

Operational errors are expected runtime conditions: invalid input, a database timeout, an upstream 503, a file not found. You handle these — validate, retry, return a 4xx/5xx, degrade gracefully.

Programmer errors are bugs: reading a property of undefined, passing the wrong type, a typo. You do not handle these. The process is now in an unknown state; the safest response is to log with full context and exit, letting your orchestrator restart a clean process.

TrapThe wrong answer is "catch everything and keep the server running." Continuing after an uncaught exception risks serving corrupted data — worse than a two-second restart. In healthcare, that distinction isn't academic.
N13What do you do with unhandledRejection and uncaughtException? 
process.on('unhandledRejection', (reason, promise) => {
  logger.fatal({ reason }, 'unhandled rejection');
  throw reason;              // escalate to uncaughtException
});

process.on('uncaughtException', (err) => {
  logger.fatal({ err }, 'uncaught exception — shutting down');
  // flush logs, then die. Do NOT resume serving.
  server.close(() => process.exit(1));
  setTimeout(() => process.exit(1), 5000).unref();
});

Note that since Node 15, unhandled rejections terminate the process by default — which is the correct behavior and worth knowing.

N14How do you implement graceful shutdown?

On SIGTERM (what Kubernetes and ECS send before SIGKILL):

  1. Flip the readiness probe to failing first, so the load balancer stops routing new traffic to you.
  2. Stop accepting new connections — server.close().
  3. Let in-flight requests finish, with a hard timeout (typically shorter than the orchestrator's grace period).
  4. Stop message consumers after acknowledging in-flight messages.
  5. Drain the database pool and close other resources.
  6. Exit 0.

Skipping step 1 is the most common mistake — you close the server while the LB is still sending traffic, producing a burst of connection-refused errors on every deploy.

TrapPromise.all does not cancel the other promises when one rejects. They keep running, and their rejections may become unhandled. In a microservices fan-out, allSettled plus explicit per-call handling is usually the correct choice.
N16You need to call an API for 10,000 records. How do you avoid destroying it?

Promise.all over 10,000 items fires 10,000 concurrent requests — you'll exhaust sockets, blow the target's rate limit, and probably get banned. You need a bounded concurrency pool.

async function mapLimit(items, limit, fn) {
  const results = [];
  const executing = new Set();
  for (const item of items) {
    const p = Promise.resolve().then(() => fn(item));
    results.push(p);
    executing.add(p);
    p.finally(() => executing.delete(p));
    if (executing.size >= limit) await Promise.race(executing);
  }
  return Promise.allSettled(results);
}

In production, reach for p-limit or p-queue rather than hand-rolling. Add exponential backoff with jitter on 429 and 5xx, and respect Retry-After when the server sends it.

N17What is the difference between async/await and raw promises in terms of error handling?

Functionally equivalent — async/await is syntax over promises. The practical differences are ergonomic: try/catch works naturally, stack traces are better preserved across await boundaries in modern V8, and sequential logic reads sequentially.

The trap is accidental serialization. This runs two calls one after the other:

const a = await getPatient(id);      // 200ms
const b = await getPrescriptions(id); // 200ms → 400ms total

When they're independent, start both before awaiting either:

const [a, b] = await Promise.all([getPatient(id), getPrescriptions(id)]); // 200ms
N18What is the EventEmitter and when would you use it?

Node's implementation of the observer pattern, and the base class for streams, HTTP servers, and process itself. You'd use it to decouple producers from consumers within a single process — an audit logger that reacts to domain events, for instance.

Two things interviewers probe: emitters are synchronous (listeners run in the order registered, blocking the emitter until done), and an unhandled 'error' event throws and crashes the process. Always attach an error listener.

The scaling caveat worth volunteering: an EventEmitter is in-process only. The moment you have more than one instance, you need a real message broker — which is exactly the SNS/SQS/Kafka line in this JD.

N19How do you handle configuration and secrets in a Node service?

Configuration comes from the environment, per twelve-factor. Validate it at startup with a schema (envalid, zod, or Joi) and fail fast — a service that boots with a missing database URL and discovers it on first request is much worse than one that refuses to start.

Secrets never live in environment variables in a mature setup, because they leak into logs, crash dumps, and docker inspect. Use AWS Secrets Manager or Parameter Store, fetched at startup with an IAM role, cached in memory, and rotated. Mention that this is exactly what IAM roles exist for — no static credentials on the instance.

N20What is package-lock.json for, and what's the difference between npm install and npm ci?

The lockfile pins the exact resolved version of every package in the tree, including transitive dependencies, so builds are reproducible. Without it, a caret range like ^4.17.0 can resolve differently on two machines a day apart.

npm install may update the lockfile to satisfy package.json. npm ci deletes node_modules, installs strictly from the lockfile, and errors if the two files disagree. Always use npm ci in CI and Docker builds — it's faster and deterministic. That single answer signals build-pipeline experience.

N21How do you audit and manage dependency risk?

npm audit in CI as a gate, Dependabot or Renovate for automated upgrade PRs, and a policy on transitive depth. Beyond tooling, the judgment answer: evaluate a dependency's maintenance status, install size, and transitive count before adding it — a 3-line utility with 40 transitive dependencies is a supply-chain liability. In a HIPAA-regulated environment you'll also need an SBOM.

N22What are the biggest Node performance wins in a typical API?
  1. Fix the database, not the Node. Missing indexes and N+1 queries dwarf everything else. Profile before touching JS.
  2. Don't block the loop. One synchronous call in a hot path costs more than every micro-optimization combined.
  3. Reduce payload size. Project only the fields you need; enable gzip/brotli; paginate.
  4. Reuse connections. HTTP keep-alive agents for outbound calls, properly sized DB pools.
  5. Cache the expensive and stable. Redis for computed results, HTTP cache headers at the edge.
  6. Scale out. Stateless processes behind a load balancer, once the above is done.
Senior signalLead with "measure first." Candidates who start listing micro-optimizations without mentioning profiling are signalling they've never done this on a real system.

  • CPU: node --cpu-prof writes a .cpuprofile loadable in Chrome DevTools. Or clinic flame for flame graphs.
  • Memory: --heap-prof, or heap snapshots via the inspector.
  • Event loop: clinic doctor diagnoses whether you're I/O-bound, CPU-bound, or GC-bound.

N24What is the difference between JSON.parse cost and streaming JSON?

JSON.parse is synchronous and C++-fast, but on a large payload it still blocks the loop for the duration and allocates the entire object graph at once. For payloads in the tens of megabytes — bulk claim files, exports — use a streaming parser so you process records incrementally with bounded memory.

N25What Node version considerations matter in an enterprise?

Know the release line: even-numbered majors go to LTS (Active for ~a year, then Maintenance for ~18 months); odd-numbered majors never do. Enterprises should run Active or Maintenance LTS only, because security patches stop at end-of-life.

Recent capabilities worth naming: a stable built-in test runner (node:test), native fetch, the permission model, and --env-file support. Being current on these signals you're not coasting on Node 14 habits.

N26How do you structure a Node service so it stays maintainable?

Layered, with dependencies pointing inward:

src/
  routes/        // HTTP concerns only: parse, validate, delegate
  controllers/   // orchestration, no business rules
  services/      // business logic — framework-agnostic, unit-testable
  repositories/  // data access; the only layer that knows about Mongo
  models/        // schemas / domain entities
  middleware/    // auth, error handler, correlation ID
  config/        // validated env
  utils/

The rule that matters: services must not import Express types, and repositories are the only place Mongo appears. That's what makes business logic testable without spinning up HTTP or a database, and what makes swapping the data layer possible. In interviews, express this as dependency inversion rather than as a folder list — the folders are the consequence, not the principle.

Express.js

Express is deliberately minimal, which means interviewers can go deep on the few concepts it does have. Middleware ordering and async error handling are where most candidates stumble.

The middleware model

E01What is middleware in Express, and how does the chain work?

A middleware is a function with the signature (req, res, next) that sits in an ordered pipeline. Each one can read and mutate req and res, end the response, or call next() to pass control onward. Express walks the stack in registration order, matching path and method.

app.use(helmet());                  // 1. security headers
app.use(express.json({limit:'1mb'})); // 2. body parsing
app.use(correlationId);             // 3. request tracing
app.use(requestLogger);             // 4. logging
app.use('/api', rateLimiter);        // 5. throttling
app.use('/api', authenticate);        // 6. who are you
app.use('/api/v1/rx', rxRouter);      // 7. routes
app.use(notFoundHandler);           // 8. 404
app.use(errorHandler);              // 9. must be LAST, 4 args

Three things a request can do at each step: continue (next()), terminate (res.send()), or fail (next(err)). Forgetting all three — no next, no response — hangs the request until the client times out.

E02Why does middleware order matter? Give a concrete failure.

Order is the entire control flow. Concrete failures:

  • Registering the error handler before your routes means it never sees errors from them.
  • Putting authenticate after the route means the route runs unauthenticated — a real security hole, and one of the four root causes you'd check for an authorization bypass.
  • Putting the rate limiter after authentication means unauthenticated attackers can burn CPU on JWT verification for free.
  • Putting body parsing after a route means req.body is undefined inside it.
Your materialThe OFS BusinessAdmin bypass you investigated included "route not calling the RBAC check" as one of four candidate causes. That's precisely this class of bug, and it's a strong thing to have already reasoned about out loud.
E03How do you write a centralized error handler?

Express identifies an error handler by arity — four parameters. It must be registered last.

class AppError extends Error {
  constructor(message, statusCode, code, details) {
    super(message);
    this.statusCode = statusCode;   // 400, 404, 409...
    this.code = code;               // 'RX_NOT_FOUND' — stable, machine-readable
    this.details = details;
    this.isOperational = true;      // expected, not a bug
  }
}

// eslint-disable-next-line no-unused-vars — the 4th arg is required
app.use((err, req, res, next) => {
  const status = err.statusCode || 500;
  logger.error({ err, correlationId: req.id, path: req.path });

  res.status(status).json({
    type:   'https://api.example.com/errors/' + (err.code || 'internal'),
    title:  status >= 500 ? 'Internal Server Error' : err.message,
    status,
    detail: err.isOperational ? err.details : undefined,
    instance: req.id
  });
});
NeverLeak stack traces, SQL text, or internal paths to the client. In healthcare, an error message containing a patient identifier is a reportable disclosure.
E04Why doesn't Express 4 catch errors thrown in async route handlers?

Because Express 4 calls your handler and doesn't inspect the returned value. An async function returns a promise; if it rejects, nothing is watching, so you get an unhandled rejection and a request that hangs until timeout.

// BROKEN in Express 4 — the 500 never happens, request hangs
app.get('/rx/:id', async (req, res) => {
  const rx = await db.find(req.params.id); // throws → nobody catches
  res.json(rx);
});

// FIX 1: wrapper
const ah = fn => (req, res, next) => Promise.resolve(fn(req,res,next)).catch(next);
app.get('/rx/:id', ah(async (req,res) => { ... }));

// FIX 2: express-async-errors (patches Express globally)
// FIX 3: upgrade to Express 5, which handles rejected promises natively

Knowing that Express 5 fixed this is a current-knowledge signal worth dropping.

E05app.use vs app.get vs router.use — what's the difference?

app.use(path, fn) matches any method and treats the path as a prefix — app.use('/api', x) matches /api/anything/deep. app.get(path, fn) matches only GET and requires an exact path match (modulo params). router.use is the same as app.use but scoped to a mounted router, which is how you compose a large API into modules.

Note that inside a mounted router, req.url is stripped of the mount prefix while req.originalUrl retains it — a detail that trips people up when building logging middleware.

E06How do you structure a large Express app into routers? 
// routes/prescriptions.routes.js
const router = express.Router({ mergeParams: true });
router.use(authorize('PRESCRIPTION_READ'));
router.get('/',    validate(listSchema),   ctrl.list);
router.get('/:id', validate(idSchema),     ctrl.get);
router.post('/',   authorize('PRESCRIPTION_WRITE'), validate(createSchema), ctrl.create);
module.exports = router;

// app.js
app.use('/api/v1/prescriptions', prescriptionRoutes);

The point to make: each router owns its own middleware, so authorization is declared once next to the routes it protects rather than scattered. mergeParams lets nested routers see the parent's route parameters.

Request handling & validation

E07How do you validate incoming requests, and where?

At the boundary, declaratively, before any business logic runs. Use a schema library — Zod, Joi, or JSON Schema via ajv — and generate the validation middleware from the schema so the contract lives in one place.

const createRx = z.object({
  patientId:  z.string().uuid(),
  ndcCode:    z.string().regex(/^\d{5}-\d{4}-\d{2}$/),
  quantity:   z.number().int().positive().max(1000),
  daysSupply: z.number().int().min(1).max(90),
  refills:    z.number().int().min(0).max(11).default(0)
});

const validate = schema => (req, res, next) => {
  const r = schema.safeParse(req.body);
  if (!r.success) return next(new AppError('Validation failed', 400, 'INVALID_BODY', r.error.issues));
  req.body = r.data;  // use the parsed, coerced, stripped version
  next();
};

Two senior points: (1) reassign req.body to the parsed output so unknown fields are stripped — that prevents mass-assignment attacks; (2) the same schema can generate your OpenAPI spec, keeping documentation honest.

E09Explain NoSQL injection in an Express + Mongo app.

If you pass a request body straight into a query, an attacker sends an object instead of a string:

// Attacker POSTs: { "username": "admin", "password": { "$ne": null } }
User.findOne({ username: req.body.username, password: req.body.password });
// becomes: password: { $ne: null }  →  matches. Login bypassed.

Three defenses, in order of importance: validate types with a schema so password must be a string; never compare passwords directly (store a bcrypt/argon2 hash and use compare); and strip $-prefixed keys with express-mongo-sanitize. Also relevant: $where and mapReduce execute JavaScript server-side and should be disabled outright.

E10How do you implement request correlation across services? 
app.use((req, res, next) => {
  req.id = req.headers['x-correlation-id'] || crypto.randomUUID();
  res.setHeader('x-correlation-id', req.id);
  // AsyncLocalStorage makes it available anywhere downstream
  // without threading it through every function signature

Then every log line and every outbound HTTP call carries the same ID. AsyncLocalStorage is the piece most candidates don't know — it's Node's answer to thread-local storage, and it's what makes correlation IDs work without polluting function signatures. Mentioning it is a strong signal.

E11How do you handle file uploads safely?

Use multer or busboy with strict limits on file size and count. Validate the actual content type by sniffing magic bytes, not by trusting the client-supplied MIME type or extension. Generate a new server-side filename — never use the client's, which is a path traversal vector. Store outside the web root, ideally in S3 via a presigned URL so the file never touches your API at all. Scan for malware if the content is user-supplied and will be served back.

E13What is the request lifecycle in Express, end to end?
  1. Node's HTTP server receives the connection and parses headers, emitting request.
  2. Express wraps req/res with its own prototype extensions.
  3. The router walks the middleware stack in order, matching method and path.
  4. Body-parsing middleware consumes the request stream and populates req.body.
  5. Route handler runs; it writes headers and body via res.
  6. On res.end(), the response is flushed and the finish event fires — that's where you log status and duration.
  7. If any step calls next(err), Express skips ahead to the first four-argument handler.

The detail worth knowing: you cannot set headers after the body has started streaming — that's the source of the ERR_HTTP_HEADERS_SENT error, which almost always means two code paths both tried to respond.

E14How do you implement rate limiting that works across multiple instances?

In-memory rate limiting breaks the moment you run more than one replica — each instance has its own counter, so N instances means N times the intended limit. Use a shared store: Redis with the rate-limit-redis adapter, or push the concern up to the API gateway.

Algorithms worth naming: fixed window (simple, but allows a burst at the boundary), sliding window (smoother, more expensive), token bucket (allows controlled bursts — usually what you want for an API), leaky bucket (smooths output rate). Always return 429 with a Retry-After header so well-behaved clients can back off correctly.

E16How do you serve an API and handle CORS correctly?

CORS is a browser-enforced policy, not a server security control — it stops other websites from reading your responses in a user's browser. It does nothing against curl or a server-side attacker, which is why "we have CORS" is never an answer to "is this endpoint secured."

Configure an explicit allowlist of origins, never a wildcard when credentials: true (the browser rejects that combination anyway), and remember preflight: a non-simple request triggers an OPTIONS call that must return the right Access-Control-Allow-* headers within Access-Control-Max-Age.

E17What are health check endpoints and why are there two kinds?

Liveness answers "is this process wedged?" It should be cheap and check nothing external — if it fails, the orchestrator kills and restarts the container. Readiness answers "can this instance serve traffic right now?" It checks dependencies — database reachable, cache connected, migrations complete — and if it fails, the load balancer stops routing to you without a restart.

Classic outagePutting a database check in the liveness probe. The database blips, every instance fails liveness, the orchestrator restarts your entire fleet simultaneously, and now you have a cold cache stampede on top of a database problem. Keep liveness dumb.
E18How do you handle long-running work in an Express endpoint?

Don't do it inline. Accept the request, validate it, enqueue a job, and return 202 Accepted with a location or job ID the client can poll — or push completion via WebSocket/SSE. This is exactly the asynchronous pattern the messaging section covers.

The frontend consequence is worth volunteering in a fullstack interview: the UI must now handle a "processing" state, and a user who refreshes before the job completes must not see stale data. That's a real design conversation, not a detail.

REST & API design

"Building and consuming RESTful APIs" appears twice in the JD. Expect design questions where they hand you a domain and ask you to model the endpoints.

Fundamentals

R01What actually makes an API RESTful?

Six constraints from Fielding's dissertation: client-server separation, statelessness, cacheability, a uniform interface, a layered system, and optionally code-on-demand. In practice, the ones that carry weight:

  • Statelessness — every request carries everything needed to process it. No server-side session affinity. This is what makes horizontal scaling possible, which is why it matters for the microservices half of this JD.
  • Uniform interface — resources identified by URI, manipulated through representations, using standard methods with standard semantics.
  • Cacheability — responses declare whether and how long they can be cached.

Honest framing: almost nothing in industry is fully RESTful — most APIs sit at level 2 of the Richardson Maturity Model (resources + HTTP verbs) and skip hypermedia entirely. Saying that shows you know the theory and the practice.

R02Explain the Richardson Maturity Model.
  • Level 0 — one endpoint, everything tunnelled through POST. SOAP-style RPC.
  • Level 1 — resources get their own URIs, but still one verb.
  • Level 2 — proper HTTP verbs and status codes. This is where nearly every production API lives.
  • Level 3 — HATEOAS: responses include links describing available next actions, so clients discover the API rather than hardcoding URLs.

Level 3 is rare because client teams generally don't want to write link-following logic. Worth noting: FHIR, the healthcare interoperability standard, actually does use hypermedia — relevant given the pharmacy domain in this JD.

R04How do you make a POST safe to retry?

Idempotency keys. The client generates a UUID per logical operation and sends it as a header; the server stores key → response and returns the stored response on a repeat.

async function withIdempotency(key, userId, fn) {
  const existing = await idem.findOne({ key, userId });
  if (existing?.status === 'completed') return existing.response;
  if (existing?.status === 'in_progress') throw new AppError('In progress', 409);

  await idem.insertOne({ key, userId, status: 'in_progress' }); // unique index on key
  const result = await fn();
  await idem.updateOne({ key }, { $set: { status:'completed', response: result }});
  return result;
}
The subtleties interviewers probe

  • Scope the key to the user, so one tenant can't collide with another's.
  • Expire keys (24h TTL is typical) so the store doesn't grow forever.
  • A unique index on the key is what makes the concurrent case safe — two simultaneous requests, one insert wins.

R10How do you prevent lost updates when two users edit the same record?

Optimistic concurrency control. The server returns an ETag (or a version field); the client sends it back in If-Match; the server rejects with 412 Precondition Failed or 409 Conflict if it no longer matches.

GET  /prescriptions/9f2      → 200, ETag: "v7"
PATCH /prescriptions/9f2     If-Match: "v7"
   → 200 if still v7, 412 if someone else already wrote v8

The alternative is pessimistic locking — take a lock on read — which is simpler to reason about but hurts throughput and needs lock expiry to survive a crashed client. Optimistic is right for the overwhelming majority of web APIs because conflicts are rare.

R11Explain HTTP caching: Cache-Control, ETag, and conditional requests.
  • Cache-Control: max-age=300 — cache for 5 minutes without asking.
  • private vs public — whether shared caches (CDN, proxy) may store it. Anything containing PHI must be private, no-store.
  • ETag — a version fingerprint. The client resends it as If-None-Match; if unchanged, the server returns 304 Not Modified with no body, saving bandwidth but not a round trip.
  • stale-while-revalidate — serve the stale copy immediately while refreshing in the background. Excellent for perceived performance.

The framing that lands: caching is the cheapest performance work available, and most teams never set a single header.

R13How do you document an API, and why does it matter more in microservices?

OpenAPI (formerly Swagger), generated from the same schemas you validate against so it can't drift. In microservices the documentation is the contract between teams — a stale spec causes integration failures that are expensive to trace across service boundaries. R14How do you handle bulk operations in REST?

REST has no native bulk semantics, so pick a convention and be consistent. Common approaches: a dedicated POST /prescriptions/bulk endpoint that accepts an array and returns 207 Multi-Status with per-item results; or an async job — POST /import-jobs returning 202 plus a job resource to poll.

The key design point is partial failure: decide up front whether the batch is atomic (all or nothing) or best-effort (each item independent), and make the response shape reflect that choice unambiguously.

R15What's the difference between PUT and PATCH, really?

PUT replaces the entire resource with the representation you send — omitted fields should be cleared, not preserved. PATCH applies a partial modification. Most teams get PUT wrong by treating it as a partial update, which then makes it non-idempotent in practice and confuses clients.

For PATCH there are two formalized formats worth naming: JSON Merge Patch (RFC 7386 — send the fields you want changed, null deletes) and JSON Patch (RFC 6902 — an array of explicit operations, which supports array manipulation and tests).

R16How do you design an API for a client you don't control?

Assume everything: they will retry, they will send stale versions, they will not read your deprecation notices, and they will depend on undocumented behavior. Therefore: version explicitly, make writes idempotent, return machine-readable error codes, publish a changelog, instrument per-client usage so you know who's on the old version, and never remove a version until telemetry shows nobody calls it.

R17What is content negotiation?

The client states preferences via Accept, Accept-Language, and Accept-Encoding; the server responds with the best available representation and declares it in Content-Type. Relevant in healthcare because FHIR supports both JSON and XML representations of the same resource, negotiated this way. If you can't satisfy the request, return 406 Not Acceptable.

R18How do you consume a third-party API robustly?
  1. Timeout everything. No outbound call without an explicit timeout — the default is often infinite.
  2. Retry with exponential backoff and jitter, but only idempotent calls, and respect Retry-After.
  3. Circuit breaker so you stop hammering a dead dependency and fail fast instead.
  4. Bulkhead — a bounded connection pool per dependency, so one slow upstream can't consume all your sockets.
  5. Validate their responses. Their contract will change without notice.
  6. Cache what's safe to cache, and define a degraded mode for when they're down.

This list is essentially the reliability half of the microservices patterns section — the same problems appear whether the dependency is external or internal.

M01Embed or reference? How do you decide?

M03What are the MongoDB anti-patterns?
  • Unbounded arrays — embedding a list that grows forever. Hits the 16MB cap and destroys write performance long before that.
  • Massive documents — the whole document is read into memory even if you project one field.
  • Too many collections — each carries index and metadata overhead.
  • Bloated documents you never read — pushing the working set out of RAM.
  • Case-insensitive queries without a collation index — forces a collection scan.
  • Separate collections mirroring relational tables — importing a normalized SQL schema unchanged, then $lookup-ing everywhere. This is the most common mistake teams make coming from SQL.

M04What is BSON and how does it differ from JSON?

BSON is Mongo's binary serialization format. It's a superset of JSON with additional types: ObjectId, Date, Decimal128, Binary, Int32/Int64, and regular expressions. It's length-prefixed so fields can be skipped without parsing.

The type that matters in healthcare and finance is Decimal128. JavaScript numbers are IEEE 754 doubles and cannot represent 0.1 exactly — storing currency or dosage amounts as doubles produces rounding errors that accumulate.

Your materialYou fixed a family of floating-point precision bugs — Math.round against IEEE 754, a 0.99h tolerance, and parseInt → Number() to preserve decimals, where the last one carried a silent over-assignment risk. That's a direct, credible answer to "why does Decimal128 exist?"
M05What is an ObjectId and what's inside it?

12 bytes: a 4-byte Unix timestamp, a 5-byte random value per process, and a 3-byte incrementing counter. Consequences worth knowing:

  • It's roughly monotonically increasing, so sorting by _id approximates sorting by creation time, and _id.getTimestamp() gives you creation time for free.
  • It's generated client-side by the driver, so you know the ID before the insert round-trips.
  • Because it's monotonic, using it as a shard key concentrates all new writes on one shard — a classic hot-shard mistake.

Indexing

M06Explain the ESR rule for compound indexes.

Equality, Sort, Range — the order fields should appear in a compound index.

// Query: exact match on status, sorted by date, range on quantity
db.prescriptions.find({ status: 'active', quantity: { $gt: 30 } })
                .sort({ filledAt: -1 });

// CORRECT: equality → sort → range
db.prescriptions.createIndex({ status: 1, filledAt: -1, quantity: 1 });

// WRONG: range before sort forces an in-memory sort
db.prescriptions.createIndex({ status: 1, quantity: 1, filledAt: -1 });

Why: equality fields narrow the scan to a contiguous block of the index. Within that block, the sort field is already in order, so Mongo can stream results without a blocking sort. A range field scatters entries, so anything after it is no longer sorted.

The consequence of getting it wrong: an in-memory sort, which fails outright above 32MB (100MB in some versions) unless you allow disk use — a production error that appears only once data grows.

Senior signalAdd the prefix rule: an index on {a:1,b:1,c:1} also serves queries on {a} and {a,b}, but not on {b} or {b,c} alone. That's why you can often replace three indexes with one.

M09What is a covered query?

A query answered entirely from the index — every field in the filter, the sort, and the projection is present in the index, so Mongo never fetches the document. Enormously faster because it avoids random document reads.

db.rx.createIndex({ patientId: 1, status: 1, ndcCode: 1 });

db.rx.find({ patientId: x, status: 'active' },
           { _id: 0, ndcCode: 1 });   // covered — note _id must be excluded

The gotcha worth naming: _id is returned by default and isn't in your index, so you must explicitly exclude it or the query won't be covered.

M10What's the cost of an index?

Indexes speed reads and slow writes. Every insert, update to an indexed field, and delete must update every relevant index. They also consume RAM — and MongoDB's performance model depends on indexes fitting in memory. An index that doesn't fit means disk reads on every lookup, at which point it can be slower than no index at all.

So: index for your actual query patterns, use $indexStats to find indexes nobody uses, and drop them. Prefer one well-ordered compound index over three single-field indexes.

M11How do you build an index on a huge production collection without downtime?

Since MongoDB 4.2, index builds use an optimized process that only holds an exclusive lock briefly at the start and end, so they're effectively online. On a replica set the safest approach is still a rolling build — take one secondary out of the set, build, rejoin, repeat, then step down the primary and do it last. In Atlas this is managed for you.

M13How do you optimize an aggregation pipeline?
  1. $match as early as possible, ideally first, so it uses an index and shrinks everything downstream.
  2. $project away unneeded fields early to reduce memory per document.
  3. Avoid $unwind before $match — you multiply documents then throw most away.
  4. $limit right after $sort lets Mongo use a top-K sort instead of sorting everything.
  5. Be aware of the 100MB per-stage memory limit; use allowDiskUse: true when necessary, but treat needing it as a design smell.
  6. Use explain() on the aggregation too — the optimizer reorders some stages automatically, and you should verify it did what you expected.
M14Is $lookup a real join? When should you avoid it?

It's a left outer join, but it's not equivalent to a relational join. It executes per input document, it can only use an index on the foreign collection's join field, and it doesn't work across shards in all configurations. On large collections it's often slower than doing two queries and joining in application code.

The Mongo-native answer is usually to avoid needing the join — via the extended reference pattern (duplicate the two fields you need), the computed pattern (precompute the aggregate), or by embedding. Saying that demonstrates you think in Mongo rather than in SQL with different syntax.

M15What are change streams and what would you use them for?

A change stream lets you subscribe to inserts, updates, deletes, and replacements on a collection, database, or deployment. It's built on the replica set oplog, so it requires a replica set, and it's resumable via a resume token after a disconnect.

Uses: cache invalidation, pushing live updates to clients, maintaining a search index, and — most relevant to this JD — implementing the transactional outbox pattern or doing change data capture into Kafka without dual writes. That connection between a Mongo feature and a microservices pattern is exactly the "connect the dots" answer that lands.

Replication, sharding & consistency

M16Explain replica sets and elections.

A replica set is a group of mongod processes holding the same data: one primary that takes all writes, and secondaries that replicate the primary's oplog (a capped collection of idempotent operations).

If the primary becomes unreachable, the remaining members hold a raft-like election; a majority is required, which is why you run an odd number of voting members. An arbiter can break ties without holding data, though it's discouraged in modern deployments because it weakens durability guarantees.

During an election — typically a few seconds — writes fail. Modern drivers have retryable writes enabled by default, so a single write is retried once against the new primary, making elections mostly invisible to applications. Knowing that detail is a good signal.

M17What are read and write concerns?

Write concern — how many members must acknowledge a write before the driver returns:

  • w: 1 — primary only. Fast, but a failover can lose the write.
  • w: "majority" — a majority acknowledged; the write survives failover. The default since 5.0.
  • j: true — additionally flushed to the on-disk journal.

Read concern — what guarantee reads give:

  • local — whatever this node has; may be rolled back.
  • majority — only data acknowledged by a majority; won't be rolled back.
  • linearizable — reflects all writes that completed before the read began. Expensive.
  • snapshot — a consistent point-in-time view, used in transactions.

Read preference is separate: which member to read from (primary, secondaryPreferred, nearest). Reading from secondaries scales reads but gives you eventual consistency — a read-your-own-writes bug waiting to happen. In healthcare, dispensing decisions read from the primary.

M18Explain sharding and how to choose a shard key.

Sharding partitions a collection horizontally across multiple replica sets. A config server replica set holds metadata; mongos routes queries. Data is split into chunks by shard key range and balanced across shards.

Choosing the shard key — three properties
  • High cardinality — enough distinct values to split indefinitely.
  • Even distribution — no hot shard. A monotonically increasing key like _id or a timestamp sends every new write to one shard.
  • Query isolation — most queries should include the shard key so mongos can target a single shard. Without it, every query becomes a scatter-gather across all shards.

Options: hashed keys give even distribution but destroy range-query locality; compound keys (e.g. {region: 1, patientId: 1}) often balance both. Since 5.0 you can reshard a live collection, but it's expensive — get it right first.

Senior signalSay "most systems don't need sharding — vertical scaling and replica sets take you a very long way, and sharding adds real operational complexity." Knowing when not to shard is the senior answer.
M19Does MongoDB support transactions?

Yes. Single-document operations have always been atomic. Multi-document ACID transactions arrived in 4.0 for replica sets and 4.2 for sharded clusters.

const session = client.startSession();
try {
  await session.withTransaction(async () => {
    await inventory.updateOne({ ndc, qty: { $gte: n } },
                              { $inc: { qty: -n } }, { session });
    await fills.insertOne({ rxId, ndc, qty: n }, { session });
  }, { readConcern: { level: 'snapshot' },
       writeConcern:{ w: 'majority' } });
} finally { await session.endSession(); }

Caveats worth naming: transactions have a 60-second default runtime limit, they carry meaningful performance cost, and — the important design point — if you need them frequently, your schema is probably wrong. The Mongo-idiomatic answer is to model so related data lives in one document, making single-document atomicity sufficient.

M20What happens to transactions across microservices?

They don't exist. A database transaction can't span two services with separate databases. This is the single most important consequence of database-per-service, and the answer is the saga pattern — see the microservices section. Being able to bridge from "Mongo has transactions" to "but they stop at the service boundary, so here's what you do instead" is exactly the dot-connecting this JD is asking for.

Mongoose & the driver

M21What does Mongoose give you over the native driver, and what does it cost?

Gives: schema definition and validation, type casting, middleware hooks (pre/post save, remove, validate), virtuals, populate for reference resolution, and a plugin system.

Costs: a performance overhead from hydrating every result into a full Mongoose document, an abstraction that hides what query actually runs, occasional lag behind new server features, and the illusion of a rigid schema in a schemaless database — validation is application-side only, so anything writing directly to the database bypasses it.

The mature position: use Mongoose for application code where schema discipline helps, use the native driver for bulk operations and complex aggregations, and add JSON Schema validation at the collection level ($jsonSchema) so the database enforces invariants regardless of client.

M22What does .lean() do and when should you use it?

.lean() returns plain JavaScript objects instead of Mongoose documents — no getters, setters, virtuals, or save(). It's substantially faster and uses much less memory because it skips hydration.

Rule: use .lean() on every read-only query. If you're serializing straight to JSON in a GET handler, you have no use for document methods. This is one of the highest-value, lowest-effort Mongoose optimizations and a good thing to have an opinion about.

M23What is populate and what's wrong with it?

populate resolves references by issuing additional queries — it's a client-side join, not a database join. Populating a field on 100 documents fires a second query (Mongoose batches with $in, so it's usually 1 extra query per populated path, not 100 — but nested populates multiply).

The problems: extra round trips, no ability for the database to optimize the join, and it encourages relational modelling in a document database. Alternatives: $lookup when you truly need a join, or — better — the extended reference pattern so the data you need is already there.

M24How do Mongoose middleware hooks work, and what's a good use?

pre and post hooks on document operations (save, validate, remove) and query operations (find, updateOne). Legitimate uses: hashing a password before save, setting audit fields, emitting a domain event after save, or applying a soft-delete filter to every query.

TrapDocument hooks do not fire on updateMany, findOneAndUpdate, or bulk operations — those are query middleware and need separate hooks. Business logic hidden in hooks that silently doesn't run is a classic source of production bugs.
M25How do you manage MongoDB connections in Node?

Connect once at process start and reuse the connection pool for the process lifetime — the driver maintains the pool internally. Never connect per request; that's the single most common Mongo performance bug in Node services.

Key options: maxPoolSize (default 100 — often too high for a small instance; each connection costs server memory), minPoolSize to keep warm connections, serverSelectionTimeoutMS, and maxIdleTimeMS.

Lambda gotchaIn AWS Lambda, declare the client outside the handler so it survives across warm invocations, and set callbackWaitsForEmptyEventLoop = false. Otherwise every invocation opens a new pool and you exhaust the server's connection limit. This is a very commonly asked serverless question.

M27How do you back up and restore MongoDB?

mongodump/mongorestore for logical backups (slow on large data, but portable), filesystem or volume snapshots for physical backups (fast, requires a consistent snapshot), and Atlas continuous backup with point-in-time restore. In a regulated environment you also need documented retention, encrypted backups, and — critically — restore drills, because a backup you've never restored is a hypothesis, not a backup.

M28How do you secure a MongoDB deployment?
  • Authentication enabled (SCRAM, or x.509 / LDAP / AWS IAM in enterprise) — never an open instance.
  • Role-based access control with least privilege; a read-only role for reporting, no root in application connection strings.
  • TLS in transit; encryption at rest.
  • Network isolation — VPC/private endpoint, IP allowlist, never public.
  • Auditing enabled (Enterprise/Atlas) — required for HIPAA.
  • Field-level encryption or Queryable Encryption for PHI, so sensitive fields are encrypted client-side and the database never sees plaintext. This is a strong thing to name in a healthcare interview.
M29A query that was fast last month is slow now. How do you investigate?
  1. explain('executionStats') — did the plan change from IXSCAN to COLLSCAN?
  2. Check data growth — an index that used to fit in RAM may no longer.
  3. Check selectivity — an index on status was selective when 1% were active; now 60% are.
  4. Look at the profiler (db.setProfilingLevel) or Atlas slow-query log for the actual shape of slow queries in production.
  5. Check for a new index the optimizer now prefers, or a dropped one.
  6. Check working set vs RAM, and whether you're now paging from disk.

The structure — reproduce, measure, form a hypothesis, test it — matters more than the specific list.

M30How do you do schema migrations in MongoDB?

There's no ALTER TABLE, so you have options:

  • Lazy migration — add a schemaVersion field; on read, if the version is old, transform and rewrite. Zero downtime, but the transformation code lives forever unless you clean up.
  • Batch migration — a background job that rewrites documents in chunks with a rate limit. Requires the application to tolerate both shapes during the run.
  • Dual-write — write both old and new shapes, backfill, cut reads over, then stop writing the old. Safest for large, critical collections.

Use a migration tool (migrate-mongo) so migrations are versioned in source control and applied consistently across environments — that's the enterprise expectation.

Section 05 · 26 questions

Microservices architecture

Named in both the technical and conceptual sections of the JD. Expect a system-design round. The recurring theme in every answer: distributed systems trade simplicity for independence, and every benefit has a matching cost.

Fundamentals & boundaries

S01What are microservices, and what problem do they actually solve?

An architectural style where an application is a suite of small, independently deployable services, each owning its own data, communicating over a network, and organized around business capabilities.

The problem they solve is organizational, not technical. A monolith forces every team onto one release train, one technology stack, and one scaling unit. Microservices let teams deploy independently. That's the actual benefit — everything else (polyglot stacks, independent scaling, fault isolation) is secondary.

Senior signalSay this out loud: "Microservices trade code complexity for operational complexity. You're choosing to solve distributed systems problems — partial failure, eventual consistency, distributed tracing — in exchange for team autonomy. If you don't have the team-autonomy problem, you're paying that cost for nothing." Interviewers are often listening specifically for whether you'll say microservices are always better.
S02When should you not use microservices?
  • Small team. Fewer than about 15 engineers and you'll spend more time on infrastructure than features.
  • Unclear domain. If you don't yet know where the boundaries are, you'll draw them wrong and pay enormously to move them. Boundaries in a monolith are cheap to change; boundaries between services are not.
  • No operational maturity. Without CI/CD, centralized logging, distributed tracing, and monitoring, microservices are undebuggable.
  • Strongly transactional domain. If nearly everything needs ACID guarantees across entities, splitting them is fighting the domain.

The recommended path is the modular monolith first — well-separated modules with enforced boundaries inside one deployable — then extract services along seams that have proven themselves. Martin Fowler's "Monolith First" is the canonical reference.

S03How do you decide where the service boundaries go?

By business capability or Domain-Driven Design bounded context — never by technical layer. A "database service" and a "business logic service" is a distributed monolith, not microservices.

Tests for a good boundary
  • High cohesion: things that change together live together. If one business change requires editing four services, the boundary is wrong.
  • Loose coupling: the service can be deployed without coordinating with others.
  • Data ownership: exactly one service is the source of truth for each entity.
  • Team alignment (Conway's Law): one team should be able to own it end to end.
  • Independent scaling: its load profile differs from its neighbors.

In a pharmacy domain the seams might be: Prescription, Inventory, Patient, Claims/Adjudication, Notification, and Prior Authorization. Each has distinct vocabulary and distinct rates of change — the same word ("order") means different things in each, which is precisely what a bounded context is.

S04What is a distributed monolith and how do you recognize one?

The worst of both worlds: the operational complexity of microservices with the coupling of a monolith. Symptoms:

  • Services must be deployed together, in a specific order.
  • Multiple services share a database or a schema.
  • A single user action requires a synchronous chain of five service calls.
  • Changing one service's API breaks three others immediately.
  • You can't test a service without spinning up the whole system.

Cause is nearly always boundaries drawn by technical layer rather than business capability, or a shared database that was never split. This is a great question to have a crisp answer to — it demonstrates you've seen microservices go wrong, not just seen the diagrams.

S05Why database-per-service, and what does it cost?

Why: a shared database is the tightest possible coupling. If two services read the same tables, neither can change its schema independently, and you've lost the entire benefit of separate deployment. Private data also lets each service pick the right store — Mongo for documents, Postgres for relational, Redis for cache.

Costs, and these are the follow-up questions:

  • No cross-service joins. You compose in the application (API composition) or maintain a read model (CQRS).
  • No distributed transactions. You need sagas.
  • Data duplication. Multiple services may hold a copy of patient name; keeping them coherent is now your problem.
  • Eventual consistency. The system is briefly inconsistent by design, and the UI has to cope.
  • Reporting is hard. Usually solved by streaming everything into a warehouse or data lake.

The design heuristic: synchronous for queries, asynchronous for state changes and side effects. A checkout should synchronously verify inventory but asynchronously trigger email, analytics, and fulfilment — otherwise a down mail server takes down checkout.

Then name the danger of long synchronous chains: if each of five services is 99.9% available, the chain is 99.5%, and latency is additive. This is why "orchestrate synchronously" scales badly.

S07What is an API Gateway and what does it do?

A single entry point in front of your services. Responsibilities: routing, authentication and token validation, rate limiting, TLS termination, request/response transformation, response aggregation, caching, and metrics.

Why it exists: without it, every client needs to know every service's address, and every service has to implement auth and rate limiting itself. It also lets you refactor service boundaries without changing clients.

The risks to name: it's a single point of failure (run it highly available), it can become a bottleneck, and — most importantly — it can turn into a "god gateway" full of business logic, at which point you've recreated the monolith at the edge. Keep it to cross-cutting concerns.

Examples: AWS API Gateway, Kong, NGINX, Apigee, or a service mesh ingress.

S08What is Backend for Frontend (BFF)?

A gateway per client type rather than one shared gateway. A mobile BFF returns compact payloads tuned for cellular; a web BFF returns richer data; a partner BFF exposes a stable public contract.

It solves the problem where one API tries to serve clients with genuinely different needs and ends up serving none of them well — the same problem GraphQL attacks from a different direction. The cost is duplication across BFFs, which is usually acceptable because each is owned by the team that owns that client.

S09How do services find each other?
  • Client-side discovery: the client queries a registry (Consul, Eureka) and load-balances itself. Fewer hops; logic duplicated in every client.
  • Server-side discovery: the client calls a stable address (load balancer, Kubernetes Service) which resolves and routes. Simpler clients; an extra hop.
  • DNS-based: Kubernetes internal DNS. Simple and what most teams actually use.
  • Service mesh: a sidecar proxy (Envoy via Istio or Linkerd) handles discovery, load balancing, retries, mTLS, and telemetry outside your application code entirely.

The mesh answer is worth mentioning because it reframes several other questions: circuit breaking, retries, and mTLS all move out of your Node code and into infrastructure.

S10How do you version and evolve service APIs without breaking consumers?

Tolerant reader — consumers ignore fields they don't understand rather than failing validation on unknown properties. Additive-only changes — new optional fields and new endpoints are safe; removals, renames, and type changes are not. Expand and contract for breaking changes: add the new field, migrate consumers, then remove the old one once telemetry shows nobody uses it.

Back it with consumer-driven contract testing (Pact): each consumer publishes the subset of the contract it depends on, and the provider's CI fails if it breaks any of them. That's how you get confidence to deploy independently, which is the entire point of microservices.

Distributed data

S11Explain the saga pattern.

A saga replaces a distributed transaction with a sequence of local transactions, each publishing an event that triggers the next. If a step fails, you run compensating transactions to semantically undo the earlier steps.

Fill a prescription:
  1. Prescription svc  → mark PENDING_FILL       → RxPending
  2. Inventory svc     → reserve stock            → StockReserved
  3. Claims svc        → adjudicate with the PBM  → ClaimApproved
  4. Prescription svc  → mark FILLED              → RxFilled

If step 3 fails:
  2'. Inventory svc    → release the reservation
  1'. Prescription svc → mark REJECTED, notify the patient
Two coordination styles
ChoreographyOrchestration

The hard partsCompensations are semantic, not literal rollbacks — you can't un-send an email, so you send an apology. Intermediate states are visible to users, so the UI must show "processing." Every step must be idempotent because retries are guaranteed. And you need saga timeouts, or a stuck saga hangs forever.
S12Why not just use two-phase commit?

2PC gives you real ACID across services, but: it's a blocking protocol — if the coordinator dies after prepare, participants hold locks indefinitely; it requires every participant to support XA; it doesn't scale, because holding locks across network calls destroys throughput; and it reduces availability, because every participant must be up for any write to succeed.

Sagas trade atomicity for availability. That's a direct application of the CAP theorem, which is a good bridge to make explicitly.

S13Explain the transactional outbox pattern.

The problem: you need to update your database and publish an event atomically. You can't — they're two systems with no shared transaction. Write first and the publish may fail (event lost). Publish first and the write may fail (event lied).

The solution: write the event into an outbox collection in the same local transaction as the business change. A separate relay process reads the outbox and publishes to the broker, marking rows as sent.

await session.withTransaction(async () => {
  await rx.updateOne({ _id }, { $set: { status: 'FILLED' } }, { session });
  await outbox.insertOne({
    type: 'PrescriptionFilled', payload: { rxId: _id },
    createdAt: new Date(), sent: false
  }, { session });
});
// Relay (or a change stream / CDC tool) publishes and marks sent

Delivery becomes at-least-once, which is why consumers must be idempotent. In MongoDB you can implement the relay with a change stream on the outbox collection — connecting those two ideas is a strong answer.

S14What is CQRS, and when is it worth it?

Command Query Responsibility Segregation: separate the write model from the read model. Writes go through a normalized, validated model optimized for consistency; reads come from denormalized projections optimized for query shape, kept up to date by events.

Worth it when: read and write loads differ by orders of magnitude; reads need data from several services; the query shapes are wildly different from the write shape; or you need independent scaling of each side.

Not worth it when: it's basic CRUD. CQRS adds a whole synchronization pathway and forces you to handle eventual consistency in the UI.

Nuance worth statingCQRS does not require event sourcing, and event sourcing does not require CQRS. They're frequently taught together and are independent choices. Saying that is an immediate credibility marker.
S15What is event sourcing?

Instead of storing current state, store the immutable sequence of events that produced it. Current state is derived by replaying events; snapshots avoid replaying from the beginning every time.

Benefits: a complete audit trail by construction (very attractive in healthcare and finance), the ability to reconstruct state at any past point, temporal queries, and the ability to build new read models retroactively by replaying history.

Costs: significant complexity; schema evolution of old events is genuinely hard; "delete this user's data" collides with immutability and therefore with GDPR/HIPAA right-to-erasure; and querying current state requires projections. Most teams that adopt it regret it on domains that didn't need it.

S16How do you query data that lives in three different services?

Three options, with escalating complexity:

  1. API composition — a gateway or BFF calls each service and merges results. Simple, but latency is the sum, and it fails if any service is down. Fine for a handful of calls.
  2. CQRS read model — a service subscribes to events from all three and maintains a denormalized view purpose-built for this query. Fast reads, eventual consistency, extra infrastructure.
  3. Data warehouse / lake — stream everything into an analytical store for reporting. Right answer for BI; wrong answer for operational queries.

The wrong answer, which they may be baiting: querying another service's database directly. That reintroduces the shared-database coupling you split to avoid.

S17Explain eventual consistency and how you handle it in the UI.

In a distributed system with independent data stores, a change propagates asynchronously — for a window of milliseconds to seconds, different services disagree. The system converges, but "now" is not a globally consistent concept.

Handling it
  • Optimistic UI — show the expected result immediately, reconcile if the server disagrees.
  • Explicit pending states — "Submitting…", "Processing…". Users tolerate this if you tell them.
  • Read-your-own-writes — route a user's reads to the primary, or to a cache updated synchronously on their write, for a short window after they write.
  • Push updates — WebSocket or SSE so the client learns when convergence happens instead of polling.
  • Version tokens — the client passes the version it last saw, so the server can wait for or detect staleness.
Your materialThe stale-cache bug you fixed — Redux and localStorage not invalidating after a proxy submission, resolved by firing cache-busting post-success and adding an invalidation counter to drive a reactive re-fetch — is a read-your-own-writes problem solved in a single-service system. The reasoning transfers directly.

Resilience & operations

S18Explain the circuit breaker pattern.

A state machine wrapping calls to a dependency:

  • Closed — calls pass through; failures are counted.
  • Open — the failure threshold was crossed; calls fail immediately without attempting the network. This is the point: stop wasting resources and stop hammering a struggling dependency.
  • Half-open — after a cooldown, let a trial call through. Success closes the circuit; failure reopens it.

Why it matters: without it, a slow dependency causes your threads/sockets to pile up waiting, until your service is unavailable too. That's a cascading failure, and circuit breakers are the primary defense.

Pair it with a fallback: serve stale cache, a default, or a degraded response. Node libraries: opossum. In a service mesh it's configuration rather than code.

S19What is the bulkhead pattern?

Named after ship compartments: isolate resources so a failure in one area can't sink the whole vessel. Concretely, give each downstream dependency its own bounded connection pool or concurrency limit, so a slow claims service can't consume every socket and starve the inventory calls.

Also applies at the deployment level — separate instance pools for critical versus non-critical traffic, so a flood of report requests can't degrade prescription filling.

S20How do you do retries correctly?
  • Only idempotent operations. Retrying a non-idempotent POST double-charges someone.
  • Exponential backoff — 100ms, 200ms, 400ms — so you don't amplify load on a struggling service.
  • Jitter — randomize the delay. Without it, all clients retry simultaneously and create a thundering herd that re-kills the recovering service.
  • A retry budget / cap — 3 attempts, not infinite.
  • Respect Retry-After when the server sends it.
  • Don't retry 4xx — a 400 will be 400 forever. Retry 429, 502, 503, 504, and timeouts.
  • Beware retry amplification — if every layer retries 3 times, a 3-layer stack turns one request into 27.
S21How do you debug a request that crosses six services?

Three pillars, and you need all three:

  1. Distributed tracing — OpenTelemetry propagates a trace ID and span IDs through headers (W3C traceparent). Jaeger, Zipkin, X-Ray, or Datadog render the waterfall so you can see which span consumed the latency.
  2. Centralized structured logging — JSON logs shipped to one place (ELK, CloudWatch, Splunk), every line stamped with the correlation ID so one query reconstructs the whole request.
  3. Metrics — RED (Rate, Errors, Duration) per service and the four golden signals, so you know which service to look at before you start reading logs.

The framing that lands: observability is not optional in microservices — it's the thing that replaces the stack trace you lost when you split the monolith.

S23How do you deploy microservices safely?
  • Blue-green — two identical environments, switch traffic at the load balancer, roll back by switching back. Fast rollback, doubles infrastructure during the switch.
  • Canary — route 1%, then 5%, then 50%, watching error rates and latency at each step. Limits blast radius; needs good metrics and automation.
  • Rolling — replace instances gradually. Kubernetes default. Simple, but both versions run simultaneously, so your API must be backward compatible.
  • Feature flags — decouple deploy from release. Ship the code dark, turn it on for a cohort, kill it instantly without a redeploy. The most powerful of the four, and it makes trunk-based development viable.

Underpinning all of them: backward-compatible database migrations. Add a column, deploy code that writes both, backfill, deploy code that reads new, then drop the old — the expand/contract pattern. Never a migration that breaks the running version.

S24How do you handle configuration across many services?

Externalized configuration — never baked into the image, because the same artifact must be promotable from dev to prod unchanged. Environment variables for simple values, a config service or Parameter Store for shared values, Secrets Manager or Vault for secrets, and dynamic reload where you need to change behavior without a restart (feature flags being the common case).

The principle: one immutable artifact, many environments. If you rebuild the image per environment, you're testing something different from what you ship.

S25How do you migrate a monolith to microservices?

The strangler fig pattern, named for the vine that grows around a tree and eventually replaces it:

  1. Put a facade (proxy or gateway) in front of the monolith, routing everything to it.
  2. Identify a seam — a capability with clear boundaries and low coupling. Start with something valuable but not the most critical path.
  3. Build the new service; dual-write or sync data during transition.
  4. Route that capability's traffic to the new service at the facade, keeping the ability to route back.
  5. Remove the code from the monolith once traffic is fully cut over and stable.
  6. Repeat. The monolith shrinks; you're never in a big-bang rewrite.

Say explicitly that the data is the hard part, not the code. Splitting a shared database — deciding who owns which tables, breaking foreign keys, handling the transition period — is where these projects actually stall.

S26What is a service mesh and do you need one?

An infrastructure layer that puts a sidecar proxy next to every service instance, intercepting all traffic. It provides mTLS, retries, timeouts, circuit breaking, load balancing, traffic splitting for canaries, and telemetry — without any application code. Istio, Linkerd, AWS App Mesh.

Do you need one? Below roughly 15–20 services, probably not — it's substantial operational complexity and a real latency and resource tax per pod. Above that, having every team reimplement retries and circuit breakers in five languages is worse. The honest answer names the threshold rather than advocating either way.

D01Explain ACID.
  • Atomicity — all operations in a transaction succeed or none do.
  • Consistency — the transaction moves the database from one valid state to another, respecting all constraints.
  • Isolation — concurrent transactions don't observe each other's intermediate state (to the degree the isolation level promises).
  • Durability — once committed, it survives a crash, guaranteed by the write-ahead log.

The interesting follow-up is that Isolation is a dial, not a boolean — which leads directly to the next question.

D03Explain the CAP theorem, and why PACELC is more useful.

CAP: in the presence of a network Partition, you must choose between Consistency and Availability. You cannot have all three, because partitions are not optional — networks fail.

The common misreading is treating it as "pick two of three." Partition tolerance isn't a choice; the real decision is CP or AP during a partition.

PACELC extends it usefully: if Partitioned, choose A or C; Else (normal operation), choose Latency or Consistency. That second half is the one that actually governs day-to-day design — reading from a Mongo secondary is choosing latency over consistency with no partition in sight.

D04Normalization vs denormalization — how do you decide?

Normalization eliminates redundancy so each fact lives in one place: updates are cheap and anomalies are impossible, but reads need joins. Denormalization duplicates data so reads are single-fetch: reads are fast, but every update must touch every copy.

Decide by read/write ratio and consistency requirement. A ledger normalizes; a product catalog page denormalizes. In microservices you denormalize across service boundaries almost by necessity — the extended reference pattern is denormalization with a name.

D05What is an N+1 query problem and how do you fix it? 
// N+1: one query for the list, then one per item
const rxs = await Rx.find({ patientId });        // 1 query
for (const rx of rxs) {
  rx.drug = await Drug.findById(rx.ndcCode);   // N queries
}

// Fix: batch
const drugs = await Drug.find({ _id: { $in: rxs.map(r => r.ndcCode) } });
const byId = new Map(drugs.map(d => [String(d._id), d]));

It's the single most common cause of an API that's fast in dev and slow in production, because the N is 3 on your machine and 3,000 in prod. In GraphQL the fix has a name — DataLoader, which batches and caches per request. In ORMs it's eager loading. Being able to name it across three contexts (SQL, Mongo, GraphQL) shows the concept rather than the trick.

D06How does a B-tree index work, and when does the database ignore yours?

A balanced tree of sorted keys with pointers to rows, giving O(log n) lookup and efficient range scans because leaves are linked in order.

Why the optimizer might ignore it
  • Low selectivity — if the predicate matches 40% of rows, a sequential scan is genuinely cheaper than random I/O per row.
  • Function applied to the column — WHERE UPPER(name) = 'X' can't use an index on name. Use a functional/expression index.
  • Implicit type conversion — comparing a varchar column to a number forces a cast on every row.
  • Leading wildcard — LIKE '%abc' can't use a B-tree; you need a trigram or full-text index.
  • Stale statistics — the optimizer's row estimates are wrong.
  • Compound index prefix violated — querying only the second column of a compound index.
D07What Postgres-specific features would you mention?

  • jsonb with GIN indexes — document storage inside a relational database, which is why "Postgres or Mongo" is a live debate.
  • Index types — B-tree, GIN (arrays, jsonb, full text), GiST (geometry, ranges), BRIN (huge append-only tables), Hash.
  • EXPLAIN (ANALYZE, BUFFERS) — the actual plan with real timings and I/O.
  • CTEs and window functions — expressive analytical SQL without leaving the database.
  • Logical replication — the basis for CDC tools like Debezium.
  • Partial and expression indexes, table partitioning, LISTEN/NOTIFY for lightweight pub/sub.

D08SQL vs NoSQL — how do you actually choose?

Reject the framing first: "NoSQL" covers four unrelated families — document (Mongo), key-value (Redis, DynamoDB), column-family (Cassandra), and graph (Neo4j). They solve different problems.

Then answer on access patterns: relational when you have many entities with genuine many-to-many relationships and ad-hoc query needs; document when data is naturally hierarchical and read as a unit; key-value for caching and session state; column-family for enormous write volume with known query patterns; graph when the relationships are the data (drug interaction networks, provider referral graphs).

Then say polyglot persistence — most real systems use several, one per service, which is what database-per-service enables.

D09How does connection pooling work and how does it fail?

Establishing a database connection is expensive — TCP handshake, TLS, authentication, session setup. A pool keeps a set of open connections and hands them out.

Failure mode: pool exhaustion. Every request checks out a connection; if queries are slow or a code path forgets to release, the pool empties and requests queue in the application. The tell is latency that climbs with concurrency while the database itself looks idle.

Fixes: release in finally, set an acquisition timeout so you fail fast rather than hanging, size the pool deliberately (more connections is not better — each costs server memory and context switching), and never hold a connection across an await on a network call. In serverless, use a proxy like RDS Proxy because thousands of Lambda instances will otherwise exhaust the database's connection limit.

D10What is a deadlock and how do you avoid one?

Two transactions each hold a lock the other needs, so neither can proceed. The database detects the cycle and kills one as the victim.

Avoidance: always acquire locks in a consistent order (sort IDs before updating a batch), keep transactions short, use the lowest workable isolation level, and add appropriate indexes so the engine locks rows rather than ranges or pages. On the application side, catch the deadlock error code and retry — deadlock victims are safe to retry by definition.

D11How do you handle database migrations in a CI/CD pipeline?

Migrations live in source control, are versioned and forward-only, and run as an explicit pipeline step (Flyway, Liquibase, migrate-mongo, Prisma Migrate) — never by hand.

The critical constraint in a zero-downtime deployment is backward compatibility: during a rolling deploy, old and new code run simultaneously against one schema. So the expand/contract sequence: add the new column nullable → deploy code writing both → backfill → deploy code reading new → stop writing old → drop old in a later release. Four deploys to rename a column, and that's correct.

D12What is a materialized view and when would you use one?

A precomputed, physically stored query result, refreshed on a schedule or on demand. Use when an expensive aggregation is read far more often than the underlying data changes — a daily claims summary, a dashboard rollup.

Tradeoff is staleness. In Postgres, REFRESH MATERIALIZED VIEW CONCURRENTLY avoids locking readers. The MongoDB equivalent is $merge/$out writing an aggregation result to a collection — and conceptually, a CQRS read model is a materialized view maintained by events instead of by a refresh job.

Authentication & authorization

A01Authentication vs authorization vs accounting.

Authentication — who are you? (credentials, MFA, tokens). Authorization — what may you do? (roles, permissions, policies). Accounting/auditing — what did you do? (immutable audit log).

HTTP conflates the first two confusingly: 401 Unauthorized actually means unauthenticated; 403 Forbidden means authenticated but not permitted. Under HIPAA all three are required — audit logging of PHI access isn't optional.

A02Explain OAuth2 and its grant types.

OAuth2 is a delegated authorization framework — it lets an application act on a resource owner's behalf without handling their password. Four roles: resource owner (user), client (app), authorization server (issues tokens), resource server (your API).

PKCE (Proof Key for Code Exchange) closes the authorization-code interception attack: the client sends a hashed random verifier up front and the plaintext when exchanging the code, so a stolen code is useless. Originally for mobile, now recommended for all clients.

A03What's the difference between OAuth2 and OpenID Connect?

OAuth2 is authorization — it produces an access token that says what the bearer may do. It says nothing reliable about who the user is. Using an access token to identify a user is a well-known security mistake.

OIDC is a thin identity layer on top of OAuth2. It adds the ID token (a JWT with standardized claims about the user: sub, email, name, auth_time), a /userinfo endpoint, and a discovery document. If you want "log in with X," you want OIDC, not raw OAuth2.

The one-liner"Access token is for the API; ID token is for the client. Never send an ID token to an API, and never use an access token to identify a user."
A04What's inside a JWT and how do you validate one properly?

Three base64url segments separated by dots: header (algorithm, key ID), payload (claims), signature.

{ "alg": "RS256", "kid": "2026-07-a", "typ": "JWT" }
{ "iss": "https://auth.example.com",   // who issued it
  "sub": "user-9f2",                    // subject
  "aud": "pharmacy-api",               // intended audience
  "exp": 1785000000,                   // expiry
  "iat": 1784999100, "nbf": 1784999100,
  "jti": "01J8Z...",                   // unique ID — enables revocation
  "scope": "rx:read rx:write" }
Validation checklist — every item matters
  1. Verify the signature against the issuer's public key (fetched from JWKS via kid, cached).
  2. Pin the algorithm. Never trust the header's alg — see the next question.
  3. Check exp and nbf with a small clock-skew allowance.
  4. Check iss matches your expected issuer exactly.
  5. Check aud includes your API — otherwise a token minted for a different service is accepted.
  6. Check scopes/roles for the specific operation.

Base64 is encoding, not encryption. Anyone can read the payload. Never put PHI, PII, or secrets in a JWT.

A05What is the alg: none attack?

An attacker takes a valid token, edits the payload (say, "role": "admin"), sets the header to {"alg":"none"}, and strips the signature. A naïve library that reads alg from the untrusted header and honors "none" accepts it.

The related attack is algorithm confusion: a token signed with HS256 using the server's RSA public key as the HMAC secret, against a server that infers the algorithm from the header.

Defense: always pass the expected algorithm explicitly to the verifier — jwt.verify(token, key, { algorithms: ['RS256'] }). Being able to name this attack is a strong security signal.

A07Where should the client store tokens?

httpOnly; Secure; SameSite=Lax cookies, not localStorage. localStorage is readable by any JavaScript on the page, so a single XSS — including one in a third-party script — exfiltrates every token.

Cookies then need CSRF protection: SameSite=Lax or Strict covers most cases, plus a double-submit or synchronizer token for state-changing requests. The pattern many SPAs use is a BFF that holds the tokens server-side and gives the browser only a session cookie — the token never reaches JavaScript at all.

Interview trap"localStorage, it's fine because we sanitize inputs" is the wrong answer. The right answer names the XSS exposure and then discusses the CSRF tradeoff you accept in exchange.
A08How do refresh token rotation and reuse detection work?

Every time a refresh token is used, the authorization server issues a new refresh token and invalidates the old one. If an old token is ever presented again, that means it was stolen and replayed — so the server revokes the entire token family and forces re-authentication.

This turns a stolen refresh token from unlimited access into a detectable event with a short window. Combine with binding the token to a device or client, and with absolute (not just sliding) expiry.

A09RBAC vs ABAC vs ReBAC.
  • RBAC — permissions attach to roles, roles attach to users. Simple, auditable, and what most enterprises run. Fails when rules depend on context.
  • ABAC — decisions evaluate attributes of the subject, resource, action, and environment: "a pharmacist may view a prescription if they are at the dispensing store and it was written in the last 90 days." Flexible; harder to reason about and audit.
  • ReBAC — permissions derive from relationships in a graph ("is the treating physician of"). Google Zanzibar is the reference design.

Real systems are usually RBAC with attribute conditions layered on. In healthcare you additionally need break-the-glass — emergency override that grants access but generates a high-priority audit event.

A12What is IDOR and how do you actually prevent it?

Insecure Direct Object Reference: the API trusts an identifier from the request without verifying the caller may access that object.

// VULNERABLE — authenticated, but not authorized for THIS record
app.get('/api/prescriptions/:id', authenticate, async (req,res) => {
  res.json(await Rx.findById(req.params.id));
});

// FIXED — scope the query by the caller's identity
app.get('/api/prescriptions/:id', authenticate, async (req,res) => {
  const rx = await Rx.findOne({
    _id: req.params.id,
    $or: [{ patientId: req.user.patientId },
          { pharmacyId: { $in: req.user.authorizedPharmacies } }]
  });
  if (!rx) return res.status(404).end();  // 404, not 403 — don't leak existence
  res.json(rx);
});

The structural fix is enforcing the scope in the query rather than as a check after fetching, so a forgotten check can't return data. Returning 404 rather than 403 prevents enumeration of which IDs exist.

A13How do you store passwords?

A slow, salted, memory-hard hash: argon2id preferred, bcrypt acceptable and ubiquitous, scrypt fine. Never MD5, SHA-1, or plain SHA-256 — they're fast, which is exactly wrong for this purpose. Salt is per-password and stored alongside the hash (bcrypt embeds it). Use a constant-time comparison.

Tune the work factor so hashing takes ~100–250ms on your hardware, and revisit it as hardware improves. In Node, remember bcrypt is CPU-bound — use the async API so it runs on the libuv thread pool rather than blocking the event loop.

A14What is SSRF and why does it matter in AWS specifically?

Server-Side Request Forgery: your server makes an HTTP request to a URL the attacker controls. The classic AWS escalation is fetching http://169.254.169.254/latest/meta-data/iam/security-credentials/ — the instance metadata service — which returns temporary IAM credentials for the instance role.

Defenses: allowlist destination hosts rather than blocklisting; resolve DNS and validate the resulting IP is not private or link-local (and re-validate to defeat DNS rebinding); disable redirects or re-validate after each; and on AWS, enforce IMDSv2, which requires a session token obtained via PUT and therefore can't be reached by a simple SSRF GET. Naming IMDSv2 is a strong cloud-security signal.

A15How do you secure secrets in a Node application?

No secrets in source control, ever — and if one lands there, rotate it, because git history is forever. No secrets baked into container images. Environment variables are acceptable but leak into crash dumps, docker inspect, and process listings.

The mature setup: AWS Secrets Manager or Parameter Store, accessed via an IAM role attached to the compute (no static credentials anywhere), fetched at startup, cached in memory, with automatic rotation configured. Scan for committed secrets in CI (gitleaks, trufflehog).

A16Explain IAM users, roles, and policies.
  • User — a long-lived identity with static credentials. Minimize these; ideally humans use SSO/Identity Center instead.
  • Role — an identity with no permanent credentials that is assumed, producing temporary credentials via STS. This is how EC2, Lambda, and ECS tasks get permissions, and how cross-account access works.
  • Policy — a JSON document of Effect / Action / Resource / Condition. Identity policies attach to principals; resource policies (like an S3 bucket policy) attach to the resource and can grant cross-account access.
  • Permission boundary — a ceiling on what an identity policy can grant. Lets you delegate IAM administration safely.

Evaluation logic worth knowing: an explicit Deny always wins, otherwise an explicit Allow is required, otherwise implicit deny.

A17What does least privilege look like in practice?

Start from zero and add what breaks, rather than starting broad and trimming. Scope Resource to specific ARNs, never "*". Use Condition keys — source VPC endpoint, MFA present, tag matching. Use IAM Access Analyzer to generate policies from actual CloudTrail usage, and to find resources shared externally. Rotate and expire. Separate environments into separate accounts so a dev mistake can't touch production PHI.

A18What does HIPAA actually require of a backend engineer?

Not legal advice, but the engineering-relevant obligations:

  • Encryption in transit (TLS 1.2+) and at rest (KMS-backed).
  • Access controls — unique user identification, least privilege, automatic logoff.
  • Audit controls — log every access to PHI: who, what record, when, from where. Immutable and retained (commonly 6 years).
  • Minimum necessary — return only the PHI required for the purpose. This is an argument for sparse field projections, not just a policy statement.
  • Integrity — detect improper alteration.

W02Explain Lambda cold starts and how to mitigate them.

A cold start happens when no warm execution environment exists: AWS provisions one, downloads your code, starts the runtime, and runs initialization before your handler executes. Typically 100ms–1s for Node, worse with a large bundle or a VPC attachment.

Mitigations
  • Provisioned concurrency — keeps N environments warm. Costs money but eliminates cold starts for that capacity.
  • Smaller bundles — tree-shake, bundle with esbuild, use layers judiciously.
  • Initialize outside the handler — database clients, config, SDK clients created at module scope are reused across warm invocations.
  • More memory — CPU scales with the memory setting, so a higher setting can be both faster and cheaper.
  • Avoid VPC attachment unless you need it (much improved since hyperplane ENIs, but still not free).
W03Why is database connection pooling hard in Lambda?

Each concurrent invocation is a separate execution environment with its own pool. At 1,000 concurrent invocations with a pool of 10, you're asking the database for 10,000 connections — far past what most engines accept, and each connection costs server memory.

Answers: RDS Proxy (or a Mongo equivalent) to multiplex connections; set maxPoolSize: 1 per function; declare the client outside the handler so it's reused across warm invocations; set context.callbackWaitsForEmptyEventLoop = false; and consider whether a container on ECS/Fargate is simply a better fit for a database-heavy service. That last point — knowing when Lambda is the wrong tool — is the senior part of the answer.

W04ECS vs EKS vs Fargate vs Lambda — how do you choose?
  • Lambda — event-driven, spiky, short tasks. No infrastructure. Best cost at low or bursty volume.
  • Fargate — containers without managing servers. Good default for steady web services; simpler than EKS, more flexible than Lambda.
  • ECS on EC2 — you manage the instances; cheaper at scale and allows specialized hardware.
  • EKS — managed Kubernetes. Choose when you need the Kubernetes ecosystem, multi-cloud portability, or already have Kubernetes expertise. Highest operational overhead.

The judgment sentence: "Lambda for events, Fargate for services, EKS when you have a reason to need Kubernetes rather than a preference for it."

W05API Gateway vs Application Load Balancer.

API Gateway gives you request/response transformation, built-in authorizers (Cognito, Lambda, JWT), usage plans and API keys, throttling per client, caching, WAF integration, and native Lambda invocation. ALB gives you plain L7 routing at much lower per-request cost.

Rule of thumb: API Gateway for public or partner APIs where you want the managed features; ALB in front of ECS/EKS for internal, high-volume service traffic where per-request cost dominates. Many architectures use both.

W06What S3 features would you use in a healthcare application?
  • Presigned URLs — let clients upload and download directly without the file passing through your API. Time-limited and scoped.
  • SSE-KMS encryption with a customer-managed key, so key usage is auditable in CloudTrail.
  • Bucket policies + Block Public Access — enabled at the account level, not just per bucket.
  • Versioning + Object Lock — WORM retention for audit records and regulatory retention.
  • Lifecycle policies — transition to Infrequent Access then Glacier as records age.
  • Access logs / CloudTrail data events — required for PHI access auditing.
  • VPC gateway endpoint — traffic never leaves the AWS network.
W07How do you monitor a Node service on AWS?

Structured JSON logs to CloudWatch Logs, with metric filters or Embedded Metric Format to derive metrics from log lines. Custom metrics for business events (prescriptions filled per minute) alongside infrastructure metrics. Alarms on the four golden signals — latency, traffic, errors, saturation — routed to SNS and then to PagerDuty or Slack. X-Ray or OpenTelemetry for distributed tracing. CloudWatch Logs Insights for ad-hoc querying.

The point to make: alarm on symptoms users feel (error rate, p99 latency), not on causes (CPU). CPU at 90% with healthy latency is fine; that alarm just trains people to ignore alarms.

W08What is a VPC and how would you lay one out?

A logically isolated network. Standard layout: public subnets holding only the load balancer and NAT gateway; private subnets for application containers; isolated subnets with no route to the internet for databases. Security groups are stateful and act as instance-level firewalls; NACLs are stateless and act at the subnet level. VPC endpoints let you reach S3, Secrets Manager, and other AWS services without traversing the internet — which is both a security and a cost win.

Multi-AZ across at least two availability zones is the baseline for high availability, which is a JD-named requirement.

W09How do you design for high availability on AWS?
  • Multi-AZ deployment for every tier — application, database, cache.
  • Auto Scaling groups or ECS service auto-scaling with health-check-driven replacement.
  • Load balancer health checks that reflect readiness, not just process liveness.
  • Stateless application instances so any can be replaced at any time.
  • RDS Multi-AZ or Aurora with automatic failover; Mongo Atlas replica sets across AZs.
  • Graceful degradation — circuit breakers and fallbacks so a dependency's outage isn't yours.
  • Defined RTO and RPO, with tested restore procedures. Multi-region only if RTO demands it, because it roughly doubles cost and complexity.
W10What is infrastructure as code and why does it matter?

Defining infrastructure in versioned, reviewable code — Terraform, CloudFormation, or CDK — rather than clicking in a console. Benefits: reproducibility across environments, peer review of infrastructure changes, drift detection, disaster recovery by re-applying, and an audit trail of who changed what. In a regulated environment the audit trail alone justifies it.

Terraform is cloud-agnostic with a large ecosystem; CDK lets you write infrastructure in TypeScript, which is attractive when your team already writes TypeScript.

W11How do you keep AWS costs under control?

Right-size instances from actual utilization; use Savings Plans or Reserved Instances for steady baseline load and Spot for fault-tolerant work; S3 lifecycle policies; set CloudWatch log retention (the default is forever, and that bill surprises people); use VPC endpoints to avoid NAT gateway data charges, which are a classic hidden cost; tag everything for cost allocation; set budget alarms. Also: scale non-production environments down outside business hours.

An internet gateway allows two-way traffic for resources with public IPs in public subnets. A NAT gateway allows resources in private subnets to make outbound connections (to reach package registries, third-party APIs) while remaining unreachable from the internet. Add: secrets injected from Secrets Manager via the task definition, IAM task role rather than static credentials, logs to CloudWatch via the awslogs driver, and migrations run as a separate one-off task before the deployment.

W15What is CloudFront and when would you put it in front of an API?

A CDN. Obviously for static assets, but in front of an API it gives you edge TLS termination (shorter handshake round trips), AWS Shield DDoS protection, WAF integration, caching of cacheable GET responses at the edge, and origin failover. For a global user base it substantially cuts latency even for uncacheable requests, because the connection to the edge is short and the edge-to-origin leg rides AWS's backbone.

W16Explain the shared responsibility model.

AWS secures of the cloud — hardware, hypervisor, physical facilities, managed service internals. You secure in the cloud — your data, IAM configuration, network rules, OS patching on EC2, encryption choices, application code.

The line moves with the service: with EC2 you patch the OS; with Fargate you don't; with Lambda you patch neither but still own your dependencies. For HIPAA, AWS being HIPAA-eligible does not make your architecture compliant — you still need the BAA and the correct configuration. That distinction is a good one to state clearly in a healthcare interview.

Docker & CI/CD

You already work in Docker Compose daily, so this section is mostly about naming what you do and knowing the production-hardening details.

C01Image vs container vs layer.

An image is an immutable, layered filesystem template plus metadata. A container is a running instance of an image with a thin writable layer on top. Each Dockerfile instruction produces a layer, and layers are cached and shared between images — which is why ordering instructions correctly matters so much for build speed.

Containers are isolated by kernel features — namespaces for what a process can see, cgroups for what it can consume — not by virtualization. That's why they start in milliseconds and why they share the host kernel.

C02Write a production Dockerfile for a Node service and explain each decision. 
# ---- build stage ----
FROM node:22-slim AS build
WORKDIR /app
COPY package*.json ./
RUN npm ci                          # deterministic; cached unless lockfile changes
COPY . .
RUN npm run build && npm prune --omit=dev

# ---- runtime stage ----
FROM node:22-slim
ENV NODE_ENV=production
WORKDIR /app
COPY --from=build /app/node_modules ./node_modules
COPY --from=build /app/dist ./dist
USER node                           # never run as root
EXPOSE 3000
HEALTHCHECK --interval=30s --timeout=3s \
  CMD node -e "require('http').get('http://localhost:3000/health/live',r=>process.exit(r.statusCode==200?0:1))"
CMD ["node", "dist/server.js"]
The decisions worth explaining
  • Copy package*.json before source — dependencies only reinstall when the lockfile changes, which is the single biggest build-cache win.
  • npm ci not npm install — deterministic, faster, fails on lockfile drift.
  • Multi-stage — build tools and dev dependencies never reach the final image, cutting size and attack surface.
  • USER node — a container escape from root is far worse than from an unprivileged user.
  • .dockerignore — exclude node_modules, .git, .env; otherwise you ship secrets and bust the cache constantly.
  • Pin the base image, ideally by digest, and rebuild regularly for OS CVEs.
C03How do you handle signals and PID 1 in a container?

Your process runs as PID 1, which in Linux has special semantics: it doesn't get default signal handlers, and it must reap zombie children. If you use the shell form CMD node server.js, a shell becomes PID 1 and doesn't forward SIGTERM — so your graceful shutdown never runs and the orchestrator eventually SIGKILLs you mid-request.

Fix: use the exec form CMD ["node","server.js"], handle SIGTERM explicitly, and use --init or tini if you spawn child processes. This connects directly to the graceful-shutdown question in the Node section.

C04How do you pass configuration and secrets into containers?

Environment variables for non-sensitive config, injected at run time so one image works in every environment. Secrets from a secret store referenced in the task definition or via a mounted volume — never baked into the image, never in ENV lines (they're visible in docker history), and never in the build args of a published image.

For local development, Compose with a gitignored .env is fine; the mistake is letting that pattern reach production.

C05What does Docker Compose give you and where does it stop?

Compose declares a multi-container local environment — your API, Mongo, Redis, a Kafka broker — with networking, volumes, and dependency ordering, brought up with one command. It's excellent for development and for integration tests, where it lets you test against real dependencies rather than mocks.

It stops at production: no multi-host scheduling, no rolling updates with health gating, no autoscaling, no self-healing across nodes. That's what ECS and Kubernetes are for.

Your materialYou run containerized development on a Linux VM with Compose and a dev.sh workflow, push to a private registry, and have debugged real build problems — disk exhaustion and registry token failures. Concrete operational detail like that is far more convincing than reciting Docker concepts.
C06How do you reduce image size and why does it matter?

Multi-stage builds, slim or distroless base images, --omit=dev, a thorough .dockerignore, combining RUN steps that create and delete files in the same layer, and bundling with esbuild so you ship one file instead of a node_modules tree.

Why it matters: faster pulls mean faster deployments and faster autoscaling response; fewer packages mean fewer CVEs to triage; and registry storage and transfer cost money at scale.

C07Walk through a CI/CD pipeline you'd build.
  1. Trigger — push or PR.
  2. Static checks — lint, type-check, format. Fast, fails early.
  3. Unit tests with coverage thresholds.
  4. Integration tests against real dependencies in containers.
  5. Security — dependency audit, secret scanning, SAST.
  6. Build — Docker image tagged with the immutable commit SHA.
  7. Image scan — fail on high/critical CVEs.
  8. Push to registry.
  9. Deploy to staging automatically; run smoke and contract tests.
  10. Deploy to production — manual approval if required, then canary or blue-green with automated rollback on alarm.

Principles to state: one artifact promoted through environments (never rebuild per environment), fast feedback first, and everything reproducible from the commit SHA.

C08What's the difference between continuous delivery and continuous deployment?

Continuous delivery means every commit that passes the pipeline is deployable, but a human decides when to release. Continuous deployment means it goes automatically. Regulated industries usually stop at delivery because of change-control requirements — which is very likely the case in a pharmacy environment, and saying so shows domain awareness.

C09How do you handle database migrations in a deployment pipeline?

As a separate, explicit step before the application rollout, run as a one-off task using the same image. Migrations must be backward compatible so old and new code coexist during a rolling deploy — the expand/contract sequence. They must be idempotent and re-runnable. And you need a tested rollback plan, which for destructive changes usually means "don't do destructive changes in the same release as the code that stops using them."

C10How do you roll back a bad deployment?

Fastest path first: shift traffic back (blue-green switch, canary abort) or redeploy the previous immutable image tag. That's why tagging by commit SHA rather than latest matters — latest makes rollback ambiguous.

Then the caveats: rollback is only safe if the schema is backward compatible, and if the bad version wrote data in a new format you may need forward-fix instead. Feature flags sidestep much of this by letting you disable a code path without redeploying at all.

C11What's the difference between GitHub Actions, Jenkins, and GitLab CI?

Jenkins — self-hosted, enormously extensible via plugins, common in established enterprises. Cost is maintaining Jenkins itself, and plugin sprawl.

GitHub Actions — YAML in the repo, hosted runners, huge marketplace, tight GitHub integration. Self-hosted runners when you need VPC access.

GitLab CI — similar model, strong built-in security scanning and environments, integrated with GitLab's issue and registry features.

The answer that matters is that the concepts transfer entirely — stages, artifacts, caching, secrets, environments, approvals. Say that, and give an example of a pipeline you've actually shaped.

C12What is trunk-based development and why does it pair with CI/CD?

Everyone commits to a single main branch with very short-lived feature branches, merged at least daily. It avoids long-lived branches and the painful merges they produce, and it keeps main always releasable.

It requires feature flags to hide incomplete work, strong automated testing, and small changes. It pairs with CI/CD because continuous integration is meaningless if you integrate once a month. Contrast with GitFlow, which suits versioned, infrequently-released software and is increasingly out of favor for services.

C13How do you test a Docker build in CI without pushing broken images?

Build, then run the image and execute smoke tests against it in the pipeline before pushing. Use layer caching (registry cache or BuildKit cache mounts) so builds stay fast. Scan before push, not after. And tag the pushed image with the commit SHA plus a moving staging/production tag that points at what's actually deployed — so docker pull production is always meaningful.

C14What is a feature flag and what are its costs?

A runtime switch that decouples deployment from release: ship code disabled, enable for internal users, then a percentage, then everyone — and kill it instantly if metrics degrade. It also enables A/B testing and per-tenant rollouts.

Costs, which interviewers like to hear: flags accumulate into unmaintainable conditional sprawl if nobody removes them; every flag doubles the code paths you should be testing; and a flag evaluated at the wrong layer can leak inconsistent behavior mid-request. Good practice is a documented lifecycle with an expiry date per flag.

Messaging & event-driven systems

SNS, SQS, and Kafka are listed as preferred. Understanding the three delivery models — queue, topic, log — covers most of what gets asked.

Q01SQS vs SNS vs Kafka — explain the three models.
ModelDeliveryRetention
SQSQueueEach message to exactly one consumer — competing consumers share the workDeleted on acknowledgement (max 14 days)
SNSPub/sub topicA copy pushed to every subscriberNone — no replay
KafkaAppend-only partitioned logEvery consumer group reads independently at its own offsetConfigurable — days, weeks, or forever. Replayable

The canonical AWS pattern is SNS fan-out to SQS: publish once to a topic, each downstream service has its own subscribed queue, so each gets a copy and gets buffering, retries, and a dead-letter queue. If you learn one thing here, learn that.

Kafka's differentiator is retention and replay — you can bring up a brand new consumer and have it read a month of history to build its own view. Queues can't do that.

Q02What does at-least-once delivery mean and why does it force idempotency?

Most brokers guarantee a message arrives at least once, not exactly once. A consumer can process a message successfully and then crash before acknowledging — the broker has no way to distinguish that from a consumer that died before processing, so it redelivers.

Therefore every consumer must be safe to run twice with the same message. Techniques: use a natural idempotency key from the message and record processed IDs; make the operation naturally idempotent (set a value rather than increment it); or use conditional writes that fail on the second attempt.

The exactly-once mythTrue end-to-end exactly-once delivery is impossible across a network. Kafka's "exactly-once semantics" is exactly-once processing within Kafka via idempotent producers and transactional writes — it doesn't extend to your external database. Knowing that distinction is a strong signal.
Q03What is a dead-letter queue?

A separate queue where messages go after N failed processing attempts, so one malformed message ("poison message") can't block the queue forever while being retried infinitely.

The operational point most candidates miss: a DLQ is only useful if someone monitors it. Alarm on depth greater than zero, have a documented triage process, and build a replay mechanism so fixed messages can be reprocessed. An unwatched DLQ is a data-loss mechanism with extra steps.

Q04How do you guarantee message ordering?

Only within a partition or message group, never globally.

  • Kafka — messages with the same key hash to the same partition and are strictly ordered within it. Choose the key to match your ordering requirement: patient ID if events per patient must be ordered.
  • SQS FIFO — ordering and deduplication within a MessageGroupId, at lower throughput than standard queues.

The design consequence: ordering requirements limit parallelism, because you can only process one message per key at a time. Often the better answer is to design so order doesn't matter — include a version or timestamp and discard out-of-order updates.

Q05What is consumer lag and why do you alarm on it?

The gap between the newest offset in a partition and the offset a consumer group has processed. Growing lag means consumers can't keep up — the system is still working, but data is getting staler by the second, which in a claims-adjudication context is a business problem before it's a technical one.

Responses: scale consumers up to the partition count (you can't exceed it — that's the parallelism ceiling), increase partitions, batch processing, or find the slow downstream call. The equivalent in SQS is queue depth and age-of-oldest-message.

Q06Explain the dual-write problem.

You need to write to your database and publish an event. They're separate systems with no shared transaction, so there's no ordering that's safe: write-then-publish loses the event if the publish fails; publish-then-write announces something that didn't happen.

The answer is the transactional outbox — write the event to a table in the same local transaction, and have a relay publish it. Or change data capture — Debezium tailing the database log, or a MongoDB change stream — so the event is derived from the committed write rather than published alongside it.

Q07Event notification vs event-carried state transfer vs event sourcing.
  • Event notification — "PrescriptionFilled, id=9f2." Tiny payload; consumers call back for details. Keeps the event contract small but creates synchronous coupling on the callback.
  • Event-carried state transfer — the event carries the data consumers need, so they never call back. Removes runtime coupling; the event schema becomes a bigger contract and data may be stale.
  • Event sourcing — events are the system of record, not just notifications.

These are three different things frequently blurred together. Distinguishing them cleanly is an easy way to sound like you've built event-driven systems rather than read about them.

Q08How do you version event schemas?

The event schema is a public contract with consumers you may not control, so the same rules as API versioning apply — additive changes only, tolerant readers, and a version field in the envelope. A schema registry (Confluent Schema Registry with Avro or Protobuf) enforces compatibility at publish time, rejecting a producer change that would break existing consumers. That enforcement is the whole value, and it's a good thing to name.

For breaking changes: publish both versions in parallel to separate topics, migrate consumers, retire the old topic once telemetry shows it's unused.

Q09Is Kafka the same as Apache Kafka, and is it portable?

Yes — "Kafka" always means Apache Kafka, built at LinkedIn and donated to the Apache Software Foundation. It's open source and runs anywhere: self-hosted, AWS MSK, Confluent Cloud, Azure Event Hubs' Kafka endpoint, or protocol-compatible rewrites like Redpanda. Skills transfer across all of them because the wire protocol is the standard.

Client libraries exist for every major language — kafkajs and Confluent's official Node client. The broker itself is JVM-based, and since Kafka 4.0 it no longer requires a separate ZooKeeper cluster (KRaft mode replaced it). The processing ecosystem — Kafka Streams, Kafka Connect — is JVM-centric, so from Node you get producers and consumers, which covers most application work.

Q10When would you choose messaging over a synchronous call?

When the caller doesn't need the result to continue: notifications, analytics, search indexing, audit logging, document generation, third-party sync. When the work is slow or unbounded. When multiple consumers care about the same fact. When you need to absorb a load spike rather than propagate it. When the consumer's availability shouldn't affect the producer's.

Stay synchronous when the user is waiting for the answer and the answer must be correct now — an inventory check before confirming a fill.

Q11How do you test event-driven code?

Unit-test the handler as a pure function of the message. Integration-test with a real broker in a container (Testcontainers has Kafka and LocalStack modules) rather than a mock, because most bugs live in serialization, offset handling, and redelivery. Explicitly test the idempotency path by delivering the same message twice and asserting the state is unchanged. Test the DLQ path with a deliberately poisoned message. Contract-test the event schema.

Q12What is the outbox relay, concretely, in a Node + Mongo stack?

Two viable implementations. A polling relay: a background worker queries outbox.find({sent:false}).limit(100), publishes each to the broker, marks them sent, with a unique index and conditional update so two relay instances can't publish the same row twice. Simple, but adds polling latency.

A change stream relay: open a MongoDB change stream on the outbox collection and publish on insert, storing the resume token so you continue after a restart. Lower latency, and it's essentially CDC. Either way delivery is at-least-once, so consumers dedupe.

Section 12 · 12 questions

Testing & code quality

The JD says "ensure code quality through unit testing." That's a low bar as written, but the follow-ups go deeper — especially contract testing, which is what makes independent deployment safe.

T01Explain the test pyramid — and the criticism of it.

Many fast unit tests, fewer integration tests, very few end-to-end tests. The rationale: cost and flakiness rise as you go up, so put the bulk of your coverage where feedback is fastest.

The criticism worth raising: in microservices, unit tests with everything mocked verify almost nothing about whether services actually work together — you can have 95% coverage and a system that doesn't integrate. Hence the "testing trophy" alternative, which weights integration tests most heavily, and the emphasis on contract tests as the layer that gives you cross-service confidence without an end-to-end suite.

T02What makes a good unit test?
  • Tests behavior, not implementation. If a refactor that preserves behavior breaks the test, the test was wrong.
  • One reason to fail. When it goes red you should know what broke without debugging.
  • Deterministic. No real clocks, no randomness, no network, no shared state between tests.
  • Fast. Milliseconds. A slow suite doesn't get run.
  • Readable as documentation. Arrange/Act/Assert, with a name that states the expected behavior.

The architectural prerequisite: business logic must be separable from the framework. That's why the layered structure in N26 matters — services that import Express types can't be unit-tested cleanly.

T03When do you mock, and when is mocking harmful?

Mock at architectural boundaries you don't own — third-party APIs, payment providers, email. Don't mock what you own, and especially don't mock the database: most bugs live in query behavior, and a mocked repository tests only that your mock returns what you told it to.

The trap is over-mocking, where the test asserts on interactions ("was save called with these arguments?") rather than outcomes. Those tests break on every refactor and pass while the system is broken. Prefer real implementations in containers where feasible.

T04How do you test code that touches MongoDB?

Testcontainers spinning up a real MongoDB per test run, or mongodb-memory-server for speed. Real Mongo is strongly preferable to a mock because it exercises actual query semantics, index behavior, and validation.

Structure: seed deterministic fixtures per test, isolate tests (fresh database per suite, or drop collections between tests), and never share state. Avoid a shared test database across a CI matrix — parallel runs will interfere and you'll spend weeks chasing "flaky" tests that are actually a concurrency bug in your test setup.

T05What is consumer-driven contract testing?

Each consumer writes tests describing exactly what it needs from a provider — these requests, these response fields. Those expectations are published as a pact. The provider's CI replays every consumer's pact against the real provider and fails if any expectation breaks.

Why it's the key microservices testing pattern: it gives you the confidence of integration testing without deploying the whole system, and it tells you precisely which consumer a change would break. It also documents which fields are actually used, so you know what's safe to remove.

T06What does code coverage actually tell you?

Which lines executed during the test run. That's all. It does not tell you whether assertions were meaningful, whether edge cases are covered, or whether behavior is correct — you can reach 100% with tests that assert nothing.

The mature position: use coverage to find untested areas, not as a target. A hard 80% gate produces tests written to satisfy the gate. Better signals: mutation testing (does changing the code break a test?), and defect escape rate.

T07How do you test asynchronous and time-dependent code?

Inject the clock rather than calling Date.now() directly, so tests can control time. Use fake timers (jest.useFakeTimers()) for timeouts and intervals. Never sleep in a test hoping something finished — poll for a condition with a timeout, or expose a completion signal. For queues and events, assert on the resulting state rather than on timing.

T08How do you handle flaky tests?

Treat them as bugs, not noise. A flaky test is usually a real race condition, a shared-state leak between tests, or a timing assumption — and often the same race exists in production code. Quarantine it out of the blocking pipeline so it stops training people to ignore red builds, but track it and fix it. The worst outcome is a team that reflexively re-runs CI, because then a genuine failure gets re-run too.

T09What's your view on TDD?

A defensible, non-dogmatic answer: TDD is excellent where the specification is clear and the logic is intricate — pricing rules, dosage calculations, state machines — because writing the test first forces you to define the contract and produces a design that's testable by construction. It's weaker for exploratory work where you don't yet know the shape of the solution.

Interviewers are usually checking whether you're an ideologue in either direction. "I use it where it pays and don't pretend it's universal" is the answer that reads as experienced.

T10How do you ensure code quality beyond tests?

Automated: linting and formatting enforced in CI, TypeScript or JSDoc types, static analysis, dependency audits, and a coverage report as information rather than a gate. Human: small PRs (large ones get rubber-stamped), a review checklist, pair programming on risky changes, and an architecture decision record for choices that will confuse someone in a year.

The cultural point worth making: quality is a function of feedback speed. If CI takes 40 minutes, people batch changes and review quality drops.

T11What do you look for in a code review?

In priority order: correctness against the requirement; security (authorization checks, input validation, injection, secrets, PHI in logs); error handling and edge cases; test coverage of the actual behavior; performance implications at production data volumes (N+1, missing index, unbounded query); readability and naming; and only last, style — which should be automated anyway.

The signal you're a senior reviewer: asking "what happens if this is called twice?" and "what does this do when the downstream service is down?"

T12How do you test for performance before production?

Load testing with k6, Artillery, or Gatling against a production-like environment with production-like data volume — that last part matters most, because a query that's fine on 1,000 rows is a table scan on 10 million. Define targets first (p95 latency at X requests per second), test steady state, then spike, then soak for hours to catch memory leaks and connection exhaustion. Profile under load rather than under synthetic single-request conditions.

P01Walk me through how you handle a production incident.

  4. Diagnose using metrics → traces → logs, in that order. Metrics tell you where, traces tell you which hop, logs tell you why.

P02What is root cause analysis and how do you do it properly?

Five Whys — keep asking why until you reach something systemic rather than a proximate trigger.

The API returned 500s.

  Why? Requests held connections for 30+ seconds.
  Why? A query had no index and scanned the full collection.
  Why? The index existed in staging but was never applied to prod.
  Why? Index creation was a manual step, not part of the migration pipeline.

P03The API is slow but the database looks fine. What now?

  • Downstream calls — is a third-party API slow and are your timeouts too generous?
  • Serialization — are you stringifying enormous payloads?
  • GC pressure — check heap and pause times.
  • Network / TLS — no keep-alive means a fresh handshake per outbound call.
  • Noisy neighbor / throttling — CPU credits exhausted, or a container hitting its cgroup limit.

P04Memory usage climbs until the container is OOM-killed. Diagnose it.

First distinguish a leak from legitimate growth: does RSS return to baseline after GC, or trend upward monotonically? Then take two heap snapshots under load, diff them, and look at which constructors grew and what retains them.

Usual culprits: event listeners registered per request without removal, an unbounded cache or array at module scope, closures captured by a long-lived timer, a global map keyed by session with no eviction, or streams that are never destroyed on error. The meta-point: an unreproducible bug usually means an environment or data difference you haven't identified yet, not magic.

P06What are the four golden signals and RED metrics?

Golden signals (Google SRE): latency, traffic, errors, saturation. RED (per-service): Rate, Errors, Duration. USE (per-resource): Utilization, Saturation, Errors.

Section 14 · 14 questions

AI-assisted development, Spec-Kit & agents

The most unusual part of this JD, and therefore your biggest opportunity. Very few backend candidates can hold a real conversation about spec-driven development, agent workflows, or MCP. Prepare this section hardest relative to how "optional" it looks.

G01What is Spec-Driven Development?

A workflow where the specification — what you're building and why — is a versioned artifact in the repository that an AI agent reads and derives implementation from, rather than a document that gets written once and abandoned. The spec is the source; the code is the output. When requirements change, you change the spec and regenerate rather than re-prompting from scratch.

The distinction from a traditional PRD: a PRD is read by humans and then goes stale. A spec is re-read by the agent on every run, so drift is visible and correctable.

G02What is GitHub Spec Kit, specifically?

GitHub's open-source (MIT) toolkit implementing SDD. It's not a model and has no inference of its own — it's markdown prompt templates plus shell scripts that install into your repo and shape how your existing agent works. A CLI called specify scaffolds it: specify init --integration copilot writes prompt files into .github/prompts/, and slash commands appear in Copilot Chat.

The workflow is a sequence of commands, each reading the artifact the previous one wrote:

/speckit.constitution  → .specify/memory/constitution.md   # engineering non-negotiables, once per repo
/speckit.specify       → specs/001-feature/spec.md          # what & why, no tech stack
/speckit.clarify       → updates spec.md                    # agent interviews you on ambiguities
/speckit.plan          → plan.md, data-model.md, contracts/ # the technical decisions
/speckit.tasks         → tasks.md                           # ordered, reviewable work items
/speckit.analyze       → consistency report                 # does every requirement have a task?
/speckit.implement     → actual source code                 # the expensive step

Each arrow is a human review gate. That's the actual value: four cheap places to catch a misunderstanding before you're reviewing generated code.

G03What problems does SDD actually solve?
  • Intent evaporates. You explain the edge cases in chat, the chat closes, and next month nobody can reconstruct why the code branches the way it does. With SDD the reasoning is in a reviewed file.
  • Every session starts from zero. Two developers prompting the same agent about the same service get two different architectures. The constitution and spec are re-read every run, so output is consistent across people and sessions.
  • Constraints arrive last. Auth, audit logging, accessibility bolted on after the code exists. The constitution puts non-negotiables up front and the plan is checked against them.
  • Review has no baseline. Reviewers can check that a large AI diff compiles; they can't check it's what was asked for, because nobody wrote down what was asked for.
G04Is SDD a replacement for Agile, or for TDD?

Neither. It fits underneath your process. /speckit.taskstoissues pushes generated tasks into GitHub Issues, so your board stays where it is. Tests still verify behavior; the spec describes intent — several presets even enforce test-first ordering in the generated task list.

The common misread is that it's waterfall. It isn't — nothing is frozen. You edit the spec and regenerate, which is a tight loop rather than a phase gate. Being able to defuse that objection cleanly is worth rehearsing, because it's the first thing a skeptical interviewer will raise.

G05How does Spec Kit work in an existing codebase rather than a greenfield project?

This is the question that separates people who've read about it from people who've tried it. specify init --here installs alongside existing code without overwriting anything, but the templates know nothing about your architecture. The practical recipe:

  1. Before anything else, have the agent read the codebase and produce a docs/codebase-research.md — architecture, key modules, data flows, existing conventions. Then review and correct it yourself.
  2. Build the constitution from what's already true in the repo, not from an ideal.
  3. Spec only the change, never the whole system. Don't reverse-engineer specs for code nobody is touching.
  4. Reference the research doc from every spec so the agent has grounding.
  5. Keep tooling upgrades separate from spec changes.

And name the honest weak spot: multi-repo features. A change spanning a web app, a service, and a shared package has no clean home when specs live per-repo. That's an unsolved area, and saying so builds credibility rather than costing it.

G06When is SDD not worth the ceremony?

Small, well-understood changes. Adding a field, renaming a prop, fixing a null check — seven commands to move a button is the most common and most justified criticism. The split isn't ticket size, though; it's how much ambiguity there is about what correct looks like. A bug where nobody agrees what the correct behavior is is spec-shaped even though it's small.

Also note the lean path: for a medium change you can run specify → plan → implement and skip clarify, tasks, and analyze. And the constitution is worth having even if you never spec another thing, because you can point the agent at it for a one-line fix.

G07What's the cost model of SDD?

The license is free; the tokens are not. Spec Kit is context-heavy — spec, plan, and tasks are re-read on each run — and /speckit.implement is where the agent requests concentrate. On Copilot Business or Enterprise that draws on your premium-request allowance.

The honest framing: it costs more turns per feature than one-shot prompting, but replaces the invisible "generate, discover it's wrong, regenerate" cycle that never appears in anyone's cost estimate. Whether it pays off depends on the size and ambiguity of the work — which is a measurable thing, and saying you'd measure it on a pilot feature before rolling it to a team is the right answer.

G08How does Spec Kit compare to other SDD tools?
  • OpenSpec — lighter. Treats existing code as an immutable baseline and writes minimal delta specs for the change only. Cheaper and faster; better for routine brownfield work; weaker for greenfield architecture.
  • BMAD-METHOD — heavier. A simulated team of PM, architect, scrum master, and developer agents. More thorough, dramatically more expensive in tokens and wall-clock time.
  • AWS Kiro and similar — spec-driven workflow built into a proprietary IDE rather than into your repo. More integrated, less portable.

Because they all produce plain markdown, moving between them is mostly reformatting — you're not locking a codebase into a platform. That portability point is a good one to raise.

G09What is MCP and why does it matter?

The Model Context Protocol is an open standard for connecting AI models to external tools and data sources. Before it, every integration was bespoke — each agent needed custom glue for each system. MCP defines a common protocol: an MCP server exposes tools, resources, and prompts; any MCP-compatible client (Claude, Copilot, Windsurf, Cursor) can consume them.

The practical significance for this role: instead of an engineer manually querying a database, checking a ticket, and reading a runbook, you build an MCP server exposing those as tools and the agent orchestrates them. The JD's "building MCPs in Windsurf" line is asking exactly this.

An MCP server is a small program — Node with the official SDK works well — that declares tools with JSON Schema input definitions and implements handlers. The engineering discipline that matters is the same as any API: least privilege on the credentials it holds, validation of tool inputs, audit logging, and read-only by default with writes gated behind explicit confirmation. In a healthcare context, an MCP server touching PHI needs the same controls as any other PHI-accessing service.

G10What are Windsurf, Devin, Copilot agent mode — and how do they differ?
  • GitHub Copilot — inline completion plus chat plus an agent mode that can plan, edit multiple files, run commands, and iterate against test results. Deepest GitHub integration; assigns issues to an agent that opens a PR.
  • Windsurf — an AI-native IDE built around Cascade, an agentic flow that maintains awareness of your codebase across multi-step edits. Supports MCP servers, which is why the JD pairs it with MCP.
  • Devin — positioned as an autonomous software engineer that takes a task and works it end to end in its own environment, rather than assisting inside your editor.

The distinction that matters conceptually: completion (predict the next tokens), chat (answer a question with context), and agent (plan, act, observe the result, and iterate toward a goal). The last one is qualitatively different because it takes actions with consequences, which is why review discipline and permission scoping matter.

G11How do you use AI agents responsibly in a regulated environment?

This is the answer that separates a thoughtful adopter from an enthusiast, and in a pharmacy context it will be asked:

  • No PHI in prompts unless the tool is covered by a BAA and configured for it. Use synthetic or de-identified data in examples and tests.
  • Mandatory human review. Generated code is a proposal, not a commit. The risk isn't code that fails to compile — it's confident, well-formatted code with a subtle logic error that a reviewer skims past because the spec made it look considered.
  • Scoped permissions. An agent with production credentials is an incident waiting to happen. Read-only by default; writes behind explicit approval.
  • Auditability. Because specs and plans are committed files, you get a reviewable record of what was intended — which is genuinely useful for change control.
  • Licensing and provenance of generated code, and an SBOM.

Healthcare & pharmacy domain

Listed as "preferred," which means nobody expects you to have it — but a vocabulary pass buys a disproportionate amount of credibility. This section is about being able to hold the conversation, not about claiming experience you don't have.

H01What is PHI and what makes it different from ordinary data?

Protected Health Information: any individually identifiable health information held or transmitted by a covered entity. That includes the obvious (diagnoses, medications, lab results) and the less obvious 18 identifiers — name, address, dates more specific than year, phone, email, SSN, medical record number, device identifiers, IP addresses, biometrics, photographs.

What changes engineering-wise: PHI cannot appear in logs, URLs, error messages, JWTs, analytics, or lower environments. It must be encrypted at rest and in transit. Every access must be audited. And the minimum-necessary principle means you return only the fields required for the purpose — which is a genuine argument for sparse projections, not just a policy line.

H02What is HL7 v2 versus FHIR?

HL7 v2 is the legacy healthcare messaging standard — pipe-delimited segment-based messages (MSH|^~\&|...) sent over MLLP. It's decades old, enormously widespread, and notoriously loosely specified, so every implementation differs. You will encounter it in any established healthcare organization.

FHIR (Fast Healthcare Interoperability Resources) is the modern standard: RESTful, JSON or XML, built on discrete Resources — Patient, Practitioner, Medication, MedicationRequest, Observation, Encounter. It uses standard HTTP verbs and status codes, supports search parameters, and is genuinely hypermedia-driven.

The point that lands for a backend engineer: FHIR is a REST API specification. Everything in the REST section of this document applies — resource modelling, versioning, content negotiation, pagination via Bundle links. You are not learning a new paradigm, you're learning a domain vocabulary on top of one you already know.

H03What is NCPDP and why does it matter in pharmacy specifically?

The National Council for Prescription Drug Programs sets the standards that pharmacy runs on. The two that matter:

  • NCPDP Telecommunication Standard — the real-time claim format used between a pharmacy and a payer/PBM. When a pharmacist scans a prescription and gets an approval or rejection in seconds, that's an NCPDP claim transaction.
  • NCPDP SCRIPT — the e-prescribing standard used between prescribers and pharmacies, carried in the US primarily over the Surescripts network. New prescriptions, refill requests, cancellations, and change requests all have message types.

If you name NCPDP unprompted in a pharmacy interview, you will stand out immediately — it's the domain's defining acronym and most general backend candidates have never heard of it.

1. Prescription received     (e-prescribe via SCRIPT, or transcribed)

Architecturally, this is a textbook saga — multiple systems, no distributed transaction, and step 8 is literally a compensating action. Framing it that way in an interview is exactly the "connect the dots" answer, because it shows you can map an unfamiliar domain onto patterns you know.

H05What is a PBM and what is a formulary?

A Pharmacy Benefit Manager is the intermediary that administers prescription drug benefits for a health plan — it processes claims, negotiates with manufacturers, and manages the network of pharmacies. When a pharmacy submits a claim, the PBM adjudicates it.

A formulary is the plan's list of covered drugs, usually in tiers with different copays. Formulary status is what determines whether a claim pays, pays at a higher copay, or rejects with a message directing the pharmacist toward an alternative.

H06What is prior authorization, and why is it a hard engineering problem?

A requirement that the prescriber justify a medication before the plan will cover it. The claim rejects with a "PA required" code, then a separate workflow runs between prescriber, PBM, and pharmacy.

It's hard because it's long-running (hours to days), involves multiple parties with different systems, has many states, and must be resumable. That makes it a natural fit for an orchestrated saga with durable state, timeouts, and event-driven notification — and a terrible fit for synchronous request/response. Saying that demonstrates you can reason about an unfamiliar business process architecturally.

H09What is a controlled substance and what does it change technically?

Drugs scheduled by the DEA (Schedules II–V) with restrictions on refills, quantity, and transfer. Technically this brings: EPCS (Electronic Prescribing for Controlled Substances) with two-factor authentication and digital signatures on the prescription; reporting to state PDMPs (Prescription Drug Monitoring Programs); stricter audit trails; and business rules that differ by schedule and by state.

That last part — rules that vary by state — is the design challenge worth naming: it argues for a configurable rules engine rather than hard-coded logic, because you cannot ship a code change every time one state amends a regulation.

H10How would you design a prescription service for high availability?

Frame it with the domain stakes: this is a system where downtime means someone doesn't get their medication, so availability targets are genuinely different from a typical web app.

  • Multi-AZ, stateless services, no single point of failure.
  • Graceful degradation with explicitly defined modes — if the PBM connection is down, can you queue claims and dispense on a documented override path? That's a business decision you should ask about rather than assume.
  • Circuit breakers on every external dependency, especially the PBM and Surescripts, which are outside your control.
  • Idempotency everywhere, because a retried claim submission must not double-bill.
  • Async for everything non-critical — notifications, analytics, reporting — so they can never affect dispensing.
  • Comprehensive audit logging, which is both a compliance requirement and your forensic tool.
H11How do you handle PHI in non-production environments?

You don't copy production data down. Options: fully synthetic data generation, or de-identification per the HIPAA Safe Harbor method (removing the 18 identifiers) or expert determination. Both have caveats — de-identified data can lose the distribution characteristics that make performance testing meaningful, so you often need synthetic data at production volume even if it's fictional.

Also: separate AWS accounts per environment so a misconfiguration in dev cannot reach production PHI, and no production database credentials on developer machines.

H12What does an audit log need to contain in healthcare?

Who (authenticated identity, not a shared service account), what (the specific record accessed, by identifier), when (with timezone), where from (IP, device, facility), what action (read, create, update, delete, export, print), and the outcome (success or denial — denials matter as much as successes for detecting probing).

Properties: append-only and tamper-evident, retained per policy (commonly six years), queryable for investigations, and separated from application logs so retention and access controls differ. And the audit log itself contains PHI references, so it needs the same protections.

V01What's the fundamental difference between Angular and React?

React is a library for rendering UI; you assemble routing, state management, forms, and HTTP from the ecosystem. Angular is a full framework with all of that built in and prescribed — router, HTTP client, forms, dependency injection, testing utilities.

The practical consequence: Angular codebases look similar to each other and React codebases don't. That's a real advantage in a large enterprise with many teams, and a real cost in flexibility. Angular is TypeScript-first and uses decorators and classes heavily; React has moved toward functions and hooks.

V03What is dependency injection in Angular?

Components declare dependencies in their constructor and Angular's injector supplies them, resolved through a hierarchical tree of providers. A service provided at root is a singleton; provided in a component, it's scoped to that component and its children.

Why it matters: it makes testing straightforward — swap the real service for a stub in the test bed — and it's the mechanism Angular uses for shared state, which is why Angular apps often need less state-management library than React apps do. Conceptually it's the same idea as the dependency inversion in your Node service layer, applied to the frontend.

V04What is RxJS and why is it everywhere in Angular?

Reactive Extensions — a library for composing asynchronous streams. Angular's HttpClient, router events, and form value changes all return Observables rather than Promises.

An Observable differs from a Promise in three ways: it can emit many values over time, it's lazy (nothing happens until you subscribe), and it's cancellable (unsubscribe aborts the underlying work). That last one is genuinely useful — a typeahead search can cancel the in-flight request when the user types another character.

Operators worth naming: map, filter, switchMap (cancel the previous inner request — the correct choice for typeahead), mergeMap, debounceTime, distinctUntilChanged, catchError, takeUntil. The classic memory leak is subscribing without unsubscribing — solved with the async pipe in templates or takeUntilDestroyed.

V05How does change detection work in Angular?

By default, Zone.js patches async APIs (events, timers, XHR) so Angular knows when something might have changed, then it checks the entire component tree from the root. Simple, but wasteful on large trees.

ChangeDetectionStrategy.OnPush tells Angular to check a component only when an @Input reference changes, an event fires within it, or an observable it uses via the async pipe emits. That's the Angular equivalent of React.memo plus immutable props — and the same discipline applies: mutate an object in place and the view won't update.

Modern Angular is moving to Signals, which track dependencies precisely and allow zoneless change detection — very close to fine-grained reactivity in other frameworks.

Your materialYou cut 50–86 renders per component down by 85% on a React page. That is exactly this problem in different vocabulary. Say so — cross-framework recognition of the same performance pattern is more valuable than Angular-specific experience.
V06Template-driven vs reactive forms?

Template-driven puts the logic in the template with ngModel — quick for simple forms, harder to test. Reactive defines a FormGroup in the component class — explicit, synchronous access to values and validity, easy to unit test, and far better for dynamic or complex forms with cross-field validation.

For anything enterprise, reactive is the answer. It's conceptually similar to a controlled form with a schema in React.

V07What are modules, and what changed with standalone components?

Historically every Angular component belonged to an NgModule that declared it and imported its dependencies — a source of significant boilerplate and confusion. Modern Angular supports standalone components that declare their own imports directly, removing NgModules from most applications.

Knowing that the framework moved this direction is a useful currency signal: it tells the interviewer you looked at Angular recently rather than remembering it from 2018.

V08What are route guards and resolvers?

Guards run before navigation and can permit, block, or redirect — CanActivate for auth checks, CanDeactivate for unsaved-changes warnings. Resolvers fetch data before the route activates so the component renders with data already present, rather than flashing a loading state.

Guards are the frontend half of authorization — and the point worth making is that they're a UX affordance, not a security control. The server must still enforce every rule, because a guard is trivially bypassed. That connects directly to the authorization discussion in the security section.

V09What are HTTP interceptors?

Middleware for outbound HTTP: attach auth tokens, add correlation IDs, retry on failure, handle 401 by refreshing the token, log, or show a global loading indicator. Registered once and applied to every request through HttpClient.

Structurally identical to Express middleware, applied on the client side — a nice symmetry to point out if you're asked to compare frontend and backend architecture.

V10How should you position Angular in the interview?

Directly: "My production depth is React and TypeScript. I've mapped the Angular equivalents — dependency injection instead of context, RxJS instead of promises and effects, OnPush instead of memo, reactive forms instead of controlled components with a schema. The architectural concerns are identical, and I'd expect to be productive in a couple of weeks with a real ramp on RxJS operators specifically."

Naming RxJS as the genuine learning curve is what makes that answer credible rather than glib — it's the part that actually takes time, and admitting it signals you've looked properly.
